# Modulix

[![CI](https://github.com/gulerseker08-art/modulix/actions/workflows/ci.yml/badge.svg)](https://github.com/gulerseker08-art/modulix/actions/workflows/ci.yml)

AI destekli, modüler, multi-tenant kurumsal iş yönetim platformu: birden fazla sektörün iş süreçleri aynı SaaS üzerinde. Pilot sektör lojistik; sıra Çekirdek → CRM → Lojistik → Antrepo → İK → Muhasebe. Tüm ekranlar mobil uyumlu.

Mimari kararlar `docs/adr` klasöründe, yol haritası [`docs/yol-haritasi.md`](docs/yol-haritasi.md) dosyasındadır.

Bu klasörün içeriğini boş repo klasörünüze kopyalayın, sonra repo kökünde çalıştırın:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\init-solution.ps1
```

## Veritabanı (Görev 2 / ADR-0002, ADR-0020)

SQL Server 2025 Developer, Docker içinde çalışır; bilgisayarınıza ayrıca SQL Server kurmanız gerekmez.

Mimari: **tek paylaşımlı veritabanı** (ADR-0002; ADR-0009'un tenant başına veritabanı modeli ADR-0020 ile geri alındı).
Bütün tenant'lar aynı veritabanındadır; platform tabloları globaldir, iş tabloları `TenantId` taşır ve iki katmanla
korunur: EF global query filter + SQL Server Row-Level Security. İşletim ayrıntıları `docs/tenant-isletim.md`.

| Ayar | Değer |
| --- | --- |
| Sunucu | `localhost,14333` (1433 değil; yerel SQL Server'ınızla çakışmasın diye) |
| Veritabanı | `Modulix` (tek; platform şeması: kullanıcılar/kimlik, tenant kayıtları, üyelikler, modül erişimleri, oturumlar, e-posta kuyruğu, outbox; diğer şemalar: tenant iş verisi, Row-Level Security altında) |
| Şemalar | `platform`, `core`, `meta`, `crm`, `logistics`, `ai` |
| `modulix_app` | Uygulamanın kullanıcısı. Veri okur/yazar; tablo veya güvenlik politikası değiştiremez; `core.AuditLog`'u değiştiremez. |
| `modulix_migrator` | Migration kullanıcısı (db_owner). |
| `sa` | Yönetici; SSMS ile bakmak için. |

Tek EF bağlamı vardır: `ModulixDbContext` (kimlik ve platform tabloları dahil). Her bağlantı açılışında aktif tenant oturuma yazılır, RLS onu uygular; aktif tenant yoksa hiçbir tenant satırı görünmez ve yazılamaz; istemci tenant seçemez. `MembershipId` taşıyan tenant tabloları (`core.MembershipRoles`, `core.TeamMembers`, `core.MembershipCompanies`) `platform.Memberships`'e bileşik yabancı anahtarla bağlıdır.

Şifreler repo kökündeki `.env` dosyasındadır. Bu dosya ilk çalıştırmada rastgele şifrelerle oluşturulur ve git'e gönderilmez. Uygulama bağlantı cümlelerini `dotnet user-secrets` üzerinden okur (`Modulix` = app, `ModulixMigrations` = migrator); kod deposunda şifre bulunmaz.

**SSMS ile bağlanmak:** Sunucu `localhost,14333`, SQL Server Authentication, kullanıcı `sa`, şifre `.env` içindeki `MSSQL_SA_PASSWORD`. Bağlantı penceresinde "Trust server certificate" seçin.

**Yeni migration eklemek** (tek zincir, `Persistence/Migrations`):

```powershell
# Yeni tenant tablosunu ayrıca RLS'e ekleyin: TenantIsolationSql.AddTable
dotnet ef migrations add <Ad> --project src/Modulix.Infrastructure --startup-project src/Modulix.Api
powershell -ExecutionPolicy Bypass -File scripts\db-up.ps1
```

Migration'ları `dotnet ef database update` ile değil, `db-up.ps1` ile uygulayın; `db-up.ps1` bekleyen migration'ları (`dotnet run --project src/Modulix.Api -- migrate`) uygular. Böylece yalnızca migration kullanıcısı şema değiştirir. Tek veritabanı bütün tenant'ları etkilediği için migration'lar geriye uyumlu ve kesintisiz yazılır (önce ekle, sonra taşı, en son kaldır).

## Giriş ve aktif tenant (Görev 4)

Kimlik doğrulama ASP.NET Core Identity ve şifreli, `HttpOnly`, `Secure`, `SameSite=Strict` bir oturum çereziyle yapılır. Kullanıcı birden fazla tenant'a üye olabilir.

| Uç nokta | Ne yapar |
| --- | --- |
| `POST /api/auth/login` | Giriş. Tek üyelik varsa o tenant otomatik seçilir. 5 hatalı denemede hesap 15 dakika kilitlenir. |
| `GET /api/auth/me` | Kullanıcı, etkin üyelikleri ve aktif tenant. |
| `POST /api/auth/active-tenant` | Aktif tenant seçimi. Yalnızca etkin üyeliği olan tenant seçilebilir. |
| `POST /api/auth/active-company` | Aktif işletici şirket seçimi (ADR-0008). Yalnızca o oturumda erişilebilir şirket seçilebilir. |
| `GET /api/tenant/current` | Aktif tenant; yoksa 403. |
| `POST /api/auth/logout` | Çıkış. |

Aktif tenant her istekte veritabanından yeniden doğrulanır: üyelik devre dışı bırakılır veya tenant kapatılırsa erişim bir sonraki istekte kalkar. İstemcinin gönderdiği bir başlık veya parametre tenant belirlemez.

### İşletici şirketler ve aktif şirket (ADR-0008)

Bir tenant birden fazla **işletici şirket** (`core.Companies`) barındırabilir; bunlar sizin belge kesen, hesap tutan tüzel kişilerinizdir (müşteri firma `core.party` değildir). Her tenant'ın en az bir **varsayılan şirketi** vardır. Aktif şirket oturumda sunucu tarafında tutulur (`modulix:company_id` claim'i) ve her istekte erişilebilir şirketlere karşı yeniden doğrulanır; açık bir seçim yoksa veya erişilemezse varsayılan şirkete düşer.

Erişilebilir şirketler: **yönetici** (sistem rolü) tenant'ın bütün şirketlerine erişir; yönetici olmayan kullanıcı yalnızca üyeliğine atanan şirketleri görür (`core.MembershipCompanies`), hiç atama yoksa yalnızca ortak veriyi görür. Erişilebilir şirketler ve aktif şirket `GET /api/tenant/access` ile gelir; arayüzdeki şirket seçici yalnızca birden fazla şirkete erişim varsa görünür.

| Uç nokta | Ne yapar | İzin |
| --- | --- | --- |
| `GET /api/companies` | İşletici şirketleri listeler | `core.companies.manage` |
| `POST /api/companies`, `PUT /api/companies/{id}` | Şirket ekler, yeniden adlandırır (varsayılan şirket silinmez/kapatılmaz) | `core.companies.manage` |
| `GET`/`POST /api/companies/{id}/branches`, `PUT /api/companies/{id}/branches/{branchId}` | Şirketin şubelerini listeler, ekler, yeniden adlandırır | `core.companies.manage` |
| `GET`/`PUT /api/memberships/{id}/companies` | Bir üyeliğin şirket görevleri (tarih ve varsayılan şube ile) | `core.companies.manage` |

Şirket/şube oluşturma-yeniden adlandırma ve şirket görevi değişikliği denetim kaydına yazılır.

**Geçici vekâlet (adım 5):** Bir şirket görevi `ValidFrom`/`ValidUntil` taşıyabilir (ikisi de boş = süresiz; `ValidUntil` dolu = vekâlet). Süresi dolunca erişim kendiliğinden kapanır — erişilebilir şirketler sorgusu yalnızca o an geçerli görevleri sayar; ayrı bir "doldu" denetim kaydı yazılmaz (ADR-0008 kararı birebir). Geçmişte biten vekâlet reddedilir.

**Şube/lokasyon (adım 5):** Şube (`core.Branches`) idari bir birimdir; **kapsam sınırı değildir** ve hiçbir kaydı süzmez. Bir üyeliğin şirket görevi isteğe bağlı varsayılan şube taşıyabilir; şube, görevlendirilen şirkete ait olmalıdır.

**Şirket başına ayar (adım 5):** Bir ayar tanımı `SettingDefinition.PerCompany` ile şirket başına yapılabilir işaretlenebilir; o zaman değeri aktif işletici şirkete göre saklanır/çözülür (tenant geneli ayarlar eskisi gibi çalışır). Çerçeve kuruldu; ayarın kendisi (numaralama, para birimi, takvim, belge şablonu) ilgili modülün işidir, çekirdek henüz hiçbir ayarı `PerCompany` yapmaz.

**Kayıt şirket kapsamı (adım 3):** Bir kayıt türü şirket kapsamlıysa (`IRecordStore.CompanyField` dolu; ör. ileride fatura, cari hareket) kayıt boru hattı şirketi de uygular: okumada yalnızca erişilebilir şirketlerin kayıtları döner (yönetici ve şirket bağlamı olmayan arka plan/sistem tenant genelini görür), kapsam dışı kayıt "bulunamadı" görünür; oluştururken `CompanyId` verilmemişse aktif şirkete düşer ve erişilebilir olmalıdır; güncelleme kaydın şirketini değiştiremez (taşıma ayrı bir işlemdir). Olay zarfı yalnızca şirket kapsamlı kaydın `CompanyId`'sini taşır (CRM'deki müşteri-firma `companyId`'si sızmaz). Şu an bütün tenant tabloları "ortak"tır; mekanizma ilk şirket kapsamlı modül (Muhasebe/Depo) geldiğinde devreye girer.

**Örnek kullanıcılar** (yalnızca geliştirme, `scripts\db-up.ps1` oluşturur; şifre `Modulix.Demo1`):

| Kullanıcı | Üyelik |
| --- | --- |
| `ayse@acme.demo` | Acme Lojistik |
| `mehmet@beta.demo` | Beta Taşımacılık |
| `deniz@ortak.demo` | İkisi de (tenant seçmesi gerekir) |
| `platform@modulix.demo` | Hiçbiri; platform yöneticisi (girişte `/platform`'a gider) |

Elle denemek için Visual Studio'da `src/Modulix.Api/Modulix.Api.http` dosyasını açın.

## Modüller, roller ve izinler (Görev E4)

Her modül kendini tek bir `IModule` uygulamasıyla tanıtır (`Modulix.Core.Contracts.Modules`): anahtar (ör. `crm`), ad ve izin listesi. İzin anahtarları modül anahtarıyla başlar (`crm.companies.read`). Modüller `src/Modulix.Api/Program.cs` içinde `AddModulixModules(...)` ile kaydedilir; kaydedilmeyen modül mimari testi kırar.

| Kavram | Nerede | Kural |
| --- | --- | --- |
| Modül hakkı (entitlement) | `platform.ModuleEntitlements` | Tenant başına açık/kapalı. Kaydı olmayan modül kapalıdır; `core` her zaman açıktır. Kapatma veri silmez. |
| Rol | `core.Roles` | Tenant'a özel; ad ve izin listesi. Row-Level Security ile korunur. |
| Rol ataması | `core.MembershipRoles` | Rol üyeliğe atanır; aynı kişinin her tenant'ta ayrı rolleri olur. Başka tenant'ın rolü veritabanı düzeyinde de atanamaz. |

Geçerli izin = kullanıcının rollerindeki izinler ∩ tenant için açık modüller. Rol veya modül değişikliği bir sonraki istekte geçerli olur. Modül uç noktaları `.RequirePermission(CrmModule.Permissions.CompaniesRead)` veya `.RequireModule("crm")` ile korunur; izin yoksa 403 döner.

| Uç nokta | Ne yapar | İzin |
| --- | --- | --- |
| `GET /api/tenant/modules` | Kayıtlı modüller ve aktif tenant için açık olanlar | Aktif tenant |
| `GET /api/tenant/access` | Oturumdaki kullanıcının açık modülleri ve geçerli izinleri | Aktif tenant |
| `GET /api/roles` | Rolleri listeler | `core.roles.manage` veya `core.users.manage` |
| `POST /api/roles`, `PUT /api/roles/{id}` | Rol ekler, düzenler | `core.roles.manage` |
| `GET /api/roles/permissions` | Rollere atanabilecek izinler (yalnızca açık modüllerin) | `core.roles.manage` |
| `GET`/`PUT /api/memberships/{id}/roles` | Bir üyeliğin rolleri | `core.users.manage` |

Örnek veride Acme'de CRM ve Lojistik, Beta'da yalnızca Lojistik açıktır; örnek kullanıcıların hepsi kendi tenant'larında "Yönetici" (sistem) rolündedir.

### Yönetim izinleri ve "Yönetici" rolü (Y1)

| İzin | Ne verir |
| --- | --- |
| `core.users.manage` | Kullanıcıları davet eder, rollerini atar, devre dışı bırakır, şifre sıfırlama bağlantısı gönderir (Y2) |
| `core.roles.manage` | Rolleri ve izinlerini tanımlar (Y3) |
| `core.settings.manage` | Firma ayarlarını yazar (`core.tenant-setting`); okumak için izin gerekmez |
| `core.audit.read` | Denetim kaydını okur (ekranı Y5'te) |

- Her tenant'ta bir **sistem rolü** vardır: "Yönetici". İzin listesi tutmaz; tenant için açık tüm modüllerin tüm izinlerini verir, yeni açılan modülün izinleri de kendiliğinden gelir. Adı ve izinleri değiştirilemez (409). `IRoleService.EnsureSystemRoleAsync` oluşturur; `SystemRole` migration'ı eski "Yönetici" rollerini sistem rolüne çevirdi ve `core.roles.manage` olan rollere diğer üç yönetim iznini ekledi.
- **Son yönetici korunur:** etkin üyeliği olan son yöneticinin Yönetici rolü kaldırılamaz (409). Kural `AdministratorGuard` içindedir; aynı anda birbirinin yetkisini kaldırmaya çalışan iki yöneticiden yalnızca biri geçer.
- Rol oluşturma, rol düzenleme ve rol atamaları denetim kaydına yazılır (`core.role`, `core.membership`).
- Gezinme: sol üstteki **ModuliX** logosu "Tüm Uygulamalar" panelini açar (ana uygulamalar → alt uygulamalar; ana uygulamalar `AppCatalog.Groups` başlıkları altında kümelenir: Satış ve müşteri / Müşteri hizmetleri / Yönetim — yalnızca görsel kümeleme, modül sahipliği ve izinler değişmez; en az iki grup görünürken ve arama yokken başlık çıkar; CRM'in alt uygulamaları da aynı yolla Müşteri ve satış süreci / Teklif / Ürün ve fiyat / Satış performansı bölümlerine ayrılır — yeni gruplama bir `AppGroup` satırı ve tanımlara `Group:` eklemektir); sol menü route'tan bulunan aktif modülün sayfalarını gösterir. Liste `Modulix.Web/Services/AppCatalog.cs` içindeki ortak tanımdan gelir; görünürlüğü tenant modül sahipliği, platform yöneticiliği ve izinlerle `AppNavigation` hesaplar. Yeni ekran/modül bu listeye satır eklemektir. Menüde gizlemek yetkilendirme değildir; route (`AuthGate`) ve sunucu denetimleri aynen geçerlidir.
- Arayüzde yönetim izinlerinden biri olan kullanıcı menüde **Yönetim** bölümünü görür (`/yonetim`). Modül açıp kapatmak için şimdilik bir uç nokta yoktur (platform yöneticisi rolü sonraki görev); kodda `IModuleEntitlements.SetEnabledAsync` kullanılır.

### Kullanıcı yönetimi (Y2)

Ekran: **Yönetim → Kullanıcılar** (`/yonetim/kullanicilar`). Uç noktalar `/api/users` altındadır ve `core.users.manage` ister; kimlik üyelik kimliğidir, başka tenant'ın üyeliği 404 döner.

- **Davet:** `POST /api/users/invitations` (e-posta, ad, roller). E-posta kayıtlı değilse şifresiz hesap ve "Davet bekliyor" üyeliği oluşur, kişiye `/davet?uyelik=…&token=…` bağlantısı gider; kişi şifresini belirler ve doğrudan giriş yapar. Bağlantı 7 gün geçerli ve tek kullanımlıktır (şifre belirlenince hesabın güvenlik damgası değişir). E-posta başka bir tenant'ta kayıtlıysa üyelik hemen etkin olur ve bilgi e-postası gider; şifre değişmez. Zaten üyeyse 409. Daveti yeniden gönderme (1 dakikada bir) ve iptal etme vardır; iptal edilen davetin bağlantısı çalışmaz.
- **Sınır:** tenant başına saatte en fazla 50 davet (`Users:MaxInvitationsPerHour`); aşılırsa 429.
- **Devre dışı bırakma:** `POST /api/users/{id}/disable` ve `/enable`. Kişi kendini devre dışı bırakamaz; son etkin yönetici korunur. Devre dışı üye bir sonraki isteğinde 403 alır; diğer tenant'lardaki üyelikleri ve kayıtları kalır.
- **Şifre sıfırlama ve kilit:** yönetici kişiye 24 saat geçerli bir bağlantı gönderir (`/sifre-sifirla`); şifreyi görmez ve belirlemez. 5 hatalı denemeyle kilitlenen hesabın kilidi açılabilir. Hesap birden fazla tenant'ta kullanılıyorsa ikisi de hepsini etkiler; e-postada isteyen tenant yazılır.
- **Yönetici kuralı:** Yönetici rolünü vermek veya almak ve bir yöneticinin hesabında işlem yapmak yalnızca yöneticiye açıktır (403). Böylece `core.users.manage` izni olan biri kendini yönetici yapamaz. Rol atamasında kural yönetici kilidi altında denetlenir.
- **Kayıt devri (Y2b, [ADR-0004](docs/adr/0004-kayit-devri.md)):** devre dışı bırakırken kişinin sorumlu olduğu kayıtlar başka bir etkin üyeye devredilebilir (`POST /api/users/{id}/disable` gövdesi `{ "transferToMembershipId": … }`); devre dışı kişinin kayıtları sonradan da devredilir (`/transfer-records`). Sayılar: `GET /api/users/{id}/owned-records`. CRM'de firmalar, açık fırsatlar ve açık aktiviteler devredilir; kapanmış olanlar eski sorumlusunda kalır. Devir kayıt boru hattından geçer: işlemi yapanın kayıtları düzenleme izni olmalı, her kayıt denetim kaydına düşer; devir ve devre dışı bırakma birlikte yapılır ya da hiç yapılmaz. Yeni bir modül, sorumlu alanı `ownerId` olan kayıt türlerini `IModule.OwnedRecords` ile bildirir. Yeni sorumluya kayıt başına atama e-postası değil, devrin tek özeti gider ([Olaylar](#olaylar-ç1)).
- Davet, iptal, durum değişikliği, şifre sıfırlama isteği ve kilit açma `core.membership` kaydı olarak denetim kaydına yazılır. Son giriş, giriş ve tenant seçiminde güncellenir.
- **E-postadaki bağlantılar** `App:PublicUrl` adresiyle oluşturulur (ör. `https://app.firmaniz.com`). Canlı ortamda zorunludur: isteğin adresine güvenilirse saldırgan, kendi sunucusuna giden şifre sıfırlama bağlantıları ürettirebilir. Development'ta boşsa isteğin adresi kullanılır. Yerelde e-postalar Mailpit'te görünür (http://localhost:8025).

### Roller ve izinler (Y3)

Ekran: **Yönetim → Roller** (`/yonetim/roller`). Uç noktalar `/api/roles` altındadır ve `core.roles.manage` ister.

- **İzin matrisi:** rol formunda izinler modüle ve kaynağa göre gruplanır (Firmalar, Sevkiyatlar…; sütunlar görüntüleme ve düzenleme). Satır adı `PermissionDefinition.ResourceName`'den gelir; verilmezse anahtardaki kaynak adı kullanılır. Düzenleme seçilince görüntüleme de seçilir. Yalnızca tenant için açık modüllerin izinleri görünür; kapalı modülün izni rolde korunur ve modül açılınca yeniden geçerli olur.
- **Yetki yükseltmeye karşı kural:** yönetici olmayan kişi bir role yalnızca kendisinde olan izni ekleyebilir veya rolden çıkarabilir (403). Böylece `core.roles.manage` izni olan biri kendine başka izin veremez. Yönetici her izni verir.
- **Silme:** `DELETE /api/roles/{id}`. Üyesi olan rol için `?moveTo={rolId}` gerekir (yoksa 409): üyeler o role taşınır, taşıma ve silme tek işlemdedir. Üye taşımak rol atamasıdır, bu yüzden `core.users.manage` de gerekir; hedef Yönetici rolüyse işlemi yapan yönetici olmalıdır. Sistem rolü silinemez. Silme ve taşıma denetim kaydına yazılır.
- **Kopyalama:** "Kopyala", yeni rol formunu aynı izinlerle ve "(kopya)" adıyla açar.
- `GET /api/roles` her rolün üye sayısını (`memberCount`) da döner. Rol değişikliği, rolün üyelerinin bir sonraki isteğinde geçerli olur.
- **Hazır roller (Y3b, [ADR-0005](docs/adr/0005-rol-sablonlari.md)):** modüller önerdikleri rolleri `IModule.RoleTemplates` ile bildirir (CRM "Satış temsilcisi", Lojistik "Operasyon"); çekirdek açık modüllerin tüm görüntüleme izinleriyle "Salt okur" şablonunu ekler. `GET /api/roles/templates` yalnızca açık modüllerin şablonlarını döner. Yeni rol formunda "Şablondan başla"; yalnızca Yönetici rolü varken rol listesi şablonları kart olarak önerir.
- **Kim neye erişebilir:** rol detayında "Bu rolde kimler var" (`GET /api/roles/{id}/members`, `core.roles.manage` veya `core.users.manage`); kullanıcı detayında "Erişim": kişinin geçerli izinleri ve her izni veren roller (`GET /api/users/{id}/access`, `core.users.manage`). Hesap sunucunun her istekte uyguladığıyla aynıdır (`MembershipPermissions`).

### Platform yönetimi (Y4)

Platformu işleten ekip için ayrı bir alan: menüde **Platform** (`/platform`), yalnızca platform yöneticisine görünür. Uç noktalar `/api/platform` altındadır.

- **Platform yöneticisi** kullanıcı düzeyinde bir bayraktır (`IsPlatformAdministrator`); firmaya bağlı değildir. Arayüzden atanamaz, komut satırıyla atanır:
  `dotnet run --project src/Modulix.Api -- platform-admin kisi@ornek.com` (kaldırmak için sonuna `--remove`). Hesap yoksa oluşturulur ve şifre belirleme bağlantısı konsola yazılır. Bayrak her istekte veritabanından okunur; kaldırılınca bir sonraki istekte 403.
- **Tenant verisi dışa aktarma ve silme** yalnızca komut satırındandır (ADR-0020 Dilim 3): `dotnet run --project src/Modulix.Api -- tenant-export acme [--dir <dizin>]` tenant'ın `TenantId` taşıyan bütün satırlarını tablo başına JSON dosyasına yazar (`manifest.json` ile); `-- tenant-delete acme --confirm acme` aynı satırları ve tenant kaydını tek işlemde siler (geri alınamaz; kullanıcı hesapları kalır). Runbook: `docs/tenant-isletim.md`.
- **Firma verisini görmez:** RLS atlanmaz. Platform yöneticisi yalnızca platform tablolarını (firmalar, üyelikler, modül hakları) ve sayıları görür; firmaya yazılan her şey (roller, denetim kaydı) o firmanın bağlamında yazılır.
- **Firmalar** (`/platform/firmalar`): ad, kısa ad, durum, etkin üye sayısı, açık modüller; arama ve durum filtresi. Yönetici sayısı listede okunmaz (roller RLS altındadır, firma başına bir kapsam ister; liste `administratorCount: null` döner); yalnızca firma detayında gelir.
- **Firma açma** tek işlemdir: firma, Yönetici sistem rolü, seçilen modüller, seçilen hazır roller ve ilk yöneticinin daveti (Y2 akışı) birlikte oluşur. Biri başarısız olursa (ör. kısa ad kullanılıyor, 409) hiçbiri oluşmaz ve e-posta gitmez.
- **Firma detayı:** yöneticiler ve bekleyen davetler, "Yönetici davet et" (yöneticisi kalmayan firmanın kurtarma yolu), ad değiştirme, kapatma ve yeniden açma. Kapatmada veri silinmez; üyeler bir sonraki isteklerinde 403 alır, firma seçim listesinden çıkar, davet bağlantıları çalışmaz.
- Açma, ad değiştirme, kapatma ve yeniden açma firmanın denetim kaydına `core.tenant` olarak, işlemi yapan platform yöneticisi adına yazılır; yönetici daveti `core.membership` kaydıdır.
- **Modül hakları (Y4b)** (`/platform/moduller`): firma × modül tablosu, her hücrede aç/kapa anahtarı; firma detayında da aynı anahtarlar. `PUT /api/platform/tenants/{id}/modules/{modül}` gövde `{ "enabled": false }`. Kapatmak veri silmez: modülün menüsü ve uç noktaları o firmada kapanır, rollerdeki izinler korunur ve modül yeniden açılınca geçerli olur. Değişiklik firmanın bir sonraki isteğinde geçerlidir ve firmanın denetim kaydına `core.tenant` olarak (`modules` önce/sonra) yazılır. Çekirdek modül kapatılamaz (400).
- **Modül kataloğu (Y4b)** (`/platform/katalog`, `GET /api/platform/catalog`): kayıtlı modüller, izinleri (kaynak ve işlem), hazır rolleri ve kaç açık firmada açık oldukları. Salt okunur; modül eklemek kodla olur.
- **Olaylar** (`/platform/olaylar`): olay teslimlerinin durumu, yeniden dene ve atla; ayrıntılar aşağıdaki [Olaylar](#olaylar-ç1) bölümünde.
- **Firma durumları ve lisans temeli ([ADR-0028](docs/adr/0028-platform-lisans-ve-tenant-yonetimi.md), Dilim 1):** firma durumu `Açık`, `Deneme`, `Askıda`, `Kapalı`. Deneme (`Trial`) erişimde açık gibidir (`POST /api/platform/tenants/{id}/activate` Deneme → Açık; firma açarken `trial: true`); askı (`POST .../suspend`, gövde `{ "reason": "…" }`, **gerekçe zorunlu**) kapatma gibi erişimi durdurur ama geçicidir ve veri silinmez; `reopen` hem kapalı hem askıdaki firmayı açar (önceki deneme durumu tutulmaz). Erişimin açık olduğu durumlar tek yerde tanımlıdır (`TenantStatusRules.Operational`); kodda `Status == TenantStatus.Active` karşılaştırması yazılmaz. `close` gövdesinde `reason` **zorunludur**; `reopen` ve `activate` için isteğe bağlıdır.
- **Hak koşulları:** `PUT /api/platform/tenants/{id}/modules/{modül}` gövdesi `{ "enabled": true, "source": "Trial", "validUntil": "2026-12-31T00:00:00Z", "note": "…" }` alanlarını da alır (`source`: `Manual`, `Plan`, `Trial`, `Exception`; istisna için `note` zorunlu; `validUntil` gelecekte olmalı). Boşsa mevcut koşullar korunur; mevcut haklar `Manual`, süresiz olarak taşındı. Gövdedeki `reason` platform denetim kaydına yazılır ve **modülü kapatırken ile süre uzatırken** (mevcut bitişi ileri almak ya da kaldırmak) zorunludur; bitişi kısaltmak ve süresiz hakka ilk kez tarih vermek gerekçe istemez. Koşullar firma detayında (`entitlements`) ve firma sayfasındaki "Hak koşulları"nda görünür ve oradan düzenlenir. **Bitiş tarihi uygulanır** (aşağıdaki "Lisans süresi" maddesi).
- **Platform denetim kaydı:** firma açma, ad değiştirme, kapatma, yeniden açma, askıya alma, etkinleştirme, modül değişikliği (koşullarıyla), yönetici daveti ve profil uygulama `platform.PlatformAuditLog` tablosuna da yazılır (işlemi yapan, gerekçe, önce/sonra; firmanın kendi `core.tenant` kaydına ek olarak). Ekleme-yalnızdır (uygulama rolü `UPDATE/DELETE` yapamaz), firmalar arasıdır ve firma silinse de saklanır; `GET /api/platform/audit?tenantId=&action=&page=` okur; ekranı `/platform/denetim`, firma bazlı görünümü firma sayfasındaki "Lisans ve işlem geçmişi"dir. İki adımlı doğrulama sıfırlama (`user.two-factor-reset`, firmasız) bu kayda da yazılır. `tenant-delete` komutu henüz yazmaz.
- **Genel bakış ve süre takvimi (ADR-0028 Dilim 2):** `/platform` sayfasında durumlara göre firma sayıları, başarısız olay teslimi ve süresi yaklaşan haklar görünür (`GET /api/platform/overview`; 30/60/90 sayıları birikimlidir, `expired` bitişi geçmiş tüm haklar, `readOnly` salt okunura geçmiş olanlardır). `GET /api/platform/expirations?days=30|60|90` (varsayılan 90, en çok 365) bitiş tarihi olan açık hakları listeler; yalnızca erişime açık firmalar (Açık, Deneme) ve süresiz olmayan haklar; bitişi geçmiş olanlar en üstte. Her satırda evre (`phase`) ve salt okunura geçiş anı (`graceEndsAt`) vardır. Ekranı `/platform/sure-takvimi`.
- **Lisans süresi (ADR-0028 Dilim 3):** modül hakkının bitiş tarihi (`validUntil`) geçince modül **ek sürede** çalışmaya devam eder (okuma ve yazma açık; firma yöneticisine uyarı çıkar); ek süre de bitince **salt okunur** olur. Evre saklanmaz, bitiş tarihinden her istekte hesaplanır, bu yüzden bir işçiye bağlı değildir ve tarih değişince hemen geçerli olur. Ek süre `License:GraceDays` ile ayarlanır (varsayılan 14 gün, 0-365). Salt okunur modülde: okuma (`GET`, `HEAD`, `OPTIONS`) ve yol adı `/preview` ile biten önizlemeler çalışır, diğer her istek 403 döner (`RequireModule` süzgeci); modülün arka plan işçileri (sözleşme, teklif süresi, kampanya gönderimi, sipariş, destek SLA) o firma için atlanır; oturumsuz uçlar (web formu, teklif bağlantısı kararı, anket yanıtı, imza webhook'u) yazmayı reddeder, salt görüntüleme (teklif ve anket görünümü) sürer. Kapalı modül ise okumaya da kapalıdır. Veri silinmez; süre uzatılınca (gerekçeyle) yazma hemen geri gelir. `GET /api/tenant/access` yanıtındaki `licenses`, bitişine 30 günden az kalan, ek sürede ve salt okunur modülleri listeler; arayüz bunu yalnızca firma yöneticisine banner olarak gösterir. Firma düzeyinde durumlar (`GracePeriod`/`ReadOnly` firma durumu) yoktur; süre modül hakkı düzeyindedir. İletişim tercihi ve abonelikten çıkma bağlantıları lisanstan etkilenmez. E-posta uyarısı henüz yoktur.

### Denetim kaydı (Y5)

**Yönetim → Denetim kaydı** (`/yonetim/denetim`), `core.audit.read` izni ister (Yönetici rolünde vardır). Uç noktalar `/api/audit` altındadır ve yalnızca okur; denetim kaydını değiştiren veya silen bir yol yoktur, veritabanında da uygulama rolüne `UPDATE` ve `DELETE` yasaktır.

- **Liste:** en yeni üstte; tarih, kullanıcı, kayıt türü, kayıt, işlem (Oluşturdu, Değiştirdi, Sildi, Dışa aktardı) ve kaynak (Arayüz, Arka plan işi, İçe aktarma, AI). Satıra tıklayınca değişen alanlar eski ve yeni değerleriyle açılır; değerler okunur biçimdedir (seçenek etiketleri, kullanıcı adları, bağlı kaydın adı).
- **Filtreler:** kullanıcı, kayıt türü, işlem, kaynak ve tarih aralığı (`GET /api/audit?userId=&entityKey=&action=&source=&from=2026-01-01&to=2026-01-31&page=1`). Tarihler Türkiye saatiyle gün olarak yorumlanır, bitiş günü dahildir.
- **Gizli değerler:** okur, kayıt türünün görüntüleme iznine sahip değilse (ör. CRM izni olmayan biri firma kaydı) satırı ve değişen alanların adlarını görür, değerler "gizli" yazılır. Yönetici her şeyi görür.
- **Kullanıcı adı:** firmaya üye olmayan bir platform yöneticisinin işlemleri "Modülix platform yöneticisi" olarak görünür; sistem işlemleri "Sistem". Bir olay abonesinin yaptığı değişiklikte kişi "Sistem", kaynak "Arka plan işi · abonelik anahtarı"dır (ör. `Arka plan işi · crm.party-renamed`).
- **CSV** (`GET /api/audit/export`, aynı filtreler): noktalı virgülle ayrılmış, UTF-8 BOM'lu (Türkçe Excel doğrudan açar), her değişen alan bir satır. En fazla 50.000 kayıt; fazlası 400 döner ve tarih aralığı daraltılır. `=`, `+`, `-` veya `@` ile başlayan hücreler kesme işaretiyle başlatılır. Dışa aktarmanın kendisi de denetim kaydına (`core.audit`, filtreler ve satır sayısıyla) yazılır.
- **Kayıt geçmişi (Y5b):** CRM firma detayında "Değişiklik geçmişi" bölümü; kim, ne zaman, hangi alan eski → yeni. `GET /api/records/{tür}/{id}/history?page=1` (sayfa başına 20). Kaydı görebilen herkes görür, `core.audit.read` gerekmez; kaydı göremeyen 403 veya 404 alır.
- **Oturum olayları (Y5b):** kayıt türü "Oturum" (`core.account`): giriş, hatalı şifre, hesap kilitlenmesi, kilitliyken deneme, şifre sıfırlama ve davet kabulü; IP adresi ve tarayıcı bilgisiyle (kişisel veri, aydınlatma metnine eklenmeli). Başarılı giriş yalnızca seçilen firmaya yazılır (iki firması olan kişi için firma seçildiğinde). Hatalı şifre, kilitlenme ve şifre sıfırlama kişinin etkin üye olduğu tüm firmalara yazılır; davet kabulü daveti kabul edilen firmalara. Kayıtlı olmayan e-postayla deneme hiçbir firmaya yazılmaz, yalnızca uygulama günlüğüne (e-posta olmadan) düşer.
- Modüller kayıt türlerini `IModule.AuditedEntities` ile tanımlar (alan etiketleri, seçenekler, kullanıcı ve bağlantı alanları, görüntüleme izni).

### Firma ayarları (Y6)

**Yönetim → Firma ayarları** (`/yonetim/ayarlar`): firma profili (görünen ad, ticari unvan, vergi dairesi ve no, adres, telefon, e-posta) ve bölgesel ayarlar (saat dilimi, para birimi, tarih ve sayı biçimi). Her bölüm ayrı kaydedilir.

- Ayarlar kodda tiplidir: modüller `IModule.Settings` ile tanımlar (anahtar `modül.grup.ad`, tip, varsayılan, uzunluk, seçenekler, biçim). Tanımsız anahtar yazılamaz, değer tanıma uymalıdır; modülü kapalı ayar görünmez ve yazılamaz. Kaydedilmemiş ayarın değeri varsayılandır (yeni firma hiçbir şey kaydetmeden çalışır).
- `GET /api/settings`: her üye okur. `PUT /api/settings` (`core.settings.manage`): gövde `{ "values": { "core.regional.currency": { "value": "EUR", "version": 1 } } }`. Hepsi birlikte kaydedilir ya da hiçbiri: tanımsız anahtar 400, geçersiz değer 422 (alan adı ayar anahtarıdır), okunduktan sonra değişmiş sürüm 409.
- Her değişen ayar denetim kaydına "Firma ayarı" olarak, ayarın adıyla ve eski → yeni değerle yazılır; değişmeyen değer yazılmaz. Genel kayıt uç noktası (`/api/records/core.tenant-setting`) da aynı kurallara uyar.
- **Ayarlar ekranlarda kullanılır.** Tarih ve saatler firmanın saat diliminde, seçili tarih/sayı biçiminde gösterilir (Türkçe `24.10.2026 14:30` · `1.234,50`, İngilizce GB `24/10/2026` · `1,234.50`, İngilizce ABD `10/24/2026 2:30 PM`). Denetim kaydının tarih filtresi gün sınırlarını, CSV de saatleri firmanın saat dilimine göre alır. Yeni fırsatın para birimi varsayılan para birimidir (mevcut kayıtlar değişmez). Görünen ad üst çubukta ve firma seçiminde kayıtlı adın yerine gösterilir.
- **Arayüz tasarım sistemi:** renkler, tipografi, açık/koyu tema ve ortak bileşenler `docs/design-system/` altında anlatılır. Tema ve sol menünün daraltılmış durumu kullanıcının tarayıcısında saklanır (sunucuya yazılmaz).
- **Logo:** `PUT /api/settings/logo` (`core.settings.manage`) gövde olarak dosyanın kendisini alır; yalnızca PNG veya JPEG, en fazla 256 KB. Tür uzantıdan değil içerikten anlaşılır; SVG kabul edilmez (betik taşıyabilir). `GET /api/settings/logo` her üyeye dosyayı döner (`nosniff`, önbellek sürüme bağlı), `DELETE` kaldırır. Logo veritabanında `core.TenantLogos` tablosunda (RLS) durur, değişikliği denetim kaydına "Firma · Logo" olarak yazılır ve üst çubukta görünür.

### Hesap güvenliği (Y7a)

**Hesabım** (`/hesabim`, üst çubukta kişinin adına tıklanınca açılan profil menüsünde; aynı menüde birden fazla kuruluş varsa *Kuruluş değiştir* ve *Çıkış* bulunur): ad, e-posta, şifre ve açık oturumlar. Bilgiler kişiye aittir; birden fazla firmada çalışan kişinin değişikliği hepsinde geçerlidir ve her firmanın denetim kaydına "Hesap" olarak yazılır.

- `GET /api/account`, `PUT /api/account/profile` (ad), `POST /api/account/password` (mevcut ve yeni şifre; bu oturum açık kalır, diğerleri kapanır; hatalı mevcut şifre girişteki gibi sayılır ve hesabı kilitler).
- `POST /api/account/email` (yeni adres ve mevcut şifre): yeni adrese 24 saat geçerli onay bağlantısı (`/eposta-onayla`) gider. `POST /api/auth/confirm-email-change` e-postayı ve giriş adını değiştirir, tüm oturumları kapatır, eski adrese bilgi verir. Adres başka hesapta kullanılıyorsa bu yalnızca bağlantıda söylenir.
- **Şifremi unuttum** (`/sifremi-unuttum`, `POST /api/auth/forgot-password`): hesap olsun olmasın 202 döner. Aynı hesaba 15 dakikada en fazla bir bağlantı gider; bir IP adresinden saatte 10 istek kabul edilir, fazlası 429 (`Account:ForgotPasswordPerIpPerHour`, `Account:ForgotPasswordInterval`). Daveti bekleyen kişiye gitmez.
- **Oturumlar** sunucuda da tutulur (`platform.UserSessions`): çerez oturum kimliğini taşır, her istekte oturumun kapatılmadığı denetlenir (son etkinlik en fazla 5 dakikada bir yazılır). `GET /api/account/sessions`, `DELETE /api/account/sessions/{id}`, `POST /api/account/sessions/close-others`. Çıkış oturumu kapatır; 30 günden eski kayıtlar girişte silinir.
- Yönetici (`core.users.manage`) `POST /api/users/{üyelik}/close-sessions` ile kişinin tüm oturumlarını kapatır (diğer firmalardaki de kapanır; Yönetici rolündekini yalnızca yönetici kapatabilir). Devre dışı bırakmak oturumları kapatmaz: o firmaya erişim zaten hemen kesilir.

### İki adımlı doğrulama (Y7b)

Doğrulama uygulamasıyla (TOTP: Google/Microsoft Authenticator vb.) çalışır; hesaba aittir, kişinin bütün firmalarında geçerlidir. "Bu cihazı hatırla" yoktur.

- **Kurulum** Hesabım → İki adımlı doğrulama: mevcut şifre → QR kod ve anahtar (`POST /api/account/two-factor/setup`) → uygulamadaki kod (`/enable`) → 10 kurtarma kodu bir kez gösterilir (indirilebilir). `GET /api/account/two-factor` durumu ve kalan kod sayısını verir; `/recovery-codes` (şifre) kodları yeniler, `/disable` (şifre ve kod) kapatır.
- **Giriş**: şifre doğruysa ve doğrulama açıksa `POST /api/auth/login` 202 döner; ikinci adım `POST /api/auth/login/two-factor` (6 haneli kod ya da kurtarma kodu). Hatalı kodlar hatalı şifre gibi sayılır ve hesabı kilitler (423). Kurtarma koduyla girişte kişiye e-posta gider ve Hesabım'a yönlendirilir.
- **Firma zorunluluğu**: Ayarlar → Güvenlik → "İki adımlı doğrulama zorunlu" (`core.security.require-two-factor`). Açıkken doğrulaması kapalı üye firmanın verisine erişemez (403 `two-factor-required`), ekranlar Hesabım'a yönlendirir; kurunca devam eder. Ayarı açan kişinin kendi doğrulaması açık olmalıdır; zorunlu firmada üye doğrulamasını kapatamaz. Kullanıcı listesinde "İki adımlı" sütunu ve süzgeci vardır.
- **Kayıp telefon ve kodlar**: yalnızca platform yöneticisi sıfırlar (Platform sayfası, `POST /api/platform/users/reset-two-factor`): doğrulama kapanır, kişinin tüm oturumları kapatılır.
- Denetim kaydına "Hesap" olarak açma, kapatma, kod yenileme, kurtarma koduyla giriş ve sıfırlama yazılır (sıfırlamada işlemi yapan platform yöneticisidir).

### Ekipler ve kayıt kapsamı (Y8a)

Roller "hangi tür kaydı", kayıt kapsamı "hangi kayıtları" belirler. Kapsam rol başınadır: **Tüm kayıtlar**, **Departmanın ve alt departmanların kayıtları**, **Departmanın kayıtları** ([ADR-0026](docs/adr/0026-departman-hiyerarsisi-ve-departman-bazli-gorunurluk.md)), **Ekibinin kayıtları** (kendisinin ve ekip arkadaşlarının sorumlu olduğu kayıtlar) ya da **Yalnızca kendi kayıtları**. Kişinin birden fazla rolü varsa her rolün gördüğü kayıtlar **birleşir** (en geniş kapsam değil: ekip ile departman birbirini kapsamaz); Yönetici her zaman tüm kayıtları görür. Mevcut roller "Tüm kayıtlar" ile başlar; "Satış temsilcisi" şablonu "Yalnızca kendi kayıtları" önerir.

- Kapsam yalnızca sorumlu alanı olan kayıt türlerine uygulanır (`IRecordStore.OwnerField`; CRM'de firma, fırsat, aktivite). Boru hattı (`IDataScopeService`) listede kapsamı sorguya koyar (`RecordQuery.Owners`), böylece sayfalama ve toplam doğru kalır; kapsam dışındaki tek kayıt 404 döner. Sorumlu kapsam dışına atanamaz (422, `ownerId`). Sorumlusu boş kayıt yalnızca "Tüm kayıtlar"da görünür.
- **Ekipler** (Yönetim → Ekipler, `core.users.manage`): `/api/teams` (liste, ekle, düzenle, sil), `PUT /api/teams/{id}/members`, kullanıcı ayrıntısında `GET/PUT /api/users/{üyelik}/teams`. Bir kişi birden fazla ekipte olabilir; ekip silinince yalnızca ekip ilişkisi kalkar. Değişiklikler denetim kaydına "Ekip" olarak yazılır.
- `GET /api/tenant/members?assignable=true&entityKey=<tür>`: kişinin sorumlu atayabileceği üyeler; kapsam kayıt türüne göre çözüldüğü için tür anahtarı (ör. `crm.company`) zorunludur, verilmezse 400 döner (ADR-0029). `GET /api/tenant/access` ve kullanıcının "Erişim" görünümü kapsamı (ve ekipleri) gösterir.
- Yönetici olmayan rol yöneticisi kendi kapsamından geniş kapsam veremez (403).

### Departman ağacı ([ADR-0026](docs/adr/0026-departman-hiyerarsisi-ve-departman-bazli-gorunurluk.md), dilim 1)

Merkez kök departmandır; bayiler ve diğer yapılar altında yer alır. Her tenant'ın tek kök departmanı vardır ve her üyelik tam bir departmandadır. **Departman ekip değildir:** ekip çok üyeli bir çalışma grubudur (bir kişi birden çok ekipte olabilir), departman ağaçtaki tek konumdur.

- **Departmanlar** (Yönetim → Departmanlar, `core.users.manage`): `GET/POST /api/business-units`, `GET/PUT /api/business-units/{id}`, `PUT /api/business-units/{id}/active` (kapat/aç). Kullanıcı kartındaki departman: `GET/PUT /api/users/{üyelik}/business-unit`. Kullanıcı listesi `?businessUnitId=` ile departmana göre süzülür; davet `businessUnitId` alabilir (verilmezse kök departman).
- Kurallar: kök kapatılamaz; ağaç kök dahil en fazla dört seviyedir; aynı üst departmanda aynı ad kullanılamaz (409); üyesi ya da etkin alt departmanı olan departman kapatılamaz (409); kapalı departmana kullanıcı atanamaz (400). Departman silinmez. Tür (Merkez/Bayi/Diğer) yalnızca açıklayıcıdır.
- Değişiklikler denetim kaydına "Departman" olarak, kullanıcının departman değişimi "Kullanıcı" kaydı olarak yazılır. Tablolar (`core.BusinessUnits`, `core.BusinessUnitMembers`) tenant verisidir: RLS ve EF filtresiyle korunur, tenant başına tek kök veritabanı kısıtıdır.
- Migration `BusinessUnits` mevcut tenant'lara kök departmanı (tenant adıyla) ve tüm üyeliklere kök departmanı geri doldurur; yeniden çalıştırılabilir.
- **Rolün departmana atanması (dilim 2):** `GET/PUT /api/business-units/{id}/roles` (Departman ayrıntısında "Departman rolleri"). Departmandaki her kullanıcı rolün izinlerini ve kayıt kapsamını alır; kullanıcıya doğrudan atanan rollerle **toplanır**, biri diğerini ezmez. Rolün **atanabilir düzeyi** (`Role.AssignLevel`: yalnızca kullanıcıya / yalnızca departmana / ikisine) rol ekranında seçilir; mevcut roller "yalnızca kullanıcıya" olarak başlar, departmana atama açık işaretlemeyle başlar. "Alt departmanlara da uygula" varsayılan **kapalıdır**: merkeze verilen rol kendiliğinden bayilere inmez.
- Kurallar: sistem rolü ("Yönetici") departmana atanamaz (409); atanabilir düzeyi departmanı içermeyen rol atanamaz (409); kapalı departmana rol eklenemez (409); atayan (yönetici değilse) verilen ya da kaldırılan rolün izinlerini ve kayıt kapsamını kendisi de taşımalıdır (403); atanmış rol "yalnızca kullanıcıya" yapılamaz ve silinirken departman atamaları hedef role taşınır (hedef departmana atanabilir olmalı). Değişiklik, etkilenen kullanıcı sayısıyla denetim kaydına "Departman" olarak yazılır.
- **Kayıt kapsamları:** `Departman` departmandaki herkesin (pasif ve devre dışı üyelikler dahil) sorumlu olduğu kayıtları, `Departman ve altı` alt departmanlar dahil olanları açar; kök departmanda "ve altı" tüm firmadır (sahipsiz kayıtlar dahil). Kapsam sahip kümesine çevrilir (`MembershipDataScope`), bu yüzden ortak firma/kişi kısıtı (`ISharedRecordVisibility`) da kendiliğinden aynı kümeyi izler. Sayısal enum değerleri kalıcıdır (`All=1, Team=2, Own=3, Unit=4, UnitAndBelow=5`); genişlik/kapsama kararı `RecordScopeRules`'tadır.
- Kullanıcı kartındaki "Erişim" bölümü rollerin **kaynağını** (doğrudan ya da hangi departmandan) ve kapsamların birleşimini gösterir.
- **Kapsam dışı ortak kayıtları gizleme (dilim 3, K8):** rol ekranında "Kapsam dışı firma ve kişileri gizle" (`Role.HideOutOfScopeShared`, `SaveRoleRequest.HideOutOfScopeShared`). Kapalıyken (varsayılan, mevcut roller) kayıt kapsamınız dışındaki ortak firma/kişiler genel uçlardan (`/api/records/core.party`, `core.person`) yalnızca asgari kimlikle görünür (ADR-0010). Açıkken bu kayıtlar liste, sayım, arama, süzgeç (vergi no), lookup, tekil okuma, değiştirme, silme ve mükerrer önerisinde **hiç görünmez** ("bulunamadı"). Kişinin **tüm** rolleri gizliyorsa gizlenir (roller izinler gibi eklenir; bir rol göstermeye izin veriyorsa gösterilir). Yönetici ve rolü olmayan kişi etkilenmez. Mekanizma: `ISharedRecordVisibility.HiddenAsync` (CRM: kapsam dışı firmanın tarafı / kapsam dışı kişi) ortak kayıt depolarının sorgusuna alt sorgu olarak eklenir; `IRecordAccess.HidesOutOfScopeSharedRecordsAsync` ayarı modüllere verir.
- **Çakışma iletileri (dilim 3, K9):** aynı vergi numarasıyla firma açılırken (`/api/crm/companies` ve `/api/records/core.party`) ileti kaydın adını, kimliğini ya da sahibini taşımaz; kapsam içi ve kapsam dışı kayıt için **aynıdır**. Gizleyen rollerde iletiye "Kaydı göremiyorsanız yetkili (merkez) kullanıcıya başvurun." eklenir. **Sınır:** vergi numarası tenant içinde tekil olduğu için bir numaranın kullanımda olduğu bu iletiden çıkarılabilir; bunu tamamen gizlemek bayi başına ayrı benzersizlik ya da inceleme kuyruğu gerektirir (bu dilimde yok).
- **Departman değişikliği (dilim 4, K7):** kayıt görünürlüğü sahibin güncel departmanına göre hesaplandığı için kullanıcıyı taşımak onun kayıtlarının görünürlüğünü de taşır. Kullanıcı kartında "Departmanı değiştir…" önce etkisini gösterir: `GET /api/users/{üyelik}/business-unit/change-preview?businessUnitId=` (kayıt sayısı türlere göre, kaybedilen/kazanılan departman rolleri, uyarılar; hiçbir şey değiştirmez). `PUT /api/users/{üyelik}/business-unit` gövdesi `reason`, `moveRecordsWithUser`, `transferRecordsToMembershipId` alır.
- Kurallar: kullanıcının kaydı varsa (ya da işlemi yapan kayıt türlerinden bazılarını göremediği için sayım eksik kalıyorsa) **karar** gerekir: ya kayıtlar kullanıcıyla yeni departmana geçer (`moveRecordsWithUser`) ya da kullanıcının **eski departmanında kalan etkin** bir üyeye devredilir (`transferRecordsToMembershipId`, ADR-0004 devri; kendisi, başka departmandaki ya da devre dışı üye reddedilir); ikisi birlikte verilemez; karar yoksa 409. Kayıt varsa ya da kullanıcı etkin değilse (devre dışı/davetli) **gerekçe** zorunludur (en çok 500 karakter). Devir, taşıma ve denetim kaydı tek işlemdedir; denetim kaydı gerekçeyi ve kayıtların akıbetini ("N kayıt kullanıcıyla taşındı" / "kime devredildi") yazar. Aynı departmana taşıma değişiklik sayılmaz.
- **Kapsam sınırı:** yönetici olmayan işlemi yapan kullanıcıyı yalnızca kendi kapsamındaki departmanlar arasında taşıyabilir ("departman ve altı" kendi ağacını, diğerleri yalnızca kendi departmanını kapsar); hem kullanıcının mevcut hem hedef departmanı bu kümede olmalıdır (403). Devre dışı üyeler bir departmanda kaldıkça o departman kapatılamaz; önce gerekçeyle taşınır.
- **Departman görünürlüğü:** departman yönetimi (`core.users.manage`) tenant geneli bir izindir, ama yönetici olmayan işlemi yapan yalnızca **kendi kapsamındaki departmanları** görür ve yönetir (kendi departmanı; "departman ve altı" kapsamı varsa altındakiler; tüm kayıtlar kapsamında kısıt yok). Diğer bayilerin departmanı `GET /api/business-units` listesinde yoktur; ayrıntı, ekleme, düzenleme, kapatma ve departman rolleri uçları "bulunamadı" (404) döner. Kullanıcı listesinde ve kartında başka bayinin departman adı boş görünür, o departmana göre süzme boş döner, kullanıcının departman ucu (`.../business-unit`) 404 döner. Davet yalnızca kendi kapsamındaki departmana yapılabilir (kapsam dışı departman "bulunmayan departman" gibi 400); departman verilmezse kök yerine davet edenin kendi departmanı kullanılır. Platform yöneticisinin tenant açılış daveti etkilenmez.
- **Kullanıcı dizini kapsamı (dilim 6):** `core.users.manage` tenant geneli bir izindir, ama yönetici olmayan işlemi yapan yalnızca **kendi kapsamındaki departmanların kullanıcılarını** listeler, görür ve yönetir (`IMembershipScope`). Başka bayinin kullanıcısı için kullanıcı kartı, erişim, sahip olunan kayıtlar, departman, ekipler, devre dışı bırakma/etkinleştirme, şifre sıfırlama, oturumları kapatma, kilit açma, kayıt devri, rol atama (`/api/memberships/{id}/roles`) ve şirket görevleri (`/api/memberships/{id}/companies`) uçları "bulunamadı" (404) döner; kullanıcı listesi, arama ve rol üyeleri listesi yalnızca kapsamdakileri içerir. Kayıt devrinde devralan da kapsamda olmalıdır (kapsam dışı devralan 400). Ekip üyeliğini değiştirmek kayıt görünürlüğünü etkilediği için, yönetici olmayan işlemi yapan kapsamı dışındaki kullanıcıları ekibe ekleyemez ya da ekipten çıkaramaz (`PUT /api/teams/{id}/members`, 400). Tüm kayıtlar kapsamındaki yönetici ve platform/sistem bağlamı (üyeliği olmayan, ör. tenant açılış daveti) kısıtlanmaz.
- **Henüz yok / sınırlar:** `/api/tenant/members` (atama listeleri için üye adları) bilinçli olarak tenant geneli kalır (ADR, Y8a); dolayısıyla bayi kullanıcıları diğer bayilerin kullanıcı **adlarını** atama listelerinden görebilir, e-posta ve rollerini göremez. Ekip adları ve ekip listesi tenant geneli kalır. Olay işleyicileri ve toplu çıktıların (ör. dışa aktarma işleri) kapsamı ayrıca gözden geçirilmelidir (ADR-0026 K10): kapsamlı CRM kayıtları boru hattından geçtiği için uygulanır, ancak tenant genelinde çalışan arka plan işleri doğrulanmadı. Bir vergi numarası başka bir modüldeki (CRM firması olmayan) taraf ile eşleşirse yeni CRM firması o tarafa bağlanır (ADR-0006, bilinçli ortak ana veri).

### Hassas alanlar (Y8b)

Bazı alanlar kaydı görebilen herkese açık değildir. Modül hassas alanlarını ve onları açan izni `IModule.SensitiveFields` ile tanımlar; CRM'de fırsatın **tutarı** ve **olasılığı** `crm.opportunity-amounts.read` ("Fırsat tutarları" satırı) ister. Para birimi hassas değildir. Bu izin "Satış temsilcisi" ve "Salt okur" şablonlarında vardır; migration bugün fırsatları gören her role izni ekler, kimse görünürlük kaybetmez.

- İzni olmayan kişiye alan hiç gönderilmez (tek kayıt, liste, `/api/records`). Boru hattı (`IFieldAccessService`) alanı çıkarır; Yönetici her şeyi görür.
- Yazma: gizli alana değer vermek 403'tür; boş gönderilen gizli alan yok sayılır ve kayıttaki değer korunur (ekran onu boş gönderir). Gizli alana göre süzmek 422'dir.
- Denetim kaydında ve kayıt geçmişinde alan satırı görünür ama değeri "Gizli" yazar (`AuditFieldChangeDto.Hidden`).
- Ekranlar: izni olmayan için fırsat listesinde Tutar ve Olasılık sütunları, huni kartlarındaki tutar, toplamlar ve düzenleyicideki iki alan gösterilmez.

### Özel alanlar (Y9a)

Firma kendi alanlarını ekleyebilir (ör. fırsatta "Araç tipi"). Tanım ekranı Yönetim → Özel alanlar'dır (`/yonetim/ozel-alanlar`) ve `core.customization.manage` ("Özelleştirme") ister. Modül hangi kayıt türlerinin özelleştirilebileceğini `IModule.CustomizableEntities` ile söyler; CRM'de firma, kişi, fırsat ve aktivite.

- Tipler: kısa metin, uzun metin, sayı, tarih, evet/hayır, seçim listesi, çoklu seçim. Kayıt türü başına en fazla 30 alan. Anahtar etiketten bir kez üretilir ve değişmez; etiket sonradan değiştirilebilir.
- Tanımlar `meta.CustomFields` tablosundadır (RLS'li). Değerler kaydın kendi tablosunda `CustomFields` JSON sütununda durur; kayıt verisinde `custom` nesnesi olarak gelir ve gider.
- Boru hattı değerleri tipine göre doğrular ve normalleştirir; bilinmeyen alan ve yanlış tip 422'dir. Zorunlu alan eklerken doldurulmalıdır; güncellemede yalnızca boş gönderilirse hata verir (huni sürüklemesi engellenmez). Güncellemede `custom` gönderilmezse değerler korunur.
- Alan silinmez, arşivlenir: değerleri kayıtta kalır, geri alındığında yeniden görünür. Seçenekler de pasifleştirilir; pasif seçenek yalnızca zaten seçili olan kayıtta kalabilir.
- Seçim listesi alanına göre süzme: `custom.<anahtar>=<seçenek>` (`/api/records`).
- Denetim kaydı alan tanımlarını "Özel alan" olarak, kayıt değişikliklerini alanın etiketiyle yazar.
- `GET /api/custom-fields` her üyeye açıktır (ekranlar formları buradan kurar). Ekranlarda alanlar formun sonunda "Ek bilgiler" bölümünde çıkar; "Listede göster" seçilenler listede sütun olur; firma ayrıntısı dolu değerleri gösterir.

### Düzenlenebilir listeler (Y9b)

Fırsat aşaması, firma durumu, firma kaynağı ve aktivite tipi artık firmanın düzenleyebildiği listelerdir. Ekran Yönetim → Listeler'dir (`/yonetim/listeler`, `core.customization.manage`). Değerin adı ve sırası değiştirilir, değer pasife alınır, yeni değer eklenir. Satış hunisinin sütunları aşama sırasıyla çizilir.

- Modül listelerini `IModule.ChoiceLists` ile tanımlar. Hazır değerlerin anahtarı eski enum adıdır (ör. `Proposal`), bu yüzden API ve kayıtlar değişmez. Migration sayı kolonlarını bu metin anahtarlara çevirir.
- Kod değere değil kategoriye bakar. Fırsat aşamasında Açık / Kazanıldı / Kaybedildi, firma durumunda Potansiyel / Müşteri / Pasif vardır. `open=true` süzgeci ve devir, kategorisi Kazanıldı ya da Kaybedildi olmayan aşamaları açık sayar. Yeni değer bir kategori seçer. Hazır değerin kategorisi değişmez. Her kategoride en az bir etkin değer kalmalıdır.
- Değer silinmez: listeden çıkarılan değer pasif kalır. Pasif değer yeni kayıtta seçilemez ama onu taşıyan kayıt aynen kaydedilebilir. Listede olmayan değer 422 döner.
- Değer verilmezse (ya da `null` veya boş gönderilirse) yeni kayıtta listenin varsayılanı atanır: tanımın varsayılanı etkinse odur, değilse ilk etkin değerdir. Güncellemede verilmeyen değer değişmez. Tipli CRM istekleri de (`status`, `stage`, `type`) bir hazır değeri varsaymaz; böylece ör. "Görev" pasife alınınca tip göndermeyen istek hata almaz.
- Tabloya (`meta.ChoiceLists`, RLS'li) yalnızca firmanın düzenlediği liste yazılır. Düzenlenmemiş listede koddaki varsayılan geçerlidir. Değişiklikler denetim kaydına "Liste" olarak yazılır. Kayıt geçmişi değerleri firmanın adlarıyla gösterir.
- `GET /api/choice-lists` her üyeye açıktır. Düzenleme `GET /api/customization/lists` ve `PUT /api/customization/lists/{anahtar}` üzerinden yapılır; gövdede liste tamamıyla, sırasıyla verilir.

### Lookup alanları ([ADR-0016](docs/adr/0016-lookup-altyapisi.md))

Formlardaki kayıt/üye seçimleri (firma, kişi, fırsat, sorumlu...) ortak `LookupPicker` bileşeniyle yapılır; veri istemciye toplu indirilmez, sunucuda aranır ve sayfalanır. Yönetim → Alan ve Lookup Ayarları (`/yonetim/alan-ve-lookup-ayarlari`, `core.customization.manage`) her alan için **Aranabilir** anahtarını açıp kapatır.

- Tanımlar kodda sabittir (`IModule.Lookups`, CRM için `CrmLookupDefinitions`); firma yalnızca "aranabilir" ayarını `meta.LookupSettings`'e yazar. Ayar yoksa varsayılan (açık) geçerlidir. "Aranabilir", liste filtresi ve global aramadan bağımsızdır ve bir erişim yetkisi değildir.
- `GET /api/lookups` (her üye), `GET /api/lookups/{anahtar}/search?q=&page=&pageSize=&parentId=`, `POST /api/lookups/{anahtar}/resolve`, `PUT /api/customization/lookups/{anahtar}` (`{ searchable: true|false|null, version }`; eski sürüm 409, `null` varsayılana döner).
- Arama kapalıyken `q` dolu istek 422 döner; sayfalı gezinme ve kimlikten çözümleme çalışır. `q` en az 2, en çok 100 karakterdir; sayfa en çok 50 sonuçtur.
- Sonuçlar kayıt boru hattından geçer: arama, toplam ve çözümleme aynı izin/kapsam kurallarını kullanır; erişilemeyen kayıt `unavailable` döner, ad sızmaz.
- Kayıt sırasında firma/kişi görünürlüğü ve kişi↔firma ilişkisi (fırsat, Lead, aktivite, lokasyon) sunucuda yeniden doğrulanır; değişmeyen eski bağ yeniden denetlenmez.
- Değişiklikler denetim kaydına `Lookup ayarı` olarak yazılır. Kayıt aramasında `ı/I` ve `i/İ` çiftleri veritabanı kolasyonu yüzünden eşleşmez (ayrıntı ADR-0016).

### Form düzeni ([ADR-0021](docs/adr/0021-form-duzeni-ozellestirme.md))

Firma yöneticisi her kayıt formunun düzenini kendine göre kurar: alanları taşır, yeni sekme ve bölüm açar, genişlik (çeyrek / üçte bir / yarım / üçte iki / tam satır), zorunluluk ve görünürlük belirler. Ekran Yönetim → Form tasarımı (`/yonetim/form-tasarimi`, `core.customization.manage`). Alanın kendisi (girdi tipi, doğrulama) koddadır; buradan yalnızca yerleşim ve zorunluluk değişir.

- Tanım kodda sabittir (`IModule.Forms`, CRM için `CrmForms`: Firma, Kişi, Fırsat, Lead, Aktivite); firmanın düzeni `meta.FormLayouts` satırında JSON olarak durur. Satır yoksa tanım geçerlidir; "Varsayılana dön" satırı silmez, sürümü ilerletir. Varsayılan tanımlar çok sekmelidir (ör. Firma: Genel bilgiler / İletişim / Notlar ve ek bilgiler; Sözleşme: Genel ve ticari bilgiler / Süre ve yenileme / Açıklama ve ek bilgiler) ve form her zaman sekme çubuğuyla çizilir; kayıt denemesinde sunucu hatası olan alanın sekmesi "!" rozeti taşır ve hatalı ilk sekme açılır. Daha önce kendi düzenini kaydetmiş firmaların düzeni değişmez.
- Sabit alanlar (kaydın adı, aşama gibi) gizlenemez ve zorunluluğu değişmez; kodun zorunlu tuttuğu alan isteğe bağlı yapılamaz. Özel alanlar (Y9a) düzende `custom.{anahtar}` adıyla yer alır ve taşınabilir; yeni alan eklemek Özel alanlar ekranının işidir.
- Firmanın zorunlu kıldığı alan **sunucuda** denetlenir (kayıt boru hattı): oluştururken dolu olmalı, güncellemede boşaltılamaz; eski kayıtlar zorunluluk konmadan önce açılmış olabilir, dokunulmadıkça reddedilmez.
- `GET /api/form-layouts` (her üye; formlar buradan çizilir), `GET/PUT/DELETE /api/customization/form-layouts/{kayıtTürü}` (PUT gövdesinde düzenin tamamı + `version`; eski sürüm 409, geçersiz düzen 422 alan hatalarıyla, tanımsız form 404; DELETE `?version=` varsayılana döner). Değişiklikler denetim kaydına `Form düzeni` olarak yazılır.

### Sektör profilleri (Y9c)

Profil, bir sektör için hazır başlangıç paketidir: modüller, özel alanlar ve liste değerleri. Dört profil kodda tanımlıdır (`Modulix.Api/Customization/SectorProfiles.cs`): Genel, Lojistik firması, Klinik, Üretici. Tanımlar açılışta modül kataloğuna göre doğrulanır; bilinmeyen modül, kayıt türü, liste veya kategori varsa uygulama açılmaz.

- Profil yalnızca ekler. Aynı adlı alan (arşivdekiler dahil) ve aynı adlı liste değeri (büyük/küçük harf fark etmez) atlanır; firmanın mevcut alanları ve değerleri değişmez. Yeni liste değeri kendi kategorisinin son değerinin arkasına eklenir. Alanlar ve değerler Y9a/Y9b servisleriyle eklenir, yani aynı kurallar ve denetim kayıtları geçerlidir. Hepsi tek işlemdir.
- Profil yeniden uygulanabilir; o gün eksik olanlar eklenir. Profil tanımı sonradan değişirse firmalara kendiliğinden yansımaz.
- Firmanın profili `platform.Tenants.ProfileKey` (ve uygulama zamanı) olarak tutulur; uygulama firmanın denetim kaydına `core.tenant` "Sektör profili" olarak yazılır.
- Platform yöneticisi firmayı açarken profil seçer (`CreateTenantRequest.Profile`); ekran profilin modüllerini önceden işaretler, değiştirilebilir. Firma detayından mevcut firmaya önizlemeyle uygular; bu yolda profilin kapalı modülleri de açılır (`GET /api/platform/profiles`, `GET`/`POST /api/platform/tenants/{id}/profile/{anahtar}`).
- Firma yöneticisi Yönetim → Sektör profili'nden uygular (`/yonetim/sektor-profili`, `core.customization.manage`; `GET /api/customization/profiles`, `GET /{anahtar}/preview`, `POST /{anahtar}/apply`). Modül açamaz: kapalı modülün alanları ve değerleri eklenmez, önizlemede ayrıca belirtilir.
- Menü sırası profilden gelmez: şimdilik yalnızca CRM'in ekranları var.

#### Sektör/faaliyet kataloğu ve tenant seçimi (ADR-0029 taslak, Dilim A)

Tek profil anahtarının yanında, sektör → faaliyet grubu → alt faaliyet ağacı ve yetenek kataloğu vardır ([ADR-0029](docs/adr/0029-sektor-profili-genisletme-ve-lojistik-kurulum.md), taslak). Henüz ekranı ve hazır içeriği yoktur: yalnızca API ve servisler; katalog boş başlar ve hiçbir modülü kendiliğinden açmaz.

- Katalog `platform` şemasında global ve RLS dışıdır; yalnızca platform yöneticisi yönetir (`GET /api/platform/sectors`, `POST .../nodes`, `PUT .../nodes/{id}`, `PUT .../nodes/{id}/active`, `PUT .../nodes/{id}/capabilities`, `POST .../capabilities`, `PUT .../capabilities/{kod}/dependencies`). Düğüm silinmez, pasife alınır; aktif alt düğümü olan düğüm pasife alınamaz. Düğüm taşıma yoktur. Eşzamanlı düzenleme sürüm numarasıyla 409 döner. Her yazma `PlatformAuditLog`'a yazılır.
- Firma yöneticisi (`core.customization.manage`) kataloğu okur ve kendi faaliyet seçimini yönetir (`GET /api/sectors/catalog`, `GET`/`PUT /api/sectors/selection`, `POST /api/sectors/selection/preview`). Seçim `core.ActivitySelections` (RLS altında); üst başlığı seçmek alt faaliyeti seçmiş saymaz, üst bağlam türetilir. Boş seçim geçerlidir. Pasif ya da bilinmeyen faaliyet reddedilir. Değişiklik firmanın denetim kaydına `core.activity-selection` olarak yazılır.
- Eksik yetenek uyarıdır, engel değildir. Şimdilik "sağlanan yetenek" katalogdaki etkin yeteneklerdir; modüllerin yetenek beyanı sonraki dilimdedir.
- Ekranlar (Dilim B): platform yöneticisi için Platform → Sektörler ve faaliyetler (`/platform/sektorler`: ağaç, düğüm ekle/düzenle/pasife al, hazırlık durumu, yetenek ve bağımlılıklar); firma yöneticisi için Yönetim → Faaliyetlerim (`/yonetim/faaliyetler`, `core.customization.manage`: çoklu seçim, anlık önizleme, kaydet).

### Ortak firma ve kişi kaydı (Ç3a)

Firma (taraf) ve kişi çekirdekte tek kayıttır ([ADR-0006](docs/adr/0006-ortak-firma-ve-kisi.md)). Modüller kendi bilgilerini bu kayda bağlı uzantılarda tutar: CRM firması ve CRM kişisi bu kayıtların CRM uzantısıdır. Lojistik ve sonraki modüller yeni firma tablosu açmaz, aynı kaydı kullanır.

- Kayıtlar `core.Parties` ve `core.People` tablolarında durur; ikisi de RLS'lidir. Genel uç: `/api/records/core.party` ve `/api/records/core.person`.
  - Taraf alanları: `kind` (`Organization` / `Individual`), `name`, `taxOffice`, `taxNumber`, `phone`, `email`, `website`, `city`, `address`. Filtre: `taxNumber`.
  - Kişi alanları: `firstName`, `lastName`, `email`, `phone`, `title`, `partyId` (çalıştığı taraf). Filtreler: `partyId`, `email`.
- **CRM API'si değişmedi:** `crm.company` ad, vergi no, telefon, e-posta, web sitesi, şehir ve adresi aynı adlarla alır ve döndürür; bu alanlar tarafa yazılır. Yanıtta `partyId` da gelir. CRM kişisinin ad, soyad, unvan, e-posta ve telefonu ortak kişidedir (`personId`). Durum, kaynak, sektör, etiketler, sorumlu, notlar ve özel alanlar CRM'de kalır.
- **Vergi numarası kesin eşleşmedir:** vergi numarası tenant içinde tekildir. Yeni CRM firması, aynı vergi numaralı bir tarafla açılırsa yeni taraf oluşmaz, firma o tarafa bağlanır. Boş gönderilen taraf alanları taraftaki değeri silmez. Tarafın zaten bir CRM firması varsa 422 döner (`taxNumber`). Başka bir tarafın vergi numarasını vermek de 422'dir.
- **Mevcut kayda bağlama:** genel uçta oluştururken `partyId` (firma) veya `personId` (kişi) verilebilir. Bağlantı sonradan değiştirilemez (422).
- **Çalıştığı firma:** CRM kişisinin firması verildiğinde ya da değiştiğinde, ortak kişinin `partyId`'si o firmanın tarafına eşitlenir.
- **Yetki:** modül, ortak kaydı hangi izinleriyle okuyup yazdığını `IModule.SharedRecordAccess` ile bildirir. CRM'de taraf için `crm.companies.read` / `.write`, kişi için `crm.contacts.read` / `.write` gerekir. Bu izinlerden birine sahip olan, açık modüllerden birinde ortak kaydı okur ya da yazar. Bildirmeyen modülün izinleri ortak kayda erişim vermez. Kayıt kapsamı (Y8a) uzantıya uygulanır. Genel uçlar bu kısıtı dolanamaz ([ADR-0010](docs/adr/0010-musteri-karti-ve-kisi-erisimi.md)): çağıranın CRM kapsamı dışındaki firma ve kişiler `core.party` / `core.person` uçlarında yalnızca asgari kimlikle (taraf: tür, ünvan, vergi no; kişi: ad, soyad) görünür, iletişim alanları boş gelir, güncelleme ve silme 404 döner. Yönetici ve "tüm kayıtlar" kapsamı etkilenmez.
- **Silme:** ortak kayda başvuran alanlar `IModule.SharedRecordReferences` ile bildirilir. Kullanılan taraf ya da kişi silinemez; 409 yanıtı nerede kullanıldığını söyler (ör. "1 CRM firması, 2 kişi"). CRM firması silinince taraf kalır.
- **Sürüm:** CRM firmasının ve kişisinin sürümü, kendi sürümüyle ortak kaydın sürümünden oluşur. Başka bir modül ortak kaydı değiştirdiyse eski sürümle gelen CRM güncellemesi 409 alır.
- **Denetim:** değişiklik, hangi kayıt üzerinden yapıldıysa onun denetim kaydına yazılır. CRM formundan değişen ünvan `crm.company`, ortak kayıt üzerinden değişen ünvan `core.party` kaydında görünür.
- `SharedRecords` migration'ı mevcut firmaları taraflara, kişileri ortak kişilere taşır; kimlikler aynı kalır.
- **Mükerrer önerisi ve birleştirme** ([ADR-0013](docs/adr/0013-mukerrer-onerisi-ve-guvenli-birlestirme.md)): vergi numarası kesin, ad/e-posta/telefon olası eşleşmedir; öneri hiçbir şeyi birleştirmez. Birleştirme ayrı izin ister (`crm.companies.merge`, `crm.contacts.merge`; hazır hiçbir role verilmez), önizleme + sürüm denetimiyle tek işlemde çalışır, kaynak kaldırılır ve eski kimlik hedefe izlenir (`merged/{oldId}`). Ortak kayda başka modüllerin başvuruları `IReferenceMover` ile taşınır; taşıyamayan depo birleştirmeyi engeller.
- Henüz yok: kullanıcının (üyeliğin) kişiye bağlanması, birleştirmenin geri alınması ve birleştirme için arka plan toplu aracı.

### İletişim tercihi ve engel ([ADR-0025](docs/adr/0025-kampanya-ve-segment-yonetimi.md), dilim 1)

Pazarlama izninin tek sahibi çekirdektir; kampanya, destek gibi modüller yalnızca okur (`ICommunicationPreferences`, `Modulix.Core.Contracts`). Tercih kişiye değil **iletişim noktasına** (kanal + normalize adres + amaç) bağlıdır; CRM kapalıyken de çalışır. Firma/e-posta kaydı izin değildir: kayıt yoksa durum `Unknown` ve pazarlama gönderilmez.

- Kanallar `Email`, `Phone`, `Sms`, `WhatsApp`; amaçlar `Marketing`, `Transactional`, `Service` (işlem/hizmet bildirimi izin gerektirmez ama pazarlama iznini aşmak için seçilemez). E-posta küçük harfe çevrilir (yerel kısımda nokta/`+etiket` birleştirilmez); telefon uluslararası rakam biçimine indirilir, `+`/`00` yoksa 10-11 haneli numaralar Türkiye (`90`) sayılır.
- `PUT /api/communication/preferences` (`core.communication.manage`): izin ya da ret. İzin için kanıt referansı ya da gerekçe zorunludur; **reddedilmiş izin içe aktarma, sağlayıcı veya sistemle yeniden açılamaz**, yalnızca `manual`/`form`/`preference-center` kaynağı ve kanıtla açılır. Her değişiklik değişmez olay satırı bırakır (`GET /preferences/{id}/events`); aynı kayıt tekrarlanırsa olay üretmez.
- Engel (`POST /api/communication/suppressions`, `core.communication.suppress`): `HardBounce` ve `InvalidAddress` bütün amaçları, `Complaint`/`OptOut`/`Manual` pazarlamayı durdurur ve izni ezer. Kaldırma gerekçe ister (`POST …/{id}/lift`), satır silinmez. Aynı kanal+adres+nedenle aktif engel varsa yenisi açılmaz.
- `POST /api/communication/check` ve `GET /preferences`, `GET /suppressions` `core.communication.read` ister. Denetim kaydı adresi maskeli yazar (`a***@example.com`).
- **Abonelikten çıkma ve tercih merkezi (dilim 6)**: her pazarlama iletisine kişiye özel bir çıkış bağlantısı girer (`IUnsubscribeLinks`; belirteç rastgele 256 bit, yalnızca SHA-256 karması saklanır, `core.CommunicationLinkTokens`). Sayfa `/abonelik/{tenant}#t=…` oturumsuzdur; belirteç `#` parçasındadır (sunucu günlüğüne ve Referer'a gitmez) ve çıkış yalnızca düğmeyle yapılır (bağlantıyı önceden açan güvenlik tarayıcıları kimseyi çıkaramaz). Uçlar `POST /api/public/communication/{tenant}/view|unsubscribe|resubscribe` (gövdede belirteç) ve RFC 8058 tek tıkla çıkış `POST …/one-click/{belirteç}` (`List-Unsubscribe=One-Click`); hepsi yalnızca POST, hız sınırlı (`CommunicationPublic:RateLimitPerMinute`, varsayılan 30), gövde ≤ 4 KB, geçersiz/başka tenant'ın/biçimsiz belirteç aynı 404. Belirteç yalnızca o adresin pazarlama tercihini değiştirir: çıkış `Denied` (kaynak `unsubscribe`, tekrarı güvenli), kişi yalnızca **kendi** çıkışını geri alabilir (firma/içe aktarma/sağlayıcı kaydı ve aktif engel geri açılamaz). Süresi (400 gün) dolmuş bağlantıyla çıkış yine yapılır, geri alma yapılamaz. Adres sayfada maskelidir. `App:PublicUrl` ayarlı değilse pazarlama çalıştırması başlatılmaz.
- **Konu bazlı tercih (dilim 14)**: konu pazarlama iznini vermez, yalnızca daraltır. Konular firmaya özgüdür (`core.CommunicationTopics`; anahtar küçük harf-rakam-tire, sonradan değişmez, silinmez yalnızca kapatılır); konudan çıkış `core.CommunicationTopicPreferences`'te kanal + adres + konu başınadır. `GET/PUT /api/communication/topics` ve `GET/PUT /api/communication/topic-preferences` (okuma `core.communication.read`, yazma `core.communication.manage`). Kampanyanın `topic` alanı doluysa konudan çıkmış alıcı hedef kitle dondurulurken elenir ve gönderimden hemen önce yeniden denetlenir (kod `topic-opt-out`); işlem/hizmet bildirimi etkilenmez. Tercih merkezinde (abone durumunda) konu onay kutuları gösterilir: `POST /api/public/communication/{tenant}/topic` `{token, topicKey, subscribed}`; çıkış her zaman yapılır, dönüş yalnızca süresi dolmamış bağlantıyla, izin açıkken, engel yokken ve çıkışı kişi kendisi yapmışsa olur. İletideki çıkış bağlantısı ve tek tıkla çıkış tüm pazarlamayı reddetmeye devam eder. Yönetim ekranı: Yönetim → İletişim tercihleri → Konular. Ayrıntı: ADR-0025 dilim 14.
- Kod: `Modulix.Core/Communication` (varlıklar, `CommunicationRules`), `Modulix.Infrastructure/Communication/CommunicationService.cs`, uç noktalar `Modulix.Api/Communication`. **Henüz yok:** tercih merkezi/abonelikten çıkma bağlantısı, soft bounce sayacı, İYS entegrasyonu, ekran (sonraki dilimler; bkz. ADR-0025 bölüm 6 ve 8).

**Eski `companyId` alanı (ADR-0011):** kişi API'sindeki `companyId` artık ilişkilerden türetilen birincil firmadır (en eski aktif ilişki). Eski istemciyle firma vermek ilişki açar, değiştirmek önceki birincil ilişkiyi bitirip yenisini açar, aynı değeri yeniden göndermek hiçbir şeyi bozmaz.

**Arama ve süzgeçler (ADR-0012, sunucu tarafı):** firma `search` ad, vergi no, şehir, etiket ve tüm iletişim noktaları ile adreslerde (normalleştirilmiş: `850-777-6655`, `cayirova`) arar; `city` (eski şehir alanı ve aktif adresler) ve `kind` süzgeçleri vardır. Kişi `search` ad ve tüm iletişim noktalarında arar; `role=Purchasing|Finance|…` aktif ilişkisinde o rol olan kişileri, `withoutCompany=true` firmasızları getirir. Arayüzde firma detayı lokasyon, adres, iletişim ve ilişkili firma bölümlerini, kişi detayı (`/crm/kisiler/{id}`) aktif/geçmiş firma ilişkilerini ve erişilebilen aktivite/fırsatları gösterir.

**Eski telefon/e-posta/şehir/adres alanları (ADR-0012):** firma ve kişi API'sindeki bu alanlar artık ana iletişim noktasının/ana adresin aynasıdır. Eski istemciyle yazmak ana kaydı günceller veya açar (değişmeyen değeri yeniden göndermek hiçbir şeyi çoğaltmaz); yeni uçlardan ana kaydı değiştirmek eski alanı günceller. Telefon/e-posta orijinal haliyle saklanır, aramalar normalleştirilmiş değer üzerinden yapılır. Aynı e-posta/santral birden fazla kişide veya firmada bulunabilir (kimlik sayılmaz); iletişim noktası pazarlama izni değildir.

**Kişi görünürlüğü (ADR-0010):** firmaya bağlı kişi, bağlı olduğu firmanın erişim kapsamına (Own/Team/All) göre görünür; firmasız kişi kendi sorumlusuna (`ownerId`) göre. Kişiyi firmaya bağlamak için firmayı görebilmek gerekir (422, `companyId`). Firma API'si `kind` (Organization/Individual) ve `taxOffice` alanlarını da taşır; vergi numarası tüzelde 10, gerçek kişide 11 hane olmalıdır (numara ya da tür değişirken denetlenir). Boş gönderilen `kind`, `taxOffice` ve kişide `ownerId` mevcut değeri korur.

| Kaynak | Filtreler |
| --- | --- |
| Firmalar | `status` (Prospect, Customer, Inactive), `ownerId`, `partyId` |
| Kişiler | `companyId`, `personId` |
| Fırsatlar | `companyId`, `contactId`, `stage`, `open=true` (kazanılmamış ve kaybedilmemiş), `ownerId` |
| Aktiviteler | `companyId`, `contactId`, `opportunityId`, `leadId`, `open`, `overdue`, `dueBefore=<ISO zaman>`, `ownerId`, `status`, `type`, `priority`, `related`, `timeline`, `range` (bkz. Aktivite ve takvim yönetimi) |

- Firma, fırsat ve aktivitenin bir sorumlusu vardır; oluştururken boş bırakılırsa kaydı oluşturan kullanıcı atanır. Sorumlu, kuruluşun etkin üyesi olmalıdır.

- Tüm işlemler kayıt boru hattından geçer: modül tenant için kapalıysa veya izin yoksa 403, başka tenant'ın kaydı 404, başka tenant'ın kaydına bağlanmak 422 döner. Bağlı kaydı olan firma silinemez (409). Audit ve outbox kaydı otomatik yazılır.
- **Sürüm zorunludur (B1):** `/api/crm/...` ve `/api/records/...` üzerinde güncelleme (`version` gövdede) ve silme (`?version=`) okunan sürümü ister; sürümsüz istek 428 (`code: VersionRequired`) alır, değişmiş sürüm 409 kalır. Zorunluluk yalnızca bu HTTP uç noktalarındadır; kayıt devri ve olay aboneleri gibi arka plan işleri boru hattını doğrudan çağırır, etkilenmez.
- Aynı kayıtlara genel uçtan da ulaşılır (`/api/records/crm.company` vb.); aynı izinler geçerlidir.
- Arayüz API ile aynı adresten sunulur: `https://localhost:7026` → giriş, kuruluş seçimi, Lead'ler / Firmalar / Kişiler / Fırsatlar / Aktiviteler. Telefonda listeler kart görünümüne döner.
- Firma adına tıklayınca firma detay sayfası açılır: solda özet kartı (sorumlu, sektör, satış özeti, hızlı iletişim), sağda sekmeler (Genel bilgiler, Kişiler ve ilişkiler, Fırsatlar ve leadler, Aktiviteler, Geçmiş); aktivite ve fırsat oradan sağdan açılan panelde eklenir. Kişi detay sayfası aynı düzendedir. Sekme ilk açılışta yüklenir, sonra durumunu korur. Fırsatlar sayfası varsayılan olarak satış hunisini (aşama sütunları, sürükle bırak) gösterir. Aktiviteler sayfası varsayılan olarak haftalık saat çizelgesiyle (bana atananlar) açılır; liste, gün, ay ve ajanda görünümleri seçilebilir. Üstteki özet kartları (Bugün, Geciken, Bu hafta, Tamamlanan) tıklanınca sayısını verdikleri görünümü açar; takvimin yanında "Bugünün aktiviteleri" paneli vardır, detay ve düzenleme sağdan açılan panelde yapılır.

### Lead yönetimi (potansiyel müşteri / satış talebi, [ADR-0014](docs/adr/0014-lead-yonetimi.md))

Lead, yeterliliği henüz doğrulanmamış satış ilgisidir; firma, kişi ve fırsattan **ayrı** bir kayıttır (`crm.Leads`). Açılırken firma ya da kişi gerekmez; mevcut müşteriden gelen yeni talep de Lead olabilir; aynı kişi/firma için birden fazla Lead bulunabilir (aynı e-posta tek başına mükerrer kanıtı değildir). Fırsat aşamalarındaki "Lead/Aday" aşaması bundan bağımsızdır; mevcut fırsatlar Lead'e **taşınmaz**.

| Uç nokta | Ne yapar | İzin |
| --- | --- | --- |
| `GET /api/crm/leads` (+ `/{id}`) | Liste/detay. Filtreler: `status`, `source`, `priority`, `ownerId` (`me`), `ownerNot=me` (ekip), `companyId`, `contactId`, `open`, `unassigned=true` (atama bekleyenler), `qualifiedNotConverted=true`, `receivedFrom`/`receivedBefore`, `firstContactDueBefore=<ISO>` (temassız ve bu andan önce gelmiş), `followUpDueBefore=<ISO>`, `convertedOpportunityId`; `search` konu, no, ad, firma, e-posta | `crm.leads.read` |
| `POST`, `PUT /{id}`, `DELETE /{id}?version=` | Oluştur / alanları düzenle / sil. Durum, sorumlu ve dönüşüm alanları bu uçlardan **yazılamaz** (yok sayılır); `ownerId` yalnızca oluştururken, başkası içinse atama izniyle verilebilir | `crm.leads.create` / `.update` / `.delete` |
| `POST /{id}/assign` `{ownerId, version}` | Sorumluyu değiştirir (hedef etkin üye olmalı; eski/yeni sorumlu audit'e, atama e-postası genel abonelikten) | `crm.leads.assign` |
| `POST /{id}/start-contacting`, `/qualify` `{note}`, `/nurture` `{followUpAt, note}` | İletişime geç / nitelendir (asgari koşullar) / daha sonra takibe al (tarih ya da vadeli açık aktivite) | `crm.leads.qualify` |
| `POST /{id}/disqualify` `{reason, note}`, `/reopen` `{reason}` | Ele (neden zorunlu) / elenmiş Lead'i gerekçeyle yeniden aç | `crm.leads.disqualify` |
| `GET /{id}/conversion-preview`, `POST /{id}/convert` | Dönüşüm önizlemesi ve dönüşüm (mevcut/yeni firma ve kişi, fırsat). Tek işlem; ikinci dönüşüm 409 | `crm.leads.convert` |
| `GET /duplicates?email=&phone=&companyName=&website=`, `GET /{id}/duplicates` | Olası eşleşmeler (Lead/firma/kişi); yalnızca çağıranın görebildikleri | `crm.leads.read` |
| `GET /report?from=&to=`, `GET /export` (CSV), `GET /settings` | Rapor, dışa aktarma (audit'e yazılır), ilk temas hedefi | `.read` / `.export` |
| `/api/crm/lead-forms` (+ `POST /{id}/secret`) | Web formu/entegrasyon tanımı ve sır yenileme | `crm.lead-forms.manage` |
| `POST /api/public/lead-forms/{firmaKisaAdi}/{formKimligi}` | **Herkese açık** Lead toplama (aşağıda) | Yok (oturumsuz) |

Aktivite ve fırsat uçlarına `leadId` (aktivite filtresi/alanı), `outcome` (aktivite sonucu: `Reached`, `NoAnswer`, `Sent`) ve `sourceLeadId` (fırsat filtresi/alanı, yalnızca dönüşümle yazılır) eklendi.

**Durumlar:** Yeni → İletişim kuruluyor → Nitelikli → Fırsata dönüştürüldü; ayrıca Daha sonra takip ve Elendi. "Atandı" ayrı durum değildir; atama `ownerId`'dir (ADR-0014). Dönüşmüş Lead kapalıdır; elenmiş Lead yetkili kullanıcıca gerekçeyle yeniden açılır. Tüm durum ve sorumlu değişiklikleri kayıt geçmişinde (eski/yeni değer, gerekçe) görünür.

**İlk temas** yalnızca *gerçekleşen* temastan türetilir: tamamlanmış toplantı; sonucu "Ulaşıldı" olan tamamlanmış arama; sonucu "Ulaşıldı/Gönderildi" olan tamamlanmış e-posta. Planlanmış arama, görev ve not temas sayılmaz. Hedef süre tenant ayarı *CRM Lead → İlk temas hedefi (takvim saati)*; çalışma saati takvimi olmadığı için süre **takvim saatidir**. Aktivite tamamlamak Lead'i otomatik nitelendirmez.

**Dönüşüm:** `Nitelikli` Lead için ekran önizleme gösterir; firma (mevcut ya da yeni — gerçek kişi müşteri için `Individual` firma) ve isteğe bağlı kişi seçilir. Yazımlar kullanıcının kendi izinleriyle yapılır (dönüşüm izni tek başına firma/kişi/fırsat oluşturma hakkı vermez), tek işlemdedir (hata olursa hiçbir kayıt kalmaz), mevcut kayıtların verisi değişmez, aktiviteler kopyalanmaz (Lead'e bağlı kalır; fırsattan "Kaynak Lead" bağlantısıyla erişilir).

**Raporlar** kullanıcının erişim kapsamıyla sınırlıdır. Dönem kohortu = dönemde *gelen* Lead'ler; dönüşüm oranı = kohortta dönüşen / kohort (kohort boşsa oran gösterilmez); dönemde yapılan ama önceki dönemde gelmiş Lead'lerin dönüşümü ayrıca "dönemde yapılan dönüşüm"dür. Süreler takvim saati; tanımlar ekranda ve `LeadReportDto` belgesindedir.

#### Web formu / entegrasyon sözleşmesi

Yönetici *CRM → Lead'ler → Formlar* ekranından (ya da `/api/crm/lead-forms`) form tanımlar: ad, varsayılan sorumlu (boş/pasifse Lead atama havuzuna düşer; rastgele kullanıcıya atanmaz), izinli siteler (`https://site.com`, joker/yol yok) ve isteğe bağlı sunucu sırrı. **Form kimliği gizli değildir**; sayfa kaynağında görünür.

```http
POST /api/public/lead-forms/{firmaKisaAdi}/{formKimligi}
Content-Type: application/json
Origin: https://www.ornek.com                 # tarayıcı gönderimi: izinli kaynak olmalı
X-Lead-Form-Secret: lfs_...                   # yalnızca sunucudan sunucuya (tarayıcıya konmaz)

{
  "submissionId": "7f3c1e9a-2b4d-4c55-9a10-0d3e5f6a7b8c",
  "firstName": "Mehmet", "lastName": "Kaya", "companyName": "Kaya Lojistik",
  "email": "mehmet@ornek.com", "phone": "0532 111 22 33",
  "message": "10 araçlık filo için bakım teklifi istiyoruz.",
  "productInterest": "Filo bakımı", "utmSource": "google", "website2": ""
}
```

- Yanıt kabulde her zaman `202 {"accepted":true}`'dur (yeni Lead, aynı gönderimin tekrarı, kayıtlı müşteri/e-posta ve bal tuzağı ayırt edilmez). Hatalar: `400` (alan hatası, bilinmeyen alan), `403` (kaynak/sır geçersiz), `404` (form yok/pasif), `413`, `415`, `429`.
- Yalnızca şu alanlar kabul edilir: `submissionId` (zorunlu, 8-100 karakter), `subject`, `message`, `firstName`, `lastName`, `companyName`, `email`, `phone`, `jobTitle`, `country`, `city`, `productInterest`, `referrer`, `utmSource`, `utmMedium`, `utmCampaign`, `website2` (bal tuzağı; boş olmalı). E-posta ya da telefon, ve ad/soyad/firma adından biri, ve bir talep metni gerekir. `tenantId`, `ownerId`, `status`, `priority`, `source`, iş birimi, rol gibi her alan `400` alır.
- Aynı `submissionId` tekrarında yeni Lead açılmaz (idempotent); aynı kişinin farklı gönderimi ayrı Lead olur.
- Hız sınırı: IP + form başına dakikada `LeadIntake:RateLimitPerMinute` (varsayılan 20) → `429`; gövde en fazla 32 KB. Ters vekil arkasında `ForwardedHeaders` yapılandırın.
- Origin/CORS yalnızca tarayıcı gönderimini sınırlar, kimlik doğrulama **değildir**. Sır oluşturulurken bir kez gösterilir, yalnızca SHA-256 özeti saklanır; "yalnızca sunucu" formlar tarayıcıdan gönderimi reddeder.
- Gönderim pazarlama izni sayılmaz. İzin/rıza altyapısı henüz yoktur; izin amacı, kaynağı ve zamanı izlemesi açık iştir.

#### Geliştirici notları (Lead)

- Kod: `src/Modulix.Modules.Crm` → `Domain` (`Lead`, `LeadForm`), `Records` (`LeadRecordStore`, `LeadFormRecordStore`, `LeadWorkflowGate`), `Leads` (`ILeadWorkflow`, `ILeadConversion`, `ILeadIntake`, `ILeadFormAdmin`, `LeadRules`, `ILeadQualificationRule`, `LeadFirstContactSubscriber`). Uç noktalar `Modulix.Api/Crm/Lead*.cs`; ekranlar `Modulix.Web/Pages/Crm/Lead*.razor`.
- Sektör nitelendirme koşulu eklemek: `ILeadQualificationRule` uygulayıp scoped kaydedin (varsayılan `MinimumQualificationRule` sektör bağımsızdır; bütçe/karar verici zorunlu değildir).
- Çok kayıtlı atomik iş: `IRecordPipeline.RunAtomicAsync`. Olay nedenleri: `LeadEventReasons` (`RecordUpdated` + `reason`).
- **AI ajan araçları (`SearchLeads` vb.) yapılmadı**: ajan altyapısı yok. `ILeadWorkflow`/`ILeadConversion` ve boru hattı sorguları araç olarak sunulabilecek şekilde tasarlandı; ajan kendiliğinden Lead elemez/birleştirmez/dönüştürmez.

**Yeni bir sektör modülü eklemek** (CRM'i örnek alın):

1. `Domain`: entity'ler `ITenantEntity` uygular. `Persistence`: `IEntityTypeConfiguration` sınıfları, şema = modül anahtarı (aksi halde uygulama açılmaz).
2. `Records`: her entity için bir kayıt deposu (`CrmRecordStore` kalıbı); `IModule.ConfigureServices` içinde kaydedilir.
3. `Program.cs` → `ModulixModules.Create()` listesine modülü ekleyin, uç noktaları `MapCrmEndpoints` gibi eşleyin.
4. Migration üretin ve her tablo için `TenantIsolationSql.AddTable` ekleyin; eklenmezse `Every_tenant_table_is_protected_by_row_level_security` testi kırılır.
5. Müşteri, tedarikçi, taşıyıcı ya da kişi tutan modül yeni firma veya kişi tablosu açmaz. Ortak kayda (`Party`, `Person`) bağlanan bir uzantı entity'si yazar, `SharedRecordAccess` ve `SharedRecordReferences` bildirir (CRM'deki `Company` / `CompanyRecordStore` kalıbı, ADR-0006).

### Aktivite ve takvim yönetimi ([ADR-0015](docs/adr/0015-aktivite-ve-takvim.md))

Aktivite, CRM'in `crm.Activities` kaydıdır. Yaşam döngüsü **tür ailesine** göre ayrı durum makineleridir (görev, arama, toplantı/ziyaret, e-posta); durum, tamamlanma, sonuç ve sorumlu yalnızca eylem uç noktalarıyla değişir, düz `PUT` bunları sessizce yok sayar. Gecikme saklanmaz, açık durum ve son tarihten türetilir.

| Uç nokta | Açıklama | İzin |
| --- | --- | --- |
| `GET/POST/PUT/DELETE /api/crm/activities` | Kayıt (PUT kaydın tamamını yazar, `version` zorunlu). Oluştururken `completedAt` (+ `outcome`) geçmiş tarihli, tamamlanmış etkileşim kaydı açar | `crm.activities.read` / `write` |
| `POST /{id}/start`, `/block {reason}`, `/unblock` | Görev: devam ediyor / bloke (neden zorunlu) / engeli kaldır | `write` |
| `POST /{id}/complete {outcome, note, completedAt, actualMinutes, nextStep}` | Aileye göre Tamamlandı / Ulaşılamadı / Katılım olmadı / Gönderildi. `nextStep` tek işlemde yeni, önceki aktiviteye bağlı aktivite açar | `write` |
| `POST /{id}/cancel {reason}` | İptal (gerekçe zorunlu) | `write` |
| `POST /{id}/reopen {reason}` | Kapanmış aktiviteyi yeniden açar (gerekçe zorunlu) | `crm.activities.reopen` |
| `POST /{id}/reschedule {reason, dueAt, startAt, endAt, isAllDay, startDate, endDate, allowConflict}` | Erteleme; sayaç artar, çakışmada 422 `conflict` | `write` |
| `POST /{id}/reassign {ownerId}` | Birincil sorumlu; kendine almak `write`, başkasına atamak `crm.activities.assign` | |
| `POST /bulk {action, items[{id,version}], reason, ownerId, days}` | `complete`, `cancel`, `reopen`, `reassign`, `reschedule-by-days`; en çok 100 kayıt, **kayıt başına** sonuç (kısmi başarı) | kayıt başına |
| `GET /{id}/related` | Doğrudan ve genel ilişkiler; başlıklar yalnızca görülebilen kayıtlar için, görünmeyenin sayısı | `read` |
| `/api/crm/activity-links`, `/api/crm/activity-participants` | İlişki ve katılımcı kayıtları (aktivitenin kapsamına ve gizliliğine bağlı) | `read` / `write` |

**Süzgeçler** (liste uçlarında): `open`, `overdue=<ISO>`, `status`, `type`, `priority`, `ownerId=me`, `participant=me`, `previousActivityId`, ilişki: `companyId`, `contactId`, `opportunityId`, `leadId`, `related=<tür>:<id>` (herhangi bir modülün kayıt türü), `timeline=crm.company:<id>` (firma + kişileri + fırsatları + dönüşmüş Lead'leri; aynı aktivite bir kez). **Takvim penceresi:** `range=<başlangıçUTC>|<bitişUTC>|<başlangıçGünü>|<bitişGünü>` en çok 93 gün; sayfa en çok 200.

**Diğer modüllerin aktiviteye bağlanması:** `Modulix.Core.Contracts.Records.IActivityLinkTarget` uygulayıp `services.AddScoped<IActivityLinkTarget, ...>()` ile kaydedin; aktivite çekirdeği değişmez. Hedef, yalnızca çağıran görebiliyorsa var sayılır ve başlığı yalnızca o zaman verilir.

**Özel aktivite** (`isPrivate`): sorumlu, oluşturan, katılımcılar ve `crm.activities.view-private` sahibi ayrıntıyı görür; diğerleri yalnızca "Meşgul" ve zaman bilgisini görür (arama, ilişki süzgeci ve alt kayıtlar dahil). **Olay/audit geçmişi yöneticilere başlığı gösterir** (ADR-0015 bilinen sınır).

**Arayüz:** *CRM → Aktiviteler*: Liste, Gün, Hafta, Ay, Ajanda görünümleri; Bugün / Gecikenler / Bana atananlar / Ekip / Tüm açıklar; durum-tür-öncelik süzgeçleri; tarayıcıda saklanan kayıtlı görünümler; gün hücresinden hızlı oluşturma; ayrıntı paneli ve eylemler; sürükle-bırak yeniden planlama; toplu seçim. Firma detayı birleşik zaman akışını gösterir. **E-posta durumu "Gönderildi" yalnızca kullanıcının kaydıdır, teslim/okundu anlamına gelmez; bu sürümde e-posta gönderen bir kod ve harici takvim bağlantısı yoktur.**

**Geliştirici:** kural katmanı `Activities/ActivityRules.cs` (saf, birim testli); eylemler `IActivityWorkflow`; kayıt depoları `Records/ActivityRecordStore.cs`, `ActivityChildStores.cs`; görünürlük `ActivityVisibility.cs`. Yeni tablolar (`ActivityLinks`, `ActivityParticipants`) RLS politikasındadır. Yapılmayanlar ve nedenleri ADR-0015 sonunda.

### Ürün, hizmet ve fiyat yönetimi ([ADR-0018](docs/adr/0018-urun-hizmet-fiyat-yonetimi.md)) — kısmen uygulandı

Kategori (`/api/crm/product-categories`), ölçü birimi (`/api/crm/units`) ve ürün/hizmet kartı (`/api/crm/products`; liste süzgeçleri: `status`, `kind`, `categoryId`, `code`, `sellableOn=yyyy-MM-dd`, arama kod/ad/barkod/etiket) kayıt boru hattından geçer. İzinler: `crm.products.read`, `crm.products.write`, **`crm.product-costs.read`** (maliyet hassas alandır; izni olmayan görmez ve yazamaz, hiçbir hazır role verilmez). Ürün kodu tenant içinde benzersizdir (iki tenant aynı kodu kullanabilir). Yaşam döngüsü Taslak → Aktif ↔ Pasif → Satıştan kaldırılmış (son durum); yalnızca taslak silinebilir, diğerleri 409 alır. Yalnızca aktif ve satış tarih aralığındaki ürün yeni satışta kullanılabilir (`CatalogRules.IsSellable`). Ürünlerde kullanılan birimin grubu/katsayısı değiştirilemez ve silinemez; kategori kendi altına taşınamaz. Fiyat seçimi, indirim, vergi/yuvarlama, birim dönüşümü ve paket hesapları `Modulix.Core.Contracts/Pricing` altındaki saf çekirdektedir ve aşağıdaki uç noktalara bağlıdır.

**Fiyatlandırma** (izinler `crm.prices.read` / `crm.prices.write`): fiyat listesi `/api/crm/price-lists` (kapsam Default/Customer/Segment; Taslak → Yayımlandı → Arşiv, yayımlanan değişmez) ve satırları `/api/crm/price-list-items` (ürün başına miktar kademesi, ürünün temel birimi başına fiyat), vergi oranı `/api/crm/tax-rates`, döviz kuru `/api/crm/exchange-rates`, paket bileşeni `/api/crm/product-components` (`crm.products.*`), indirim politikası `/api/crm/discount-policies`. **`POST /api/crm/pricing/calculate`** sunucu tarafı tek fiyat hesabıdır: liste seçimi (açık → müşteri → segment → varsayılan), birim dönüşümü, ardışık indirim, vergi ve yuvarlama; hata `code` ile 422 döner (`price-not-found`, `price-conflict`, `tax-rate-not-found`, `exchange-rate-not-found`, `product-not-sellable`, `invalid-quantity` …). Ekranlar: Ürün ve hizmetler (`/crm/urunler`, paket bileşenleri dahil), `/crm/urun-kategorileri`, `/crm/birimler`, `/crm/fiyat-listeleri`, `/crm/vergi-kur`, `/crm/indirimler`, `/crm/fiyat-hesapla`. **Henüz yok:** varyant, onay kuyruğu (yalnızca `requiresApproval` işareti), sabit paket fiyatının hesaba bağlanması, içe aktarma, dosya ilişkisi, teklif entegrasyonu (ayrıntı ADR-0018 "Uygulama durumu").

### Teklif yönetimi ([ADR-0019](docs/adr/0019-teklif-yonetimi.md)) — kısmen uygulandı

Teklif başlığı `/api/crm/quotes`, kalemleri `/api/crm/quote-lines` (kayıt boru hattı; tek veritabanında, RLS'li). **Toplamlar yalnızca sunucuda** `QuoteCalculator` ile hesaplanır (satır indirimi → genel indirim dağıtımı → satır başı vergi → oran gruplarına özet); istek gövdesindeki tutarlar yok sayılır. Ticari durum (`Draft → Presented → Accepted/Rejected/Expired/Cancelled/Superseded`), iç onay (`NotRequired/Pending/Approved/Rejected/ChangesRequested`) ve gönderim durumu ayrı alanlardır. Durum geçişleri yalnızca eylem uç noktalarıdır (`POST /api/crm/quotes/{id}/submit-for-approval | withdraw-approval | approve | reject-approval | request-changes | present | record-accepted | record-rejected | cancel`; hepsi kayıt sürümü ister, eşzamanlı çakışmada 409), kurallar `QuoteRules` ile arayüzle ortaktır; `GET .../actions` yetkili kullanıcıya eylem listesini ve yapılamayanların nedenini verir, `GET .../history` tarihçeyi. `POST .../revise` aynı ailede yeni taslak revizyon (kalemler aynı kararlı anahtarla kopyalanır), `POST .../duplicate` yeni aileyi açar. Yeni sürüm **sunulunca** ailenin önceki sunulmuş sürümü `Superseded` olur; aile başına en fazla bir `Accepted` sürüm veritabanında filtreli benzersiz indeksle korunur. Sunulmuş/sonuçlanmış sürüm yerinde değiştirilemez. Ticari değişiklik bekleyen/verilmiş iç onayı geçersiz kılar. İzinler: `crm.quotes.read|write|discount|manual-price|approve|present|record-decision|cancel`, `crm.quote-costs.read` (kalem maliyeti, yetkisiz yanıtta hiç dönmez). Ayarlar (`CRM Teklif`): iç onay indirim eşiği %, toplam tutar eşiği, varsayılan geçerlilik günü, kendi teklifini onaylama (varsayılan hayır). Ekranlar: `Teklifler` (`crm/teklifler`), teklif oluşturma/detay/kalem editörü (`crm/teklifler/yeni`, `crm/teklifler/{id}`), `Teklif onayları` (`crm/teklif-onaylari`). **Müşteri belgesi ve paylaşım:** sunum anında sabit PDF üretilir (QuestPDF; SHA-256 özeti, şablon sürümü, revizyon başına tek belge): `GET|POST /api/crm/quotes/{id}/documents`, `GET .../documents/{docId}/file`. Paylaşım bağlantısı `GET|POST .../share-links`, `POST .../share-links/{linkId}/revoke` (`crm.quotes.share`); belirteç yalnızca oluşturulurken bir kez görünür, veritabanında özeti saklanır. Müşteri kararları `GET .../decisions`. Oturumsuz müşteri sayfası `/teklif/{firma}#t={belirteç}` (belirteç URL parçasındadır, sunucu günlüğüne girmez) `POST /api/public/quotes/{firma}/view | pdf | decision` uç noktalarını kullanır; hız sınırı `QuotePublic:RateLimitPerMinute` (varsayılan 60, karar için 1/6). Kabul; ad soyad, onay cümlesi ve görülen belgenin özetiyle kanıtlanır ve teklif geçişiyle aynı işlemde yazılır. Ayarlar: `crm.quote.seller-details`, `crm.quote.footer-note`. QuestPDF Community lisansı yıllık geliri 1 milyon USD altındaki şirketlere ücretsizdir; üstü ücretli lisans ister. **Onay kuralları:** `/api/crm/quote-approval-rules` (`crm.quote-rules.manage`; ekran `crm/teklif-kurallari`). Bir kuralın girilen tüm koşulları (indirim % eşiği, genel toplam eşiği + isteğe bağlı para birimi) birlikte sağlanırsa teklif iç onay ister; kurallardan biri yeter ve genel eşik ayarlarıyla birlikte uygulanır. İsteğe bağlı onaylayan atanırsa onay yalnızca o kullanıcıdan kabul edilir. `GET .../quotes/{id}/approval-requirements` eşleşen kuralları ve karar yetkisini verir; onaya gönderimde kural adı ve sürümü teklif geçmişine yazılır. **Revizyon karşılaştırma:** `GET /api/crm/quotes/{id}/compare?with={otherId}` aynı ailenin iki revizyonunu kararlı kalem anahtarıyla karşılaştırır (maliyet ve iç not yok); ekran `crm/teklifler/{id}/karsilastir`. **E-posta gönderimi:** bağlantı oluştururken `sendEmail` ile (alıcı e-postası zorunlu) müşteri bağlantı e-postası platform e-posta kuyruğuna yazılır (`platform.EmailMessages.Reference = crm.quote-link:{id}`); gönderim durumu kuyruktan okunur: `Pending` (kuyrukta), `Processing`, `Succeeded` (**yalnızca sağlayıcı/SMTP sunucusu kabul etti**; alıcıya ulaştığını göstermez), `Failed`. Teklifin `deliveryStatus` alanı en son e-postalı bağlantıya eşitlenir. Gönderen/SMTP yapılandırılmamışsa e-posta bekler; geliştirmede SMTP yerel Mailpit'tir. **Raporlar:** `GET /api/crm/quotes/report` (ekran `crm/teklif-raporu`) kayıt boru hattından okunur (izin + veri kapsamı), yalnızca ailelerin son revizyonunu sayar, toplamlar para birimi bazındadır; kabul oranı, karar süresi, sorumlu dağılımı ve dikkat listeleri içerir. Kalem maliyeti, marj ve iç not rapora girmez. `GET /api/crm/quotes/export` (`crm.quotes.export`) CSV verir (formül karakterleri etkisiz, denetim kaydı). **Kabul sonrası:** `Modulix.Core.Contracts.Sales.IAcceptedQuoteSource` kabul edilen teklifi (kalem, toplam, kabul eden, belge özeti; maliyet/iç not yok) sonraki modüllere verir; `GET /api/crm/quotes/{id}/handover` aynı görünümdür. Ayarlar (`CRM Teklif`, hepsi varsayılan kapalı): `crm.quote.on-accept-win-opportunity` (kabulde bağlı açık fırsat net toplamla kazanıldı olur; olay aboneliği, tek kez), `crm.quote.follow-up-days` (sunumdan N gün sonra sorumluya takip aktivitesi), `crm.quote.expiry-reminder-days` (bitmeden N gün önce hatırlatma aktivitesi). `QuoteExpiryWorker` (`QuoteExpiry:WorkerEnabled`, `PollIntervalSeconds`) geçerliliği bitmiş "sunuldu" teklifleri `Expired` yapar (tenant başına `sp_getapplock` oturum kilidiyle tek örnekte); kabul anındaki süre denetimi işe bağlı değildir. Hatırlatma açıldığında ve teklif süresi dolduğunda teklif sorumlusuna e-posta kuyruğa yazılır. Tekliften açılan takip/hatırlatma aktiviteleri teklife bağlanır (`ActivityLink`, `entityKey=crm.quote`) ve teklif sonuçlanınca otomatik iptal edilir; elle bağlanan aktivitelere dokunulmaz. **Esas teklif:** `Opportunity.PrimaryQuoteId` fırsatın esas teklifidir; ilk sunulan teklif otomatik esas olur, yeni revizyon sunulunca esas ona geçer, `POST /api/crm/opportunities/{id}/primary-quote` (`crm.opportunities.write`) ile seçilir/kaldırılır (yalnızca sunulmuş/kabul edilmiş, aynı fırsatın teklifi). Ayar `crm.quote.sync-opportunity-amount` (varsayılan kapalı) açıksa açık fırsatın tutarı esas teklifin net toplamıyla eşitlenir. **Çok adımlı onay:** kuralın `step` alanı (1–9) adımı belirler; adımlar sırayla tamamlanır, bir adımdaki adlı onaylayanların hepsi (ya da vekilleri) onaylamalıdır, adsız adımı onay izni olan herhangi biri tamamlar. Ara onaylar tarihçeye `StepApproved` yazılır, son adım teklifi `Approved` yapar; yeni gönderim sayacı sıfırlar. **Vekâlet:** `/api/crm/quote-approval-delegations` (`crm.quote-rules.manage`; ekran `crm/onay-vekaletleri`): vekil adlı onaylayan adına karar verir (tarihçede "vekâleten"), kendi onay izni olmalıdır. **Onay hatırlatması:** `crm.quote.approval-reminder-hours` (varsayılan 0) açıksa bekleyen adımın adlı onaylayanlarına ve vekillerine bir kez e-posta. **Marj raporu:** `GET /api/crm/quotes/margin-report` yalnızca `crm.quote-costs.read` ile (maliyet = Σ miktar × kalem maliyeti, yalnızca ana toplamdaki kalemler; maliyetsiz kalem ayrıca sayılır); rapor ekranında izinli kullanıcıya ayrı bölüm. **Yapılmadı:** sipariş/sözleşme oluşturma (hedef modül yok), teslim/okundu ve geri dönen e-posta (bounce) bildirimi, marj eşiğine bağlı onay kuralı, rol/grup tabanlı onay ve otomatik yükseltme, marj kuralı, sipariş/sözleşme dönüşümü, fırsat entegrasyonları (kabulde kazanma), raporlar, kur sabitleme ekranı, dışa aktarma, kayıtlı görünümler.

### Fırsat yönetimi ([ADR-0017](docs/adr/0017-firsat-yonetimi.md))

Fırsat; numara (`OP-20261029-AB12CD`, tenant içinde benzersiz), durum (`Open`, `OnHold`, `Won`, `Lost`, `Cancelled`), aşama (Y9b listesi), öncelik, tür, kaynak, ihtiyaç analizi, tutar/olasılık/müşteri bütçesi (bütçe durumu ayrı), tahmini ve gerçek kapanış, sonraki aksiyon ve son müşteri etkileşimi taşır. **Durum–aşama ilişkisi:** Kazanıldı ↔ `won` kategorili aşama, Kaybedildi ↔ `lost`; Açık, Beklemede ve İptal edildi `open` aşamada durur. Çelişkili birleşim kaydedilemez.

**Eylemler** (`POST /api/crm/opportunities/{id}/...`, gövdede `version` zorunlu): `stage` (aşama değiştir), `hold` / `resume` (gerekçe + yeniden değerlendirme tarihi), `win` (kapanış tarihi, kazanılan tutar, neden, devir notu), `lose` (yapılandırılmış neden zorunlu; "Diğer" açıklama ister; kazanan rakip yalnızca rakibe kayıpta; yeniden iletişim tarihi + isteğe bağlı takip aktivitesi), `cancel` (gerekçe; kayıp sayılmaz), `reopen` (ayrı izin, gerekçe, yeni açık aşama, gelecekte kapanış). Durum, aşama (oluşturma sonrası) ve kapanış alanları genel `PUT`/`/api/records` uçlarından yazılamaz; Kanban da `stage` uç noktasını kullanır. Kapanışta açık aktiviteler silinmez ya da devredilmez; yanıtta sayısı (`openActivities`) bildirilir.

| Uç nokta | Açıklama | İzin |
|---|---|---|
| `GET /api/crm/opportunities/{id}/history` | Aşama/durum/kapanış tarihi tarihçesi (kapanış tutarları tutar izni ister) | `read` |
| `/api/crm/opportunity-contacts`, `/api/crm/opportunity-competitors` | Fırsat kişileri (rol ilişkide) ve rakipleri; `opportunityId` süzgeci | `read` / `write` |
| `GET /api/crm/opportunities/report?from=&to=&ownerId=` | Rapor; tanımları yanıttaki `definitions` | `read` (tutar izni yoksa tutarlar null) |
| `GET /api/crm/opportunities/export` | CSV, denetim kaydına yazılır | `crm.opportunities.export` |

**Yetkiler:** `change-stage` (aşama, bekletme), `close` (kazan/kaybet/iptal), `reopen`, `export`. `write` izni olan mevcut roller aşama değiştirmeye ve kapatmaya devam eder (geriye uyumluluk); yeniden açma ve dışa aktarma ayrı izindir. **Ayarlar** (Firma ayarları → "CRM Fırsat"): `crm.opportunity.stage-requirements` (aşamaya geçerken dolu olması gereken alanlar), `crm.opportunity.stage-probabilities` (aşama varsayılan olasılığı; elle girilen olasılık ezilmez), `crm.opportunity.stale-days` (hareketsizlik eşiği).

**Liste süzgeçleri:** `status`, `open`, `live` (açık + beklemede), `stage`, `stageCategory`, `priority`, `type`, `source`, `lossReason`, `currency`, `ownerId=me`, `companyId`, `contactId`, `sourceLeadId`, `number`, `closeFrom`/`closeTo`, `actualCloseFrom`/`actualCloseTo`, `closeOverdueBefore=<tarih>`, `noNextAction=true`, `inactiveBefore=<ISO>`, `holdReviewDueBefore=<tarih>`, `closeDatePostponed=true`. Ekranlar: Fırsatlar (pano/liste), Fırsat sayfası (`/crm/firsatlar/{id}`: satış hunisi, gösterge şeridi, özet, işlemler, esas teklifin kalemleri, kişiler, rakipler, teklifler, tarihçe; sağ panelde aktivite zaman çizelgesi ve esas teklifin finansal özeti. Hunide bir aşamaya tıklamak aşamayı doğrudan değiştirmez, ilgili işlem panelini açar), Fırsat raporu (`/crm/firsat-raporu`).

**Henüz yok:** çoklu pipeline, teklif entegrasyonu, sipariş/sözleşme devri, tahmin anlık görüntüsü, zamanlanmış bildirimler, toplu işlemler (ayrıntı ADR-0017'de).

### Satış raporlama, hedef ve tahmin ([ADR-0026](docs/adr/0026-raporlama-ve-satis-tahmini.md)) — dilim 1 (EPIC 14 kısmen)

Raporlar yetki kazandırmaz: her sayı fırsat listesiyle aynı izin, veri kapsamı ve hassas alan (tutar/olasılık) kurallarıyla kayıt boru hattından okunur; kapsam dışı fırsat hiçbir toplamda yer almaz. Tutarlar vergi hariç net fırsat tutarıdır (muhasebe geliri/tahsilat değil). Hesap tek yerdedir (`Modulix.Modules.Crm/Reporting/SalesMetrics`): kart, detay listesi ve tahmin aynı işlevi kullanır.

- **Satış görünümü** (`/crm/satis-gorunumu`, `GET /api/crm/sales/overview?kind=Month|Quarter|Year&date=&ownerId=&currency=`): gerçekleşen satış, açık pipeline, bu dönem beklenen, ağırlıklı tahmin, dönem öngörüsü (gerçekleşen + ağırlıklı açık), kazanma oranı, hedef gerçekleşme/kalan/pipeline kapsama, aşama dağılımı, 6 dönemlik trend, gecikmiş fırsatlar. Her kart `GET .../overview/cards/{OpenPipeline|ExpectedOpen|WeightedOpen|Realized|Lost}` ile aynı kesitin detay listesine açılır (toplamlar kartla aynı hesaptan). Yanıttaki `warnings` kısmi veriyi (eksik kur/tutar/olasılık/kapanış tarihi, okuma sınırı, kısıtlı veri kapsamı) söyler; `definitions` hesap açıklamalarıdır. Tutar izni yoksa tutar toplamları hesaplanmaz, yalnızca adetler gelir.
- **Kur ve tarih:** açık fırsatlar hesap günü, kazanılanlar kazanım günü kuruyla (`crm.ExchangeRates`) raporlama para birimine çevrilir; kur yoksa tutar toplama girmez ve ayrıca sayılır (1 varsayılmaz). Dönemler firmanın saat diliminde, başlangıç dahil sonraki dönem başı hariçtir; çeyrek/yıl mali yıl başlangıç ayına (ayar "Mali yıl başlangıç ayı", varsayılan Ocak) göredir.
- **Hedefler** (`/crm/satis-hedefleri`, `/api/crm/sales-targets`): metrik (kazanılan tutar / kazanılan adet), kapsam (tenant / kullanıcı), para birimi (yalnızca tutar hedefinde), dönem. Aynı kapsam, metrik ve para biriminde dönemler çakışamaz; metrik/kapsam/para birimi/dönem oluşturulduktan sonra değişmez; değer değişimi gerekçe ister ve sürüm kaydı bırakır. Dönem hedefi, dönemi boşluksuz kaplayan hedeflerin toplamıdır. Tenant hedefi varken kullanıcı hedefleri eklenmez; üst hedefi aşarlarsa uyarılır. Veri kapsamı kısıtlı kullanıcı kapsamındaki kullanıcıların hedefini görür.
- **Sürümlü tahmin** (`/crm/satis-tahmini`, `/api/crm/sales/forecasts`): dönem × kapsam × para birimi için kapsamdaki açık fırsatların anlık görüntüsü. Kategoriler (Hariç, Pipeline, En İyi Durum, Taahhüt) birbirini dışlar, varsayılanı olasılık eşiklerinden gelir (ayarlar "Tahmin: Taahhüt/En İyi Durum için en düşük olasılık"). Senaryolar: Taahhüt, İyimser, Ağırlıklı (kategorilerin üstüne eklenmez). Yönetici düzeltmesi (kategori, tutar farkı, olasılık) gerekçelidir, kaynak fırsatı değiştirmez. Akış Taslak → Sunuldu → Kilitlendi; kilitli sürüm değişmez, yeniden açma gerekçeli ve **yeni sürüm** üretir; sürümler karşılaştırılır (eklenen, çıkan ve nedeni, tutarı/kategorisi değişen); dönem bitince kilitli tahmin gerçekleşenle karşılaştırılır (ufuk gün olarak verilir). Satırlar okurken çağıranın bugünkü veri kapsamına göre süzülür.
- **İzinler:** `crm.sales-reports.read`, `crm.sales-targets.read|manage`, `crm.forecasts.read|write|submit|lock|reopen`; yeni rol şablonu "Satış yöneticisi" (`crm.sales-manager`). Mevcut rollere eklenmedi.
- **Satış analizi (dilim 2)** (`GET /api/crm/sales/analytics/{quotes|leads|stages|team|quality}?kind=&date=&asOf=&ownerId=&currency=`; ekranlar `/crm/satis-analizi`, `/crm/ekip-performansi`, `/crm/veri-kalitesi`; `crm.sales-reports.read` ve alttaki kaydın okuma izni gerekir): **teklif kohortu** (ailenin ilk gönderilme tarihi kohortu, kesim anına göre kabul oranı, revizyon oranı ayrı), **lead dönüşümü** (tekil lead, tüm kohort ve uygun lead oranı, olgunluk uyarısı), **aşama dönüşümü** (fırsat tarihçesinden, oluşturulma kohortu; güncel aşama dağılımı değildir; geçmişi olmayan dönem için üretilmez), **ekip performansı** (kullanıcı bazında, döngü örneklem adediyle, hedefle), **veri kalitesi** (eksik tutar/kur/olasılık/kapanış, gecikmiş, hareketsiz, tarihçesiz).

- **Rapor merkezi ve sınırlı oluşturucu (dilim 3)** (`/raporlar`, `/api/reports`; izinler `core.reports.read|manage|share`): modüller raporlanabilir kayıt türünü veri kümesi olarak bildirir (`IModule.Reports`; CRM: fırsatlar, lead'ler). Rapor, veri kümesinin bildirilmiş sütunlarından kurulur (süzgeç, en çok 2 gruplama, en çok 5 ölçü, sıralama, tablo/çubuk/çizgi/pasta); serbest SQL, hesaplanan alan ve veri kümeleri arası birleştirme yoktur. Her çalıştırma çağıranın izin, veri kapsamı ve hassas alan kurallarıyla kayıt boru hattından yapılır: izni olmayan tutar sütunu süzgeçte/gruplamada/toplamda da kullanılamaz (`forbidden`), paylaşım yetki vermez ve kaldırılınca erişim hemen biter. Tutarlar para birimine göre ayrı toplanır; eksik değer sayılır (`excludedRows`), okuma sınırı (5000) aşılırsa `truncated`. Özet satırına tıklayınca ayrıntı listesi açılır ve toplamı özet satırıyla eşittir. Özel alanlar sütun olur (anahtar kalıcı: yeniden adlandırma raporu bozmaz; arşivleme raporu `columnRemoved` ile geçersiz işaretler). Kayıtlı rapor: özel / seçilen kullanıcılar / firma, favori, sürüm çakışması (409), denetim kaydı (`core.report`). Ayrıntı ve sınırlar: ADR-0026 bölüm 8.
- **Dışa aktarma ve zamanlama (dilim 4)** (`/raporlar/disa-aktarimlar`; izinler `core.reports.export|schedule`): rapor sonucu **ekrandakiyle aynı hesaptan** CSV olur (formül enjeksiyonuna karşı `=+-@` başlangıçları kaçışlanır; UTF-8 BOM). Dosya sahibine özel, 24 saat, kullanıcı başına 20 dosya / 5 MB; **indirme anında** izinler, modül ve hazırlandığı andaki erişim parmak izi (izin kümesi + kayıt kapsamı + sahip kümesi) yeniden denetlenir: yetki değiştiyse `409`, süre dolduysa `410`. Zamanlanmış rapor (günlük/haftalık/aylık, firma saat diliminde) **sahibinin yetkisiyle** arka planda çalışır (`ReportJobs:WorkerEnabled`, `PollIntervalSeconds`); üyelik, izin, modül ya da rapor görünürlüğü bozulursa zamanlama nedeniyle durdurulur ve hiçbir şey teslim edilmez; e-postada veri yoktur, yalnızca indirme bağlantısı. Aynı planlı an için tek çalışma kaydı tutulur (tekrar/yarışan çalışma ikinci dosya üretmez). Önbellek/özet tablo **uygulanmadı**: ilk ölçümde 5000+5000 fırsatta genel görünüm p95 hedefi (2 sn) karşılanmamıştı (3,2 sn); darboğaz sayfa başına sıralama maliyeti ve çok sayıda 200'lük sayfaydı. `Opportunities(TenantId, Status, CreatedAt DESC, Id)` dizini ve toplu okuma (`RecordQuery.Bulk`, sayfa üst sınırı 1000; yetki kuralları aynı) sonrası p95 1,65 sn'dir (ADR-0026 bölüm 8). Rapor veri kümeleri: fırsat, lead, teklif (revizyon satırı), firma. Ölçüm testi: `MODULIX_PERF=1 dotnet test tests/Modulix.IntegrationTests --filter ReportPerformanceMeasurementTests` (`MODULIX_PERF_ROWS`, `MODULIX_PERF_OUT` isteğe bağlı). Okuma sınırı istek başına 5000 fırsattır (aşılırsa yanıt "kesildi" der); büyük hacim ölçülmedi.

## Sözleşme modülü ([ADR-0022](docs/adr/0022-sozlesme-yonetimi.md)) — ilk dilim

Modül anahtarı `contracts`, şema `contracts`; sektörden bağımsızdır ve CRM tablolarına bağlanmaz. Müşteri ve ilgili kişi **ortak kayıttır** (`core.party`, `core.person`; ADR-0006), böylece CRM kapalıyken de sözleşme açılır. Tek veritabanında, RLS'li dört tablo: `Contracts`, `ContractParties`, `ContractLines`, `ContractEvents` (migration `ContractManagement`).

Uç noktalar (kayıt boru hattı; başka tenant'ın kaydı 404): `/api/contracts/contracts`, `/api/contracts/contract-parties` (`contractId`, `partyId`, `personId`, `role` süzgeçleri), `/api/contracts/contract-lines` (`contractId`, `kind`), `GET /api/contracts/contracts/{id}/history` (tarihçe). Sözleşme listesi süzgeçleri: `partyId`, `personId`, `previousContractId`, `ownerId=me`, `number`, `type`, `preparationStatus`, `approvalStatus`, `signatureStatus`, `effectiveStatus`, `renewalMode`, `confidentiality`, `currency`, `indefinite`, `startFrom/startTo`, `endFrom/endTo`, `noticeFrom/noticeTo`; arama başlık/numara/açıklama.

- **Dört ayrı durum alanı** (tek alana sıkıştırılmaz; yalnızca iş akışı eylemleri yazar, genel `PUT` yok sayar): hazırlık `Draft|InReview|ReadyToPublish`, onay `NotRequired|Pending|Approved|Rejected|Withdrawn`, imza `NotSent|Pending|PartiallySigned|Completed|Rejected|Expired|Cancelled`, yürürlük `NotInForce|AwaitingStart|Active|Suspended|Expired|Terminated|Cancelled`. İçerik (başlık, taraf, kalem) yalnızca taslakta, onay beklemiyorken ve imzaya gitmemişken düzenlenir (`ContractRules.CanEditContent`); imzalı ya da yürürlük kaydı olan sözleşme silinemez (`CanDelete`). Durum geçişleri ikinci dilimdedir.
- **Tarihler:** bitiş başlangıçtan önce olamaz; belirsiz süreli sözleşmede bitiş girilmez; yenilemeli (`Manual|Automatic`) sözleşmede yenileme süresi (ay, 1–120) zorunlu, yenilemesizde girilmez; bildirim süresi 0–3650 gün. **Son bildirim tarihi** sunucuda hesaplanır: bitiş − bildirim süresi (`noticeDeadline`, istemci yazamaz).
- **Toplamlar yalnızca sunucuda** (`QuoteCalculator`, Core.Contracts/Pricing; satır indirimi → vergi; dahil/hariç). Tek seferlik kalemlerin toplamı başlıkta (`netTotal/taxTotal/grossTotal`), dönemsel kalemler (`billingPeriod`: Monthly/Quarterly/Yearly) dönem başına özet JSON'da (`recurringSummary`); dönemsel tutar sözleşme süresiyle çarpılıp genel toplama eklenmez. Sözleşme tek para birimlidir. Açıklama satırı (`kind=Text`) tutar taşımaz.
- **İzinler:** `contracts.contracts.read`, `contracts.contracts.write`, `contracts.financials.read` (hassas alan: sözleşme bedeli, kalem fiyat/indirim ve tüm tutarlar; izni olmayan sözleşmeyi görür, tutarları görmez, gönderdiği fiyat yok sayılır). Hazır roller: "Sözleşme sorumlusu" (kendi kayıtları), "Sözleşme izleyici" (tutarsız okuma). Veri kapsamı sorumluya göredir; taraf ve kalemler üst sözleşmenin kapsamını izler. Özel alan (Y9a) sözleşmede açıktır; tür (`type`) düzenlenebilir listedir (`contracts.contract-type`).
- **Lookup'lar (ADR-0016):** `contracts.contract.party|person|owner|previous`, `contracts.contract-party.party|person`; kişi lookup'ı müşteri tarafına bağımlıdır ve kayıt sırasında sunucuda yeniden doğrulanır ("Kişi seçilen müşteriyle ilişkili değil").
- **Ekranlar:** `Sözleşmeler` (`/sozlesmeler`: hızlı görünümler "Sözleşmelerim", "İmza bekleyen", "Bitişi yaklaşan (90 gün)", "Bildirim süresi yaklaşan (30 gün)", "Taahhüdü geciken"; yürürlük ve tür süzgeci; sıralama; kaydedilmiş görünümler; CSV indir; kritik tarih sütunu), `Pano` (`/sozlesmeler/ozet`), `Sihirbaz` (`/sozlesmeler/sihirbaz`), sözleşme sayfası (`/sozlesmeler/yeni`, `/sozlesmeler/{id}`: genel bilgiler, taraflar ve kişiler, kapsam ve kalemler, tarihçe + işlem geçmişi sekmeleri; kaydedilmemiş değişiklik uyarısı; 409'da yenileme uyarısı).
- **Durum geçişleri (dilim 2):** yalnızca eylem uç noktaları `POST /api/contracts/contracts/{id}/send-to-review | mark-ready | reopen-draft | submit-for-approval | withdraw-approval | approve | reject-approval | cancel | revise` (gövde `version` zorunlu, `reason` ret/iptal/revizyonda zorunlu; çakışmada 409); `GET .../actions` yetkili eylemleri ve yapılamayanların nedenini verir. Yayıma hazır için müşteri, başlangıç ve bitiş (ya da belirsiz süreli) gerekir; onay yalnızca yayıma hazır içerikte; onay beklerken taslağa dönülmez; imzalı/yürürlükteki içerik taslağa dönmez, `revise` yeni sürüm açar. Onaylama ayrı izindir (`contracts.contracts.approve`); onaya gönderen kendi gönderdiğini onaylayamaz (ayar `contracts.approval.allow-self`, varsayılan hayır).
- **Sürümler:** onaya gönderimde içerik (başlık, taraflar, kalemler) `ContractVersions`'a JSON + SHA-256 ile dondurulur; onay/ret sürüme yazılır; onaylı/reddedilmiş içeriği düzenlemek için taslağa dönülünce eski sürüm `Superseded` olur ve sürüm numarası artar. `GET .../versions`, `.../versions/{no}` (finansal izni olmayana tutarlar maskeli), `.../versions/{no}/compare?with={no}` (`with=0` güncel taslak). **Süre aritmetiği** (`ContractPeriod`): on iki ay takvim ayıyla hesaplanır, ay sonu taşması bir sonraki ayın ilk gününe kayar (1 Mart + 12 ay → 29 Şubat artık yılda), bugün tenant saat dilimiyle bulunur.
- **Tekliften sözleşme (dilim 3):** `GET /api/contracts/from-quote/{quoteId}` (önizleme: teklif özeti, kalemler ve hangilerinin başka sözleşmede olduğu) ve `POST /api/contracts/from-quote/{quoteId}` (gövde: `type`, `startDate`, `termMonths`, `renewalMode`, `renewalPeriodMonths`, `noticePeriodDays`, `lineKeys`, `ownerId`). Teklif `IAcceptedQuoteSource` ile (CRM tablosuna bağlanmadan) okunur; yalnızca kabul edilmiş revizyon, CRM kapalıysa ya da teklif görünmüyorsa 404. İzin: `contracts.contracts.write` + `contracts.financials.read` (fiyatlar sözleşmeye sunucu yazar). Müşteri ve kişi ortak kayıt kimliğiyle (`PartyId`/`PersonId`) gelir. **Bire bir değil:** `lineKeys` ile kalem alt kümesi seçilerek bir tekliften birden çok sözleşme açılabilir; aynı teklif kalemi aynı anda yalnızca bir sözleşmede olur (mükerrer istek 409, yarışta filtreli benzersiz indeks `UX_ContractLines_SourceQuoteLine`; sözleşme iptalinde kalem serbest kalır). Kalem fiyatı teklifin indirim sonrası net birim fiyatıdır (sözleşme vergi hariç fiyatlanır, vergi satır başına); teklif ya da katalog sonradan değişse de sözleşme değişmez. `termMonths` + `startDate` verilirse bitiş takvim ayıyla hesaplanır. Sözleşmede kaynak izi tutulur (`sourceQuoteId/Number/RevisionNo/Sha256`, `sourceOpportunityId`; süzgeçler `sourceQuoteId`, `sourceOpportunityId`, `partyId`), tarihçe `CreatedFromQuote`. Tek işlemdir: kalem reddedilirse hiçbir şey yazılmaz. Ekran `/sozlesmeler/tekliften/{teklifId}` (kabul edilmiş teklif sayfasında "Sözleşme oluştur"); firma kartının Satış sekmesinde ve fırsat sayfasının Teklifler sekmesinde "Sözleşmeler" bölümü (modül kapalı/izin yoksa çizilmez). Sözleşme aktiviteye bağlanabilir (`IActivityLinkTarget`, `contracts.contract`; başlıkta yalnızca ad ve numara). **Form düzeni** `IModule.Forms` (`ContractsForms`) ile metadata'dan gelir; özel alan sözleşmede açıktır.
- **Şablon ve belge üretimi (dilim 4):** şablon düz metindir; HTML ve kod çalıştırılmaz. Yalnızca beyaz listedeki `{{değişken}}` yer tutucuları kabul edilir (`GET /api/contracts/templates/variables`): `sozlesme.*`, `musteri.*`, `hizmet_veren.unvan`, `tarih.bugun`; tek başına satırda blok değişkenler `kalem_tablosu`, `taraflar_listesi`, `imza_alani`, `sayfa_sonu`. Bilinmeyen değişken kaydetmede reddedilir; eksik veri belge üretimini 422 ile durdurur ve eksikleri listeler. Finansal değişkenler (`sozlesme.bedel`, toplamlar, `kalem_tablosu`) kullanan şablon ve belge `contracts.financials.read` ister. Şablon uç noktaları `/api/contracts/templates` (CRUD, `{id}/publish | archive | restore`, `{id}/versions`, `{id}/versions/{no}`, `GET /sample`); düzenleme (`contracts.templates.edit`) ve yayımlama (`contracts.templates.publish`) ayrı izinlerdir. Yayımlama şablonu değişmez bir sürüme dondurur (SHA-256); değişiklik yoksa 409; yayımlanmış ya da belgesi olan şablon silinemez; arşivli şablon salt okunurdur. Belge: `POST /api/contracts/contracts/{id}/documents/preview` ve `POST .../documents` (`contracts.documents.generate`), `GET .../documents` ve `GET .../documents/{belgeId}/file` (`contracts.documents.download`). Yalnızca **yayımlanmış şablon sürümünden** üretilir; sözleşme sürümü dondurulmuşsa donmuş içerikten, dondurulmamışsa güncel taslaktan ("taslak kopya" işaretiyle). Üretilen PDF (QuestPDF, Community lisansı) SHA-256 ile mühürlenir; şablon ya da müşteri kartı sonradan değişse de belge değişmez; üretim tarihçeye (`DocumentGenerated`) yazılır. Kurum unvanı/ayrıntı/alt not firma ayarlarındandır (`contracts.document.provider-*`, `footer-note`). Örnek hizmet sözleşmesi metni **ÖRNEK**tir, hukuki inceleme yapılmamıştır ve belgede ve önizlemede bu uyarı görünür. Ekranlar: `/sozlesmeler/sablonlar` (şablon listesi/düzenleyici/sürümler), sözleşme detayında **Belgeler** sekmesi (önizleme, üretme, indirme). Henüz yok: kurum logosu (tenant logo deposu yok), belge antivirüs taraması gerekmez (dosyayı sunucu üretir).
- **İç onay (dilim 5):** sözleşme onaya gönderilirken etkin **onay kuralları** sözleşmenin özetiyle eşleştirilir ve sonuç (kural adı, kural sürümü, adım, neden) sürüme **plan** olarak dondurulur; kural sonradan değişse de bekleyen onay eski planla yürür. Kural koşulları: toplam tutar, en yüksek kalem indirimi, süre (ay; belirsiz süreli sözleşme sonsuz sayılır), standart dışı madde işareti, en az risk düzeyi; tür ve para birimi yalnızca daraltır. Bir kuralın koşulları birlikte (VE), kurallar arasında biri yeter (VEYA); en az bir ölçüt zorunludur. Adımlar sırayla tamamlanır (sıralı), aynı adımdaki adlı onaylayıcıların hepsi onaylar (paralel); adsız adımda onay izni olan biri yeter; hiç kural eşleşmezse tek adsız adım vardır (gönüllü onay). Adım ve vekâlet hesabı CRM ile ortaktır (`ApprovalFlow`, Core.Contracts). Plan nedenleri tutar/yüzde içermez; finansal izni olmayan da okuyabilir. Sözleşmede iki gösterge alanı vardır: `hasNonStandardTerms` (standart dışı madde) ve `riskLevel` (Low/Medium/High); ikisi de dondurulan sürüme girer ve karşılaştırmada görünür.
  - **Karar eylemleri:** `POST .../contracts/{id}/approve | reject-approval | return-for-changes` (gövde `version` zorunlu; ret ve geri gönderme gerekçe ister). Karar yetkisi sunucuda denetlenir: adlı adımda yalnızca adı geçen kişi ya da etkin vekili; adımdaki payı zaten verilmişse ikinci karar verilemez (403); **dört göz:** onaya gönderen kendi gönderdiğini onaylayamaz/reddedemez (422, ayar `contracts.approval.allow-self` ile açılabilir) ve aynı sürümde önceki bir adımda karar veren kişi (ya da adına vekâlet edilen) sonraki adımı onaylayamaz. Son adım dışındaki onay sözleşmeyi onay bekler bırakır, kararı ve sıradaki adımı yazar. `return-for-changes` onay turunu bitirir, sözleşmeyi taslağa döndürür ve yeni revizyon açar (dondurulan sürüm geçersiz kalır). Her gönderim yeni bir **onay turu** açar (geri çekilip yeniden gönderilen sürümün eski kararları sayılmaz). Kararlar `ContractApprovalDecisions`'a değişmez satır olarak yazılır (kim, hangi adım, kimler adına, gerekçe) ve tarihçeye `ApprovalStepApproved`, `Approved`, `ApprovalRejected`, `ApprovalReturned` olarak girer. İçerik bütünlüğü: onaya giden içerik dondurulmuştur ve onay beklerken ya da onaylıyken düzenlenemez; her içerik değişikliği için önce taslağa dönülür, bu da önceki onayı geçersiz kılar (`ApprovalInvalidated`).
  - **Uç noktalar:** `GET .../contracts/{id}/approval` (plan, adımlar, kararlar, geçerli kullanıcının karar verip veremeyeceği ve nedeni, hedef süre, gecikme), `GET /api/contracts/approvals/inbox?mine=true|false` (onay iş listesi; `contracts.contracts.approve`), kurallar `/api/contracts/approval-rules` ve vekâletler `/api/contracts/approval-delegations` (`contracts.approvals.manage`, denetim kaydına yazılır). **Vekâlet:** vekil, vekâlet verenin adına karar verir; vekilin onay iznine kendisinin sahip olması gerekir, karar "vekâleten" işaretlenir ve vekâlet bitse de geçmiş karar değişmez. **Hedef süre:** onaya gönderimde ayardaki saat (`contracts.approval.due-hours`, varsayılan 72, 0 kapalı) eklenir; geçen onay iş listesinde ve sözleşmede "Gecikti" görünür, kararı engellemez. Ekranlar: `/sozlesmeler/onaylar` (iş listesi, satır içi karar), `/sozlesmeler/onay-kurallari` (kurallar ve vekâletler), sözleşme detayında **Onay** sekmesi. **Henüz yok:** gecikme için e-posta hatırlatması ve yöneticiye eskalasyon (dilim 8'deki zamanlanmış iş altyapısıyla gelecek); onay kuralının sözleşme dışı tetikleyicileri (ör. yenilemede fiyat değişimi, dilim 8).
- **İmza (dilim 6):** imza isteği, onaylı ve yayıma hazır sözleşmenin güncel sürümünün **kesin belgesine** (dondurulmuş sürümden üretilmiş, örnek olmayan PDF) bağlıdır; belgenin SHA-256 özeti istekle sabitlenir. İmzacılar sıralı ya da paralel imzalar; her imzacının sırası, sıfatı, iç/dış türü (iç: firma üyesi; dış: ad ve isteğe bağlı e-posta) ve zorunluluğu vardır; isteğe bağlı imzacının reddi isteği bozmaz, zorunlu imzacının reddi isteği reddeder ve diğer açık imzacıları iptal eder. İstek durumu ayrı bir alandır (`ContractSignatureRequests`), sözleşmenin imza durumu ondan türetilir; zorunlu imzacıların hepsi imzalayınca sürüm `Signed` olur, `EffectiveVersionNo` yazılır ve yürürlük durumu tenant gününe göre belirlenir (başlangıç gelecekteyse `AwaitingStart`). Süre dolumu, iptal ve ret sonrası yeni istek açılabilir (aynı anda tek açık istek: filtreli benzersiz indeks).
  - **İki yöntem, eşdeğer değil:** **Manuel**: imzalı belge taraması (PDF/PNG/JPEG, en fazla 10 MB, dosya imzası denetlenir; antivirüs taraması yoktur, dosya her zaman indirme olarak ve `nosniff` + sandbox başlığıyla sunulur) yüklenir ve doğrulama izni olan yetkili kaydeder; güvence düzeyi `ManualScan` ("ıslak imza taraması, yetkili doğruladı"; kimlik ve yetki doğrulaması Modulix dışındadır). Doğrulayan kayda yazılır; iç imzacı kendi imzasını doğrulayamaz; sıralı kipte sıra denetlenir. **Sağlayıcı**: imza sağlayıcıdan olayla gelir; güvence düzeyi `ProviderElectronic`/`ProviderQualified` yalnızca gerçek sağlayıcı bildirirse yazılır ve Modulix bunu doğrulamaz, sağlayıcıya güvenir. Simülasyon her zaman `SimulatedElectronic` yazar (simülasyon "nitelikli" bildirse bile) ve ekranlarda ve belgede "hukuki değeri yok" olarak işaretlidir.
  - **Sağlayıcı arayüzü:** `IContractSignatureProvider` (istek oluştur/iptal et) ve ayarla seçilen sağlayıcı (`contracts.signature.provider`: `none` ya da `simulation`; varsayılan `none`). Gerçek sağlayıcı eklemek arayüzü uygulayıp host'ta o sağlayıcının webhook doğrulayıcısını bağlamaktır. **Gerçek bir sağlayıcı entegrasyonu bu dilimde yoktur**; yalnızca arayüz ve ağ çağrısı yapmayan, kimseye istek ya da e-posta göndermeyen simülasyon vardır.
  - **Webhook:** `POST /api/public/contracts/signature/{sağlayıcı}/events` (oturumsuz). Kimlik doğrulama HMAC-SHA256 imzasıdır: `X-Modulix-Timestamp` (unix saniye, 5 dakika tolerans: tekrar saldırısını sınırlar) ve `X-Modulix-Signature: v1=hex(HMAC(gizli, "{zaman}.{gövde}"))`. Gizli anahtar yapılandırmadan gelir (`ContractSignature:Simulation:WebhookSecret`, ortam değişkeni `ContractSignature__Simulation__WebhookSecret`); yoksa uç nokta o sağlayıcı için kapalıdır (404). Tenant, isteğin sağlayıcı referansından (`{tenant:N}.{rastgele}`) çözülür ve istek `contracts.signature-webhook` sistem kimliğiyle kendi tenant kapsamında çalışır. Olay gövdesi `{ eventId, sequence, type, reference, signatoryPosition, occurredAt, assurance, note }`; `type`: Sent, Viewed, Signed, Declined, Expired. **Idempotency:** aynı `eventId` bir kez uygulanır (yinelenen 200 `Duplicate`); **sıra:** `sequence` son uygulanandan büyük olmalıdır (küçük olan `OutOfOrder` kaydedilir, uygulanmaz); kapanmış isteğe gelen olay `Ignored`; sırasız ya da süresi dolmuş imza `Rejected`. Hepsi olay günlüğüne yazılır. 16 KB gövde ve hız sınırı uygulanır.
  - **Uç noktalar:** `GET/POST /api/contracts/contracts/{id}/signature` (özet / başlat), `POST .../signature/signatories/{imzacıId}/manual | decline | remind`, `POST .../signature/cancel | expire | simulate`, `GET .../signature/files/{dosyaId}` (kanıt). İzinler: başlatma, ret, hatırlatma, iptal ve simülasyon `contracts.signatures.manage`; manuel imzayı doğrulama `contracts.signatures.verify` (ayrı yetki); kanıt indirme `contracts.documents.download`; sağlayıcı olayları `contracts.signatures.provider-events` (yalnızca sistem kimliği). Hatırlatma yalnızca **kaydedilir** (saatte en fazla bir; Modulix müşteriye e-posta ya da bildirim göndermez). Süresi dolan istek işlem kabul etmez; `expire` onu sonlandırır (zamanlanmış iş dilim 8'de bu servise bağlanacak). Sözleşme iptalinde açık istek de iptal edilir; imza başarısız olduktan sonra taslağa dönüş imza durumunu sıfırlar.
  - **Ekranlar:** sözleşme detayında **İmza** sekmesi (istek başlatma, imzacı durumları, manuel imza kaydı, simülasyon, olay günlüğü, kanıt indirme) ve `/sozlesmeler/imzalar` (imza durumuna göre sözleşmeler). **Kapsam dışı:** Modulix tarafından barındırılan müşteri imza sayfası/bağlantısı (dış imzacı ya imzalı belgeyi manuel yollar ya da sağlayıcının kendi sayfasında imzalar; bağlantının kimlik doğrulama sayılması imza yöntemine bağlıdır ve sağlayıcıya aittir).
- **Taahhütler (dilim 7):** sözleşmeden doğan yükümlülükler sektörden bağımsız tanımlanır (kategori Y9b listesidir: teslimat, eğitim, kurulum, belge sağlama, raporlama, hizmet seviyesi, ödeme, diğer). Taahhüdün başlığı, açıklaması, yükümlü tarafı (hizmet veren, müşteri, her ikisi), sorumlu kullanıcısı, takvimi (tek seferlik ya da dönemsel: haftalık/aylık/üç aylık/yıllık, ilk son tarih, tekrar bitişi), ölçütü (ad, yön en az/en çok/tam, hedef, tolerans, birim), tolerans süresi (gün), eskalasyon (ihlalden gün sonra, eskalasyon kullanıcısı), bağımlı olduğu taahhüt ve sonuç maddesi atfı vardır. **Ceza ya da finansal sonuç uygulanmaz**; sonuç maddesi yalnızca nottur. Her dönem ayrı bir gerçekleşme satırıdır (`ContractCommitmentOccurrences`: durum Open, Fulfilled, Breached, Waived, Cancelled); tamamlanmış, ihlal edilmiş ya da muaf satır üzerine yazılmaz. Dönemler tekrar kuralından türetilir: aylık/üç aylık/yıllık dönemlerde gün ilk son tarihe bağlıdır ve ay sonuna kırpılır, kaymaz (31 Ocak → 28 Şubat → 31 Mart); bitişi olmayan (belirsiz süreli sözleşmede açık uçlu) dönemsel taahhüt kayan 12 aylık ufukla üretilir, (taahhüt, sıra) benzersiz indeksi tekrar üretimi mükerrer yapmaz. Gerçekleşmesi kaydedilmiş taahhütte takvim ve ölçüm değiştirilemez, taahhüt silinemez (iptal edilir); başlık, sorumlu ve not düzenlenebilir.
  - **Kayıt ve ölçüm:** gerçekleşme `POST .../commitments/{id}/occurrences/{occurrenceId}/complete` ile kaydedilir (tamamlanma tarihi gelecekte olamaz; ölçümlü taahhütte gerçekleşen değer zorunlu; isteğe bağlı kanıt dosyası PDF/PNG/JPEG, en fazla 10 MB, dosya imzası denetlenir, indirme ayrı izin ister ve ek olarak sunulur). Hedef tolerans dahil karşılanmazsa ya da son tarih + tolerans günü geçtikten sonra tamamlanırsa gerçekleşme **ihlal** (`Breached`, tamamlanma tarihi dolu) olarak kaydedilir; ihlal kaydı korunur. Bağımlı taahhüt, bağlı olduğu taahhüdün aynı ya da daha eski tarihli gerçekleşmeleri tamamlanmadan kaydedilemez (409; muaf ve iptal engel sayılmaz); bağımlılık aynı sözleşmeden olmalı, kendine ya da döngüye işaret etmemelidir.
  - **İhlal, takip aktivitesi ve eskalasyon:** `POST .../commitments/evaluate` değerlendirme turudur (zamanlanmış işin çalıştıracağı aynı servis; dilim 8): son tarih + tolerans geçmiş açık gerçekleşmeleri ihlal eder, ihlalden sorumluya **takip aktivitesi** açar (aktivite alanı CRM'e aittir; modül `IFollowUpActivities` bağlantı sözleşmesini kullanır, CRM uygular), eskalasyon süresi dolmuşsa eskalasyon kullanıcısına ikinci aktivite açar ve kayan ufku genişletir. Tekrar çalıştırmak güvenlidir (ihlal, aktivite ve eskalasyon bir kez). Aktivite modülü bu tenant için kapalıysa durum "kullanılamıyor"dur; açılamazsa ("başarısız", örn. tamamlayanın CRM yazma yetkisi yoksa) bir sonraki yetkili tur yeniden dener (en az bir kez garanti). İhlal kaydı aktiviteden bağımsızdır. Muafiyet (`.../waive`, gerekçe zorunlu, ayrı izin) ihlal sayılmaz; iptal (`.../cancel`, gerekçe zorunlu) açık gerçekleşmeleri iptal eder.
  - **İzinler:** tanımlama, düzenleme, iptal ve değerlendirme `contracts.commitments.write`; gerçekleşme kaydı `contracts.commitments.complete`; muafiyet `contracts.commitments.waive`; kanıt indirme `contracts.documents.download`; görünürlük sözleşmeyi izler. Taahhüt kaydı tanım alanları kayıt boru hattından (audit, outbox) yazılır; gerçekleşme değişiklikleri taahhüt güncellemesiyle aynı işlemde, sürüm denetimli yazılır ve sözleşme tarihçesine (`CommitmentDefined/Completed/Breached/Waived/Cancelled/Escalated`) işlenir.
  - **Uç noktalar:** `/api/contracts/commitments` (CRUD), `GET .../commitments/occurrences?contractId=&partyId=&mine=&status=Overdue|Open|Breached|Fulfilled|Waived&dueFrom=&dueTo=&includeClosed=`, `POST .../commitments/{id}/occurrences/{occurrenceId}/complete | waive`, `POST .../commitments/{id}/cancel`, `POST .../commitments/evaluate`, `GET .../occurrences/{occurrenceId}/files/{fileId}`. **Ekranlar:** sözleşme detayında **Taahhütler** sekmesi (tanım, dönem tablosu, tamamlama, muafiyet, iptal, değerlendirme), `/sozlesmeler/taahhutler` (iş listesi: gecikmiş/açık/ihlal; "yalnızca sorumlusu olduklarım"), firma kartında "Aktif taahhütler ve yaklaşan tarihler".
- **Yenileme, fesih ve zamanlanmış işler (dilim 8):** sözleşmede son bildirim tarihi bitiş − bildirim süresinden türetilir; her dönem için tek karar vardır (`ContractRenewals`: yenileme taslağı açıldı, otomatik uzatıldı, yenilenmeyecek). Zamanlanmış iş (`ContractJobsWorker`, tenant başına `sp_getapplock`, `contracts.scheduler` sistem kimliği; `ContractJobs:WorkerEnabled` / `PollIntervalSeconds`; elle tetikleme `POST /api/contracts/scheduler/run`, `contracts.renewals.manage`) sırayla otomatik uzatma, planlı fesih, başlangıcı gelen sözleşmeyi aktifleştirme / bitişi geçeni süresi doldu yapma, yenileme hatırlatması ve eskalasyon, imza süre dolumu, onay gecikmesi hatırlatması ve taahhüt değerlendirmesi yapar; tekrar çalıştırmak güvenlidir (hatırlatma (sözleşme, dönem, tür, eşik) başına bir kez), kesinti sonrası birikmiş eşiklerden yalnızca en dar olanı için aktivite açılır, geniş olanlar "atlandı" yazılır. Hatırlatma eşikleri firma ayarıdır (`contracts.renewal.reminder-days`, varsayılan 90,60,30,7); aktivite sorumluya, eskalasyon sözleşmedeki eskalasyon kullanıcısına açılır; **müşteriye bildirim gitmez**. **Otomatik uzatma varsayılan kapalıdır**: yalnızca yenileme yöntemi "otomatik" ve firma ayarı açıksa (`contracts.renewal.allow-auto`), imzalı yürürlükteki sözleşmede, bildirim süresi geçip dönem bitince, takvim ayıyla (365 gün değil) uzatır; fiyat ya da ceza uygulanmaz. `GET .../contracts/{id}/renewal` (dönem, eşikler, karar ve hatırlatma geçmişi), `POST .../renewal/draft` (kaynak sözleşmenin kopyasını taslak açar, önceki sözleşme bağı kurar, aynı dönem için mükerrer taslak üretmez; fiyat değişikliği taslakta yapılır ve normal onaya girer; `contracts.contracts.write` + `contracts.financials.read` + `contracts.renewals.manage`), `POST .../renewal/decline` (neden listesi), `POST .../terminate` (ayrı kritik izin `contracts.contracts.terminate`; bugün ya da geçmiş tarih anında, gelecek tarih planlı; bildirim süresinden kısa fesih onay ister; etkin taahhütler kapatılır; ceza/tazminat hesaplanmaz), `GET .../chain` (yenileme zinciri), `GET /api/contracts/renewals/calendar?days=`. Ekranlar: sözleşme detayında **Yenileme** sekmesi (tarihler, otomatik uzatma durumu, karar/hatırlatma geçmişi, zincir, taslak/yenilememe/fesih), `/sozlesmeler/yenileme` (takvim). Zamanlanmış işin aktiviteleri sözleşme kaydına bağlanmaz (konuda numara ve başlık vardır); ek protokol `revise` ile yapılır, ayrı tür yoktur.
- **Ekran tamamlama (dilim 9):** liste uç noktası `sort` süzgecini kabul eder (oluşturma, başlık, numara, başlangıç, bitiş, son bildirim; başına `-` azalan; **tutar sütunları sıralanamaz**) ve `commitmentOverdue=true|false` (açık ihlalli taahhüdü olan sözleşmeler); `signatureStatus` virgülle ayrılmış birden çok durum alır. **Kaydedilmiş görünümler** (`/api/contracts/saved-views`, `contracts.ContractSavedViews`, RLS'li): yalnızca sahibine görünür, ad kullanıcı içinde tekil, en fazla 25; süzgeç metni yalnızca bilinen anahtar ve değerleri kabul eder, göreli tarihli hızlı görünümler `preset` ile saklanır; **görünüm yetki taşımaz** (liste açılınca yetki ve veri kapsamı yeniden uygulanır). **Pano** (`GET /api/contracts/dashboard`, `/sozlesmeler/ozet`): liste süzgeçleriyle aynı süzgeçlerle sayılan sayaçlar (tıklanınca listeyi açar), türe göre dağılım, para birimine göre ayrı tutarlar (yalnızca `contracts.financials.read`), 90 gün içindeki son bildirim/bitiş tarihleri. **CSV dışa aktarma** (`GET /api/contracts/contracts/export`, ayrı izin `contracts.contracts.export`; süzgeçler liste ile aynı, en fazla 5000 satır, tutar sütunları yalnızca tutar iznine sahipte, formül karakterleri etkisizleştirilir, müşteri adı ortak lookup'tan, çıkış denetim kaydına yazılır; durum/tür anahtar olarak yazılır). **Sihirbaz** (`/sozlesmeler/sihirbaz`, `?id=` ile taslağa devam): kaynak (boş / şablondan / kabul edilmiş tekliften) → müşteri ve taraflar → kalemler → tarihler ve yenileme → taahhütler → önizleme ve gönderim; taslak her adımda mevcut uç noktalar ve kurallarla sunucuya yazılır, eksik ön koşullar `actions` nedenleriyle gösterilir. Sözleşme ayarları ortak firma ayarlarındadır (menüde "Sözleşme ayarları" → `yonetim/ayarlar?grup=Sözleşmeler`). **Yapılmadı:** toplu işlemler, paylaşılan kayıtlı görünüm, ay ızgarası takvimi (yenileme takvimi dilim 8'dedir), sihirbazda dönemsel taahhüt/özel alan.
- **Operasyon işi (dilim 4):** devir operasyon tarafından kabul edilince işler aynı işlemde ve bir kez üretilir (`orders.jobs.strategy`: `PerKind` varsayılan, `Single`, `PerLine`; `orders.jobs.service-after-delivery`). `GET /api/orders/operation-jobs` (süzgeçler: `orderId`, `status` (virgülle çoklu), `kind`, `responsibleUserId=me`, `unassigned=true`, `overdue=true`, `plannedFrom|To`, `sort`), `GET /api/orders/operation-jobs/{id}/detail` (kalemler, görevler, bağımlılıklar, yapılabilir eylemler, geçmiş, ilerleme), `POST .../{id}/assign|start|complete|cancel` (kayıt sürümü ister; atama kullanıcı ve/veya ekip; iptalde gerekçe), `POST|DELETE .../{id}/dependencies`, `POST /api/orders/orders/{id}/jobs` (elle iş; devir kabul edilmiş olmalı), `/api/orders/operation-tasks` (görevler; şablon görevi silinmez). Atanacak sorumlu/ekip yoksa iş \"Atama bekliyor\" durumunda görünür. Başlatma: atanmış, bağımlı işler tamamlanmış, sipariş onaylı; tamamlama: zorunlu görevler bitmiş. Sipariş iptalinde açık işler iptal edilir. İzinler: `orders.jobs.assign`, `orders.jobs.manage` (rol şablonu `orders.operations`). Ayar `orders.jobs.unassigned-hours` (varsayılan 24; 0 kapalı): atama bekleyen iş için devri kabul edene, geciken iş için sorumluya iş başına bir kez takip aktivitesi açılır.
- **Henüz yok (sonraki dilimler):** sipariş/başlangıç devri, müşteri başlangıcı, destek/SLA ve faturalama devri (hedef modül yok); gerçek imza sağlayıcısı. Ayrıntı ve dilim planı ADR-0022'de. Kabul kriterleri, çapraz modül akışları ve açık riskler: [Sözleşme yönetimi teslim raporu](docs/sozlesme-yonetimi-teslim-raporu.md).

## Sipariş modülü ([ADR-0023](docs/adr/0023-siparis-ve-satis-devri.md)) — dilim 1-6 (EPIC 8 kısmen)

Modül anahtarı `orders`, şema `orders`; sektörden bağımsızdır, CRM tablolarına bağlanmaz ve kabul edilmiş teklifi yalnızca `IAcceptedQuoteSource` (Core.Contracts) ile okur. Müşteri ve kişi ortak kayıttır. **Sipariş tutarı tahsilat, fatura ya da gelir değildir**; finans, stok ve muhasebe modülleri yoktur.

- **Uç noktalar:** `/api/orders/orders` ve `/api/orders/order-lines` (liste, detay, taslak düzenleme; genel uçtan sipariş oluşturulamaz ve silinemez), `GET /api/orders/orders/{id}/history`, `GET|POST /api/orders/from-quote/{quoteId}` (önizleme ve oluşturma). Liste süzgeçleri: `partyId`, `personId`, `sourceQuoteId`, `sourceOpportunityId`, `ownerId=me`, `status` (virgülle çoklu), `handoverStatus`, `fulfillmentStatus`, `currency`, `deliveryFrom|To`, `overdue=true`, `handoverPending=true`, `sort`.
- **Tekliften dönüşüm:** yalnızca `Accepted` teklif (kaynak, kabul edilmemiş/reddedilmiş/iptal/kapsam dışı teklifi vermez → 404). Geçerlilik **kabul anında** denetlenmiştir; dönüşümde yeniden denetlenmez. Varsayılan teklifin tamamıdır (`Full`); kalem bazında miktar `Partial` ayrı ve açık seçenektir. Kalem tüketim defteri (`orders.QuoteLineConsumptions`) kabul edilen/dönüştürülen miktarı tutar; `CHECK (Converted <= Accepted)`, sürüm belirteci ve benzersiz anahtar çift tıklamada ve eşzamanlı istekte tek sonuç üretir (ikinci istek 409, yanıt mevcut siparişi söyler). Son kalan miktarda tutar kalan tutardır (kuruş farkı kalmaz).
- **Snapshot:** kalemler (kod, ad, miktar, net birim fiyat, vergi, tutarlar), para birimi/kur, ödeme-teslimat-ticari koşullar, müşteri ünvanı, fatura ve teslimat adresi metin kopyası siparişe yazılır; sonradan katalog, müşteri kartı ya da teklif değişse de sipariş değişmez. Kabul kanıtı: yöntem (`Portal` belge özetine bağlı, `Manual` belge kanıtı yok), kabul eden, zaman, belge SHA-256, geçerlilik.
- **Üç ayrı durum alanı:** ticari (`Draft|PendingApproval|Approved|Cancelled|Closed`), devir (`NotStarted|…|Accepted`), gerçekleşme (`NotStarted|Planned|Partial|Completed`). Oluşturulan sipariş `Draft/NotStarted/NotStarted`tır; ticari durum dilim 2 geçişleriyle ilerler, devir ve gerçekleşme durumları sonraki dilimlerdedir. Ticari alanlar yalnızca taslakta düzenlenir.
- **İzinler:** `orders.orders.read|create|write|approve|cancel|close|force-close`, `orders.financials.read` (hassas alan: tutarlar, kalem fiyatları ve talep tutar farkı; tekliften oluşturma da bunu ister). Rol şablonları: `orders.sales` (kendi kayıtları), `orders.approver`, `orders.closer`, `orders.viewer` (tutarsız). Lookup'lar: `orders.order.person|owner`.
- **Ekranlar:** `/siparisler` (liste, hızlı görünümler, arama, sıralama), `/siparisler/tekliften/{teklifId}` (önizleme, eksik bilgi uyarıları, kısmi dönüşüm miktarları, planlama), `/siparisler/{id}` (durum işlemleri, özet, kabul kanıtı, kalemler, koşullar, değişiklik talepleri, geçmiş); kabul edilen teklifin sayfasında "Sipariş oluştur".
- **Durum geçişleri (dilim 2, sunucuda doğrulanır; `POST /api/orders/orders/{id}/{eylem}` kayıt sürümünü ister, `GET .../actions` yapılabilirliği ve nedenini söyler):** `submit-for-approval` (Taslak → Onay bekliyor; en az bir etkin kalem), `withdraw-approval` (→ Taslak, gerekçeli), `approve` (→ Onaylandı; `orders.orders.approve`; onaya gönderen kendi siparişini onaylayamaz, ayar `orders.approval.allow-self` ile gevşer), `return-to-draft` (onaylayan, gerekçeli), `cancel` (Taslak/Onay bekliyor/Onaylandı → İptal edildi; `orders.orders.cancel`, gerekçeli), `close` (Onaylandı → Kapatıldı; gerçekleşme `Completed` olmalı; `orders.orders.close`), `force-close` (kalan yükümlülük varken; `orders.orders.force-close`, gerekçeli). İptal siparişin **teslim edilmemiş** kısmını sonlandırır: teslim edilen miktar ve kayıtları korunur, iptal edilen miktar teklif kalemi tüketim defterinden serbest kalır (aynı kalem yeniden siparişe alınabilir), bekleyen değişiklik talebi geri çekilir; iptal iade ya da fatura değildir. Kalemin kopyalanmış tutarı değişmez; etkin miktar `quantity - cancelledQuantity`.
- **Değişiklik talebi (dilim 2):** onaylanmış siparişin ticari alanları yerinde değişmez. `POST /api/orders/orders/{id}/change-requests/preview|(boş)` talebi önizler/açar (gerekçe zorunlu; başlık alanları: adres, lokasyon, planlanan tarihler, ödeme/teslimat/ticari koşullar, taahhütler, operasyon notları; kalem: yalnızca miktar azaltma ve planlanan tarih), `GET .../change-requests` listeler, `POST /api/orders/change-requests/{id}/approve|reject|withdraw`. Etki özeti (operasyon, teslimat, sözleşme, tutar farkı; tutar yalnızca `orders.financials.read` ile) talep anında hesaplanıp saklanır. Onay tek işlemde uygular; sipariş başına tek bekleyen talep vardır; talebi açan kişi karara bağlayamaz (ayarla gevşer).
- **Satış devri (dilim 3):** `GET|POST /api/orders/orders/{id}/handover` (sipariş başına tek kayıt; açılışta varsayılan kontrol listesi), `GET /api/orders/handovers/{id}/detail` (alanlar, kontrol listesi, eksik bilgi listesi, yapılabilir eylemler, geçmiş), `PUT /api/orders/handovers/{id}` ve `/api/orders/handover-items` (kontrol listesi; varsayılan madde silinmez), `POST /api/orders/handovers/{id}/send|request-info|accept` (kayıt sürümü ister; bilgi isteği ve bilgi sonrası yeniden gönderimde not zorunlu; kabulde sorumlu operasyon kullanıcısı atanabilir). Sunucu zorunlu bilgi ve kontrol listesini denetler (eksik → 409 ve ilk eksik söylenir); gönderim yalnızca Hazır devirle ve onaylanmış siparişle; gönderilen/kabul edilen devir değişmez. İzinler: `orders.handovers.write|send|accept` (rol şablonları `orders.sales`, `orders.operations`). Ayarlar: `orders.handover.accept-due-days` (varsayılan 2), `orders.handover.wait-hours` (varsayılan 48; 0 kapalı). Zamanlanmış iş `OrderJobs:WorkerEnabled` (varsayılan `true`) ve `OrderJobs:PollIntervalSeconds` (varsayılan 900) ile yapılandırılır; kabulü bekleme süresini aşan devir için satış sorumlusuna tur başına bir kez takip aktivitesi açar.
- **Teslimat ve hizmet başlangıcı (dilim 5):** `GET /api/orders/orders/{id}/fulfillment` (ürün kalemi özeti: sipariş/etkin/teslim edilen/kalan/planlı; teslimatlar ve eylem durumları; hizmet kalemleri, engeller ve eylemler), `POST /api/orders/orders/{id}/deliveries` (kalan miktarı aşmayan plan), `POST /api/orders/deliveries/{id}/deliver|fail|cancel|reschedule` (kayıt sürümü ister; teslimde teslim alan kişi zorunlu, başarısız/iptalde gerekçe, yeniden planlamada gerekçe ve yeni tarih; fazla teslimat reddedilir), `PUT /api/orders/deliveries/{id}/evidence?fileName=` (ham gövde, PDF/PNG/JPEG, en çok 2 MB, teslimat başına 10) ve `GET .../evidence/{kanitId}` (`no-store`, `nosniff`, indirme yetkisi ve kapsamdan geçer), `POST /api/orders/orders/{id}/service-starts` ve `POST /api/orders/service-starts/{id}/start|confirm|complete` (başlangıç ön koşullar eksikse reddedilir; başlangıç tamamlanma sayılmaz). Siparişin gerçekleşme durumu bunlardan türetilir (Planlandı / Kısmen / Tamamlandı) ve normal kapatma Tamamlandı ile mümkündür. İzin `orders.fulfillment.record`. Ekran: `/siparisler/{id}/teslimat`.
- **Özet göstergeler (dilim 6):** `GET /api/orders/summary` yalnızca sayı döndürür (devir bekleyen, onay bekleyen, kısmen gerçekleşen, geciken sipariş; atanmamış ve geciken iş; açık ve geciken teslimat; geciken hizmet başlangıcı; ortalama devir kabul süresi). Sayılar kullanıcının izni ve veri kapsamıyla sınırlıdır, tutar toplanmaz. Ekran `/siparisler/ozet`; firma kartı ve fırsat ekranı ilişkili siparişleri, sipariş detayı teslimat özetini ve bağlı aktiviteleri gösterir.
- **Henüz yok:** onboarding, destek, finans/stok/lojistik bağlantıları, istisnai dönüşüm, operasyon işine belge, ekip/business unit aktarımı. Ayrıntı ve kabul senaryosu eşlemesi için ADR-0023 bölüm 5. Sözleşme bağlantısı kimlik+numara referansıdır (doğrulanmaz); genel dosya deposu (Ç4) olmadığından teslim kanıtı için sınırlı tablo planlanmıştır.

## Destek modülü ([ADR-0024](docs/adr/0024-destek-ve-sikayet-yonetimi.md)) — dilim 1-6 (EPIC 10 kısmen)

Modül anahtarı `support`, şema `support`; sektörden bağımsızdır, **CRM kapalıyken de çalışır** (müşteri ve kişi ortak kayıttır: `core.Parties`/`core.Persons`) ve diğer modüllerin tablolarına bağlanmaz. Talep, aktivite (görev/görüşme) değildir; aktivite talebe `IActivityLinkTarget` ile bağlanır (aktivite altyapısı CRM'e ait olduğundan yalnızca bu bağlantı CRM ister).

- **Uç noktalar:** `/api/support/tickets` (liste, detay, oluştur, düzenle; silme yok), `/api/support/queues`, `/api/support/categories`, `GET /api/support/summary` (sayılar), `GET /api/support/tickets/{id}/actions|history|messages`, `POST /api/support/tickets/{id}/messages` (`kind`: `reply` müşteriye yanıt, `customer-message` müşteriden gelen mesaj, `note` iç not). Liste süzgeçleri: `partyId`, `personId`, `categoryId`, `queueId`, `ownerId=me`, `status` (virgülle çoklu), `priority`, `channel`, `typeKey`, `number`, `parentTicketId`, `open`, `unassigned`, `awaitingFirstResponse`, `search`, `sort`.
- **Durum makinesi (sunucuda uygulanır):** Yeni → Sınıflandırmada → Atandı → İşlemde → (Müşteriden bilgi bekleniyor | İç ekip bekleniyor) → **Çözüldü** → **Kapandı**; Yeniden açıldı ve İptal edildi ayrı durumlardır. Çözüldü ile Kapandı aynı anlama gelmez. Geçişler yalnızca `POST /api/support/tickets/{id}/{triage|assign|take|transfer|start|wait-customer|wait-internal|resume|resolve|close|reopen|cancel|set-priority}` eylemleridir (kayıt sürümü ister; desteklenmeyen geçiş 409, eksik gerekçe/çözüm alanı 422). Genel `PUT` durum, sorumlu, kuyruk, öncelik ve çözüm alanlarını yok sayar. Çözümde çözüm kodu ve açıklaması zorunludur; şikâyet türünde kök neden ve düzeltici aksiyon da (ayar `support.complaint.require-root-cause`). Kapanan talep `support.reopen.window-days` (varsayılan 7) içinde gerekçeyle yeniden açılır; pencere dışında ilişkili yeni talep açılır. Çözülmüş talebe gelen müşteri mesajı talebi yeniden açar.
- **Öncelik ve yönlendirme:** öncelik tenant başına yönetilebilir etki × aciliyet matrisinden hesaplanır (`GET|PUT /api/support/priority-matrix`, 9 hücre eksiksiz; kayıt yoksa varsayılan matris; değişiklik yalnızca yeni ya da düzenlenen talepleri etkiler); elle değişiklik `support.tickets.priority` ve gerekçe ister ve etki/aciliyet düzenlemesiyle sessizce ezilmez. Yönlendirme (yalnızca talep açılırken): açık kuyruk/sorumlu (yetkiyle) → **yönlendirme kuralları** (`/api/support/routing-rules`, `support.settings.manage`; koşul: kanal, tür, öncelik, kategori, müşteri; etkin kurallardan sırası küçük olan, eşit sırada daha çok koşulu olan, sonra ad ve kimlik; olay tarihçede "Yönlendirme kuralıyla yönlendirildi") → kategori varsayılan kuyruğu → üst kategori → varsayılan kuyruk → kuyruksuz. `POST /api/support/routing/preview` hiçbir şey yazmadan eşleşen kuralı gösterir. Kuyruk ile sahiplik ayrıdır; atanmamış talepler kuyrukta herkese görünür.
- **Çözüm derinliği (dilim 3):** kategori `requiredFields` ile açılışta zorunlu alanlar tanımlar (açıklama, kişi, başvuran e-postası/telefonu, olay tarihi, beklenen sonuç; üst kategoriden devralınır, iş akışı eylemlerini engellemez). `GET /api/support/tickets/duplicates` aynı müşteri ya da başvuran e-posta/telefonuyla konusu benzer (≥ 0,5) açık talepleri çağıranın görünürlüğü içinde önerir; uyarıdır, engellemez. `POST /api/support/tickets/{id}/merge` (`support.tickets.merge`, gerekçe zorunlu) mükerrer talebi aynı müşterinin açık hedefine birleştirir: kaynak `Merged` son durumuna geçer, geçmiş, mesajlar ve dış anahtar korunur, mesajlar özgün zamanıyla hedefe kopyalanır; geri alınamaz. Alt işler (`/api/support/tickets/{id}/tasks`, `.../complete|reopen`) talep içi yapılacaklardır; engelleyici açık alt iş çözmeyi/kapatmayı reddeder. Müşteri teyidi (`customer-confirmation` mesajı) çözülmüş talebi kapatır; ayar `support.auto-close-days` (0 = kapalı) süresi dolan çözülmüş talepleri zamanlayıcı bir kez kapatır. Ekranlar: `/destek/yonlendirme` (matris, kurallar, kural denemesi), talepte alt iş ve birleştirme panelleri, yeni talepte mükerrer uyarısı.
- **İç not ayrımı:** iç not müşteriye hiçbir yoldan gitmez; veritabanı `CHECK` iç görünürlüğün dış kanalda saklanmasını engeller, mesajlar genel kayıt uçlarında yoktur, iç not `support.internal.read` olmayana dönmez, tarihçe ve arama gövde içermez. Dış yanıt e-postası kuyruğa alınır (`Queued` müşteriye ulaştı demek değildir; geçersiz adres `Failed`). İlk insan yanıtı (otomatik mesaj, iç not, müşteri mesajı ve başarısız gönderim sayılmaz) `firstResponseAt` olarak saklanır.
- **Tekrar koruması:** oluştururken `clientKey` verilirse aynı anahtarla ikinci istek 409 alır (tenant kapsamlı filtreli benzersiz indeks yarışta da korur).
- **SLA ve eskalasyon (dilim 2):** politika (`/api/support/sla-policies`, `support.sla.manage`): kısıtlar (tür, kategori, öncelik, müşteri), ilk yanıt ve çözüm hedefi (dk), takvim, bekleme kuralları (müşteri beklemesi durdurur; iç ekip beklemesi varsayılan durdurmaz), eskalasyon kuralları; seçim sırası: en çok kısıt → küçük `precedence` → ad → kimlik, uyan yoksa varsayılan politika, o da yoksa talep hedefsiz. İş takvimi (`/api/support/sla-calendars`): saat dilimi, haftalık pencereler, tatil ve yarım gün, 7/24; süre iş takvimine göre hesaplanır, zaman UTC saklanır (örnek: Pzt-Cum 09-18, hedef 2 iş saati, Cuma 17:00 → Pazartesi 10:00). Her SLA örneği (talep + döngü + ölçüt) politika ve takvim anlık görüntüsü taşır: politika/takvim değişikliği açık talepleri **değiştirmez**; `POST /api/support/tickets/{id}/sla/recalculate` (`support.sla.recalculate`, gerekçe zorunlu) yetkili yeniden hesaplamadır (önce/sonra tarihçede). `GET /api/support/tickets/{id}/sla` backend hesaplı durumları verir (Running, Paused, Breached, Met, Missed, Cancelled); `POST /api/support/sla/preview` örnek talep için seçilen politikayı ve hedef anlarını gösterir. Yeniden açma yeni döngü başlatır; ihlal öncelik düşürülerek silinemez. Zamanlayıcı (`SupportJobs:WorkerEnabled`, `PollIntervalSeconds` varsayılan 300; tenant başına kilit) ihlali gerçek hedef anıyla işaretler ve eskalasyon eylemlerini (`NotifyOwner`, `NotifyUser`, `Reassign`) tekil anahtarla bir kez uygular. Liste süzgeçleri `slaAtRisk`, `slaBreached`, sıralama `resolutionDue|firstResponseDue`; özet `slaAtRisk`/`slaBreached`. Ekranlar: talep detayında SLA paneli, `/destek/sla` (takvim, politika, eskalasyon kuralları, önizleme).
- **Kanal, ek, memnuniyet, dışa aktarma, toplu işlem (dilim 4):** *Ek:* `GET /api/support/tickets/{id}/attachments`, `POST .../messages/{messageId}/attachments?fileName=` (gövde dosyanın kendisi), `GET .../attachments/{attachmentId}/file`; ek mesaja bağlıdır, iç nota bağlı ek iç not iznine bağlıdır (indirme dahil 404); tür uzantı + dosya imzasıyla doğrulanır (pdf, png, jpg, gif, docx, xlsx, doc, xls, txt, csv), 5 MB, mesaj başına 5 / talep başına 20; `html`/`svg`/betik/çalıştırılabilir ve çift uzantı reddedilir; indirme `attachment` + `nosniff`; içerik **taranmaz** (`NotScanned`), genel dosya deposu gelene kadar içerik veritabanında durur. *Gelen kanal:* `POST /api/support/inbound` (`support.inbound.ingest` + talep oluşturma + yanıt izni; rol şablonu `support.integration`) bir **adaptör sözleşmesidir**, gerçek IMAP/webhook alıcısı kurulu değildir: aynı kanal+`externalMessageId` tekrarı `Duplicate`, otomatik yanıt/bounce `IgnoredAutomatic` (talep açmaz, eklenmez), `In-Reply-To`/`References` ya da konudaki `[TK-…]` ile eşleşir ve **gönderen talebin başvuran/alıcı adresiyle aynı olmalıdır**, eşleşme yoksa yeni talep, kapalı talebe gelen mesaj ilişkili yeni talep açar, gönderen başına saatte 30 mesaj sınırı (429). *Memnuniyet anketi:* ayar `support.survey.enabled` (varsayılan hayır) açıkken çözümde, alıcı e-postası varsa, süreli (`support.survey.valid-days`, 14) tek kullanımlık bağlantı e-posta kuyruğuna yazılır (`App:PublicUrl` gerekir); herkese açık `POST /api/public/support-survey/{tenant}/view|answer` (belirteç gövdede ve adreste `#t=`; hız sınırı, tek tip 404); 1-5 puan, ikinci yanıt 409, süre dolunca 409, 2 ve altı `LowSatisfaction` tarihçe olayı; `GET /api/support/tickets/{id}/surveys` personel görünümü. *Dışa aktarma:* `GET /api/support/tickets/export` (`support.tickets.export`; liste süzgeçleri ve veri kapsamı, mesaj/iç not/çözüm notu yok, formül etkisizleştirme, audit). *Toplu işlem:* `POST /api/support/tickets/bulk` (`assign|transfer|close|cancel`, en çok 50; her talep kendi eyleminin kurallarıyla, atomik değil, sonuç talep başına). Ekranlar: talepte **Ekler** ve **Memnuniyet anketi** panelleri, çalışma alanında CSV ve toplu işlem çubuğu, herkese açık `/anket/{tenant}#t=…`.
- **Entegrasyonlar (dilim 5):** destek başka modüllerin tablolarına bağlanmaz. *İlişkili kayıtlar:* `GET|POST /api/support/tickets/{id}/links`, `DELETE .../links/{linkId}`; bağlanabilen türler `contracts.contract`, `orders.order`, `orders.delivery`. Hedef kayıt bağlanırken kayıt boru hattından **çağıranın yetkisi ve veri kapsamıyla** okunur (yok / başka tenant / yetkisiz / modül kapalı aynı 422), talebin müşterisiyle aynı müşteriye ait olmalıdır (müşterisiz talebe bağlanmaz), talep düzenleme izni gerekir, kapalı talebin bağları değişmez; yalnızca anahtar, kimlik ve bağlandığı andaki etiket saklanır (yabancı anahtar yok), karşı modül kapanınca etiket okunur kalır, bağlantı çizilmez. *Sözleşmeye bağlı SLA:* SLA politikasına `contractId` kısıtı (kaydedilirken sözleşme yöneticinin yetkisiyle doğrulanır); talebe sözleşme bağlanınca ya da bağ kalkınca açık örnekler yeniden seçilir (tarihçede yazar, ihlal edilmiş örnek değişmez); `POST /api/support/sla/preview` `contractId` alır. *Karşı modül sayfaları:* `GET /api/support/tickets?linked=contracts.contract:{id}` süzgeci; firma kartında "Destek talepleri" (+ "Talep aç"), sözleşme ve sipariş sayfalarında "İlişkili destek talepleri" (destek kapalıysa ya da izin yoksa görünmez). *Olay adları:* talep olayları `RecordCreated`/`RecordUpdated`, neden alanı `support.<TarihçeOlayı>` (`support.Resolved`, `support.SlaBreached`, `support.LinkAdded`, `support.LowSatisfaction`, ...). Destek modülü kapanınca API kapanır, veri ve bağlar korunur.
- **Raporlar ve şikâyet inceleme (dilim 6):** `GET /api/support/reports/overview` (`support.reports.read`) dönemde (Türkiye günü, en çok 366 gün) açılan talepler için hacim (gün/hafta/ay serisi, durum/tür/kanal/öncelik kırılımı), birikim yaşı (çalışılan talepler, yaş kovaları, atanmamış, en eski), süreler (ilk yanıt ve çözüm; **takvim süresi** ve SLA **iş süresi**; ortalama, medyan, %90, %95 en yakın sıra, en kısa/en uzun, örneklem büyüklüğü, ulaşmayanların sayısı), SLA uyumu (pay = hedefinde tamamlanan, payda = sonuçlanmışlar; devam eden ve iptal paydada yok; payda 0 ise oran boş), yeniden açılma oranı (pay/payda yazılı) ve memnuniyet (gönderilen, yanıt oranı, ortalama, 1-5 dağılımı, düşük puan; yanıt < 30 ise "örneklem küçük" uyarısı, yorum metni yok) döner. Veri çağıranın izin ve veri kapsamıyla kayıt boru hattından okunur (üst sınır 10.000 talep, aşılırsa `truncated`); her sayı `drillDown` süzgeci taşır ve aynı süzgeçle `GET /api/support/tickets` aynı sayıyı verir (yeni liste süzgeçleri: `createdFrom`, `createdTo`, `minAgeDays`, `maxAgeDays`, `reopened`, `lowSatisfaction`, `ids`). `GET /api/support/reports/complaints` tekrarlayan kök nedenleri (normalleştirilmiş metin eşitliği, eşik `minOccurrences` 2-100; anlamsal eşleştirme yok) ve düzeltici aksiyon özetini (açık/gecikmiş/tamamlanan, vadesi dönemde olanların zamanında tamamlanma oranı, en gecikmiş 50 aksiyon) verir. *Düzeltici aksiyon:* `GET|POST /api/support/tickets/{id}/corrective-actions`, `POST .../{actionId}/status` (`Done|Cancelled|Open`); yalnızca şikâyet türünde, ayrı yetki `support.complaints.manage`, sorumlu etkin üye, son tarih geçmiş olamaz (en çok 2 yıl), tamamlama/iptal/yeniden açma not ister, silinmez, tarihçeye yazılır; gecikme = açık ve son tarihi (Türkiye günü) geçmiş. Ekranlar: `/destek/raporlar`, `/destek/sikayetler`, talepte **Düzeltici aksiyonlar** paneli, çalışma alanında `?filtre=` ile rapor kırılımı.
- **İzinler:** `support.tickets.read|create|write|assign|take|resolve|close|reopen|cancel|priority|merge|export`, `support.reports.read`, `support.complaints.manage`, `support.inbound.ingest`, `support.messages.reply`, `support.notes.write`, `support.internal.read`, `support.settings.manage`. Rol şablonları: `support.agent`, `support.lead` (kapsam Ekip), `support.manager`, `support.viewer` (iç not yok). Lookup'lar: `support.ticket.party|person|category|queue|owner|parent`.
- **Ekranlar:** `/destek/talepler` (çalışma alanı: sayılı hızlı görünümler, süzgeç, arama), `/destek/talepler/yeni`, `/destek/talepler/{id}` (işlemler, yazışma, tarihçe, çözüm), `/destek/ayarlar` (kuyruk ve kategori).
- **Henüz yok (sonraki dilimler):** rapor zamanlaması/CSV, tekrarlayan neden için anlamsal eşleştirme, düzeltici aksiyon bildirimi/eskalasyonu, "sonraki müşteri mesajına yanıt" SLA sayacı, otomatik alındı mesajı, gerçek gelen e-posta alıcısı (IMAP/webhook) ve gönderenden müşteri eşleştirme, ek dosya taraması ve genel dosya deposu, müşteri portalı, finans iade/tazmin ve lojistik sevkiyat bağları (hedef kayıt türü yok), kapalı modülde karşı sayfada salt okunur talep gösterimi. Ayrıntı, dilim planı ve kabul kriteri izlenebilirliği: ADR-0024.

## Pazarlama modülü ([ADR-0025](docs/adr/0025-kampanya-ve-segment-yonetimi.md)) — dilim 2 (EPIC 12 kısmen)

Segment yönetimi (arka uç). Sektörden ve CRM'den bağımsızdır; modül anahtarı `marketing`, şema `marketing`. Segment üyeliği gönderim izni vermez; izin ve engel kararı çekirdekteki iletişim tercihindedir (yukarıda).

- **Segment**: hedef türü `Company` (üyelik kimliği ortak taraf), `Person` (ortak kişi) ya da `Lead`; tür `Static` (üyeler elle) ya da `Dynamic` (koşuldan). Hedef türü, tür ve kod oluşturulduktan sonra değişmez. Durum `Draft → Active → Archived`; durum, yayın sürümü ve son hesaplama özeti yalnızca eylem uç noktalarıyla değişir.
- **Koşul ağacı**: iç içe `and`/`or` (derinlik ≤4, ≤25 koşul), koşul `{"field","operator","values"}`; operatörler `eq, ne, contains, in, between, empty, notempty, lastdays, nextdays, before, after, exists, notexists` ve her alan tipinde yalnızca uyumlu olanlar geçerlidir. SQL/kod yazılmaz. `ne` boş değeri de kapsar; eşitlik/içerir/aralık boşla eşleşmez; gün sınırları firmanın saat dilimindedir.
- **Alanlar** `GET /api/marketing/segment-fields?target=` ile listelenir: yalnızca çağıranın okuyabildikleri; kapalı modül ya da yetkisiz alan `unavailable` altında nedeniyle görünür ve o alanla önizleme/yayım 422 verir. CRM alanları: firma (ad, şehir, sektör, durum, kaynak, etiket, sorumlu, oluşturma tarihi; kişisi/açık fırsatı/kazanılmış fırsatı var), kişi (unvan, firma sektörü, oluşturma tarihi), lead (durum, kaynak, ülke, şehir, sektör, UTM kampanyası, oluşturma tarihi). Sayılar çağıranın veri kapsamıyla hesaplanır.
- **Uç noktalar** (`/api/marketing`): `segments`, `segment-members` (dahil/hariç; statikte yalnızca dahil), `segment-versions` (salt okunur), `POST segments/preview` (`marketing.segments.read`; hiçbir şey yazmaz), `GET segments/{id}/members`, `POST segments/{id}/publish|refresh|archive|restore` (`marketing.segments.publish`), `POST segments/{id}/copy`. Üyelik: dinamikte yayımlanmış sürüm ∪ dahil ∖ hariç, statikte dahil ∖ hariç. Yayımlanmış sürüm değişmez; taslak düzenlenebilir.
- Ekranlar: Pazarlama → Segmentler (`/pazarlama/segmentler`, `/yeni`, `/{id}`): liste ve süzgeçler, koşul düzenleyici, önizleme, üyeler ve istisnalar, sürümler, yayımla/yenile/arşivle/kopyala. Arayüz izin ve modül durumunu menüde gizler; asıl denetim sunucudadır.
- İzinler: `marketing.segments.read|write|publish`, `marketing.recipients.read`. Rol şablonları: Pazarlama uzmanı, yöneticisi, izleyicisi.
- **Kampanya ve hedef kitle (dilim 4)**: `/api/marketing/campaigns` (hedef türü, kanal ve kod değişmez; kişi seçme kuralı `PrimaryContact`/`DecisionMaker`/`Role`/`AllContacts`/`CompanyPoints`, hedef başına sınır), `campaign-audience` (dahil/hariç segment ya da elle hedef), `POST campaigns/{id}/audience/preview` (yazmaz) ve `…/snapshot` (değişmez, kişisel veri kopyalamayan dondurma), `GET audience-snapshots/{id}/recipients` (`marketing.recipients.read`). Sayılar ayrı verilir (hedef, alıcısı bulunan hedef, çözümlenen kişi, benzersiz iletişim noktası, uygun, elenen) ve elenme nedenleri sayılır; uygunluk her zaman iletişim tercihinden gelir, bilinmeyen izin elenir, paylaşılan adres otomatik gönderilmez. **İleti gönderilmez**; içerik, onay ve gönderim sonraki dilimlerde. İzinler: `marketing.campaigns.read|write|audience`. Ekran: Pazarlama → Kampanyalar.
- **İçerik, onay ve çalıştırma (dilim 5)**: `campaign-contents` (sürümlü, değişmez, düz metin; bağlantılar yalnızca http/https), `campaign-runs` ve eylemleri `POST campaign-runs/{id}/submit|approve|reject|reopen|start|pause|resume|cancel|process`, `GET …/summary|deliveries` (adres içermez). Hazırlayan kendi çalıştırmasını onaylayamaz; onaydan sonra değişiklik için taslağa alınır. **Gerçek gönderim kapalıdır:** firma ayarı `marketing.provider` varsayılan "yok"; seçilebilen tek sağlayıcı iletiyi hiçbir yere göndermeyen test sağlayıcısıdır. Her gönderimden önce adres yeniden çözülür, izin/engel yeniden denetlenir, günlük sıklık sınırı (`marketing.frequency.daily-limit`, varsayılan 1) atomik ayrılır; teslimat anahtarı çift satırı engeller; sağlayıcı kabulünden sonra kaybolan yanıt "belirsiz" olur ve kör yeniden denenmez; "kabul edildi" teslim edildi değildir. **Henüz yok:** gerçek sağlayıcı, otomatik işçi (elle başlat ve işle), kişi bazlı değişken. Her gönderilen iletiye abonelikten çıkma bağlantısı eklenir (dilim 6; bkz. "İletişim tercihi ve engel"); `App:PublicUrl` ayarsızsa başlatma bloklanır. İzinler: `marketing.campaigns.approve|send`.
- **Yanıt çalışma alanı ve kaynak/UTM (dilim 7)**: `GET|POST /api/marketing/campaign-responses`, `GET …/{id}` ve eylemleri `POST …/{id}/take|convert-to-lead|create-activity|apply-opt-out|close|reopen` (genel PUT/DELETE yok). Yanıt gönderilmiş (kabul edildi ya da sonucu belirsiz) bir iletiye (`deliveryId`) kaydedilir; kampanya, çalıştırma ve hedef iletiden gelir, yanıtta adres yoktur. İzinler `marketing.responses.read|write`; görünürlük yanıtın sorumlusuna bağlı veri kapsamındandır. Yalnızca ilgi, soru ve görüşme talebi lead'e dönüşür (lead çağıranın CRM yetkisiyle açılır; kaynak ayrıntısı `Kampanya: <ad>` ve kampanya UTM'si yazılır); aktivite yanıt başına bir kez açılır. "İletişim istemiyorum" yanıtının çıkışı kendiliğinden uygulanmaz: "Çıkışı uygula" pazarlama iznini reddeder. Kampanyada `utmSource|utmMedium|utmCampaign` (küçük harf; boşsa kaynak `kampanya`, ortam kanal, kampanya kodu). **Henüz yok:** sağlayıcıdan otomatik yanıt toplama, yanıt raporları, yanıttan fırsat (lead'in CRM dönüşümüyle yapılır).
- **Maliyet, rapor ve müşteri kartı (dilim 8)**: kampanyada `budget|actualCost|costCurrency`; `GET /api/marketing/reports/campaigns?channel=&status=&campaignId=` (gönderildi = kabul edilen + belirsiz, yanıt, ilgi, çıkış, lead, ilk/son dokunuş lead sayıları, yanıt ve lead başına maliyet) ve `GET /api/marketing/targets/{id}/history` (firma/kişiye giden iletiler ve yanıtlar, adres yok). İzin `marketing.reports.read` (geçmiş ayrıca `marketing.recipients.read`); yalnızca görülebilen kampanyalar sayılır. Atıf yalnızca yanıttan açılan lead içindir; fırsat/ciro, ağırlıklı atıf ve dışa aktarma yoktur. Ekranlar: `/pazarlama/rapor`, firma ve kişi kartında "Pazarlama geçmişi".
- **İşletim ve ölçek (dilim 9)**: ölçülen süreler, 20.000 hedef sınırı, gönderim hızı (~34 ileti/sn), yapılandırma ve bilinen sınırlar `docs/pazarlama-isletim.md` içindedir. Ölçüm: `MODULIX_SCALE=1 dotnet test tests/Modulix.IntegrationTests -c Release --filter MarketingScaleTests` (varsayılan atlanır). Gerçek gönderim kapalıdır.
- **Gönderim işçisi, değişkenler, test gönderimi (dilim 10-11)**: başlatılmış çalıştırmaların satırlarını arka plan işçisi gönderir (`MarketingSend:*`; başlatmaz, onaylamaz; ≈76 ileti/sn ölçüldü). İçerikte `{{ad|yedek}}`, `{{soyad|…}}`, `{{ad_soyad|…}}`, `{{firma|…}}` değişkenleri kullanılır (yedek metin zorunlu; gönderim anında doldurulur). "Kendime test gönder" yalnızca çağıranın hesap e-postasına gider (günde 10, örnek değerlerle). Eski bağlantı belirteçleri (süresi dolalı 365 gün) ve sıklık pencereleri (7 gün) günlük işle temizlenir (dilim 12). Ayrıntı: ADR-0025 dilim 10-12, `docs/pazarlama-isletim.md`.
- Kod: `src/Modulix.Modules.Marketing` (`Domain`, `Records`, `Segments`), CRM kaynağı `Modulix.Modules.Crm/Records/CrmSegmentFieldSource.cs`, sözleşme `Modulix.Core.Contracts/Marketing`. **Henüz yok:** gerçek gönderim sağlayıcısı ve abonelikten çıkma, sözleşme bitişi ve son aktivite alanları, zamanlanmış yenileme, üye değişimi geçmişi, dışa aktarma (ADR-0025 bölüm 6 ve 9).

## E-posta

Uygulama e-postayı hemen göndermez: `IEmailQueue.Enqueue(...)` e-postayı `platform.EmailMessages` kuyruğuna yazar, arka plandaki işleyici (her 10 saniyede) SMTP ile gönderir. Kuyruğa yazma, çağıranın kaydıyla aynı işlemdedir; kayıt geri alınırsa e-posta da gitmez. Aktif tenant varsa e-posta o tenant'a bağlanır; yoksa platform e-postasıdır (ör. şifre sıfırlama). `IEmailQueue` `Modulix.Core.Contracts` içindedir, modüller de kullanabilir.

- Gönderilemeyen e-posta 1 dk, 5 dk, 15 dk ve 1 saat arayla tekrar denenir; 5. denemeden sonra veya sunucu alıcıyı kalıcı olarak reddederse (5xx) `Failed` olur ve hata `LastError` alanında kalır.
- Birden fazla uygulama örneği aynı anda çalışabilir; her e-posta tek bir örnek tarafından alınır. Kayıtlara alıcı adresi değil, yalnızca e-postanın kimliği yazılır.
- Kullanıcı girdisini HTML gövdeye eklemeden önce kodlayın (`WebUtility.HtmlEncode`).

**Yerelde:** `scripts\db-up.ps1` SQL Server'ın yanında **Mailpit**'i de başlatır. Development ayarları e-postaları ona gönderir; hiçbir e-posta dışarı çıkmaz, hepsi **http://localhost:8025** adresinde görünür.

```powershell
# SMTP ayarlarını sınamak için deneme e-postası (sonucu yazar)
dotnet run --project src/Modulix.Api -- test-email ayse@acme.demo
```

**Gerçek sunucu (canlı ortam):** `appsettings.json` içindeki `Email` bölümü; şifre kod deposuna yazılmaz.

| Ayar | Örnek | Not |
| --- | --- | --- |
| `Email:FromAddress` | `noreply@firmaniz.com` | Gönderen adres; SPF/DKIM kayıtları bu alan adı için yapılmalı |
| `Email:FromName` | `Modülix` | |
| `Email:Smtp:Host`, `Port` | `smtp.sendgrid.net`, `587` | Herhangi bir SMTP hizmeti (SendGrid, Amazon SES, Mailgun, Office 365) |
| `Email:Smtp:Security` | `Auto` | `Auto`, `StartTls`, `SslOnConnect`; `None` yalnızca Mailpit için |
| `Email:Smtp:UserName` | `apikey` | Boşsa kimlik doğrulama yapılmaz |
| `Email:Smtp:Password` | | `dotnet user-secrets set Email:Smtp:Password ...` veya ortam değişkeni `Email__Smtp__Password` |

`FromAddress` veya `Smtp:Host` boşsa işleyici başlamaz ve uyarı yazar; e-postalar kuyrukta bekler, ayarlar tamamlanıp uygulama yeniden başlatılınca gönderilir.

## Olaylar (Ç1)

Modüller birbirinin değişikliğine ve bildirimlere olaylarla tepki verir ([ADR-0007](docs/adr/0007-olay-altyapisi.md)). Bir modül başka modülün tablosuna yazmaz; olaya abone olur ve tepkisini kendi kayıtlarında, kayıt boru hattından gösterir.

- **Outbox:** kayıt boru hattı her oluşturma, güncelleme ve silmede `platform.OutboxMessages`'a bir olay yazar; kayıt, denetim kaydı ve olay aynı işlemdedir (işlem geri alınırsa olay da yoktur). Olay türleri `RecordCreated`, `RecordUpdated`, `RecordDeleted` (`DomainEventTypes`, sürüm 1). Zarf (`EventEnvelope`, `Modulix.Core.Contracts.Events`): olay kimliği, tenant, tür ve sürüm, kayıt türü ve kimliği, sıra numarası (kaydın yeni sürümü; silmede son sürüm + 1), işlemi yapan kişi ve kaynak (denetim kaydıyla aynı), correlation (isteğin izi), causation ve derinlik (abonenin değişikliğinden doğan olayda), neden (ör. `transfer`), şirket kapsamlı kaydın işletici şirketi `CompanyId` (ortak kayıtta boş, [ADR-0008](docs/adr/0008-sirket-ve-sube-kapsami.md)) ve değişen alanların `{ alan: { old, new } }` farkı.
- **Abonelik:** modül `IModule.EventSubscriptions` ile bildirir, abone sınıfını `ConfigureServices`'te scoped kaydeder:
  ```csharp
  EventSubscription.For<PartyRenamedSubscriber>(
      "crm.party-renamed", [DomainEventTypes.RecordUpdated], [SharedEntities.Party], [CrmModule.Permissions.CompaniesWrite])
  ```
  Anahtar modül anahtarıyla başlar ve değişmez; kayıt türleri boşsa bütün türler; izinler modülün kendi izinleridir. Katalog açılışta denetler (bilinmeyen olay veya kayıt türü, başka modülün izni, olayın güncel sürümünü okuyamayan abone uygulamayı açmaz). Abone `IEventSubscriber.HandleAsync` uygular, yalnızca Contracts servislerini kullanır ve kayıtları `IRecordPipeline`'dan değiştirir (`IModuleData`/`DbContext` kullanmaz; mimari test denetler).
- **Abonenin kimliği:** abone olayı tetikleyen kişi adına değil "sistem" adına çalışır: olayın tenant'ının bağlamında (RLS), yalnızca aboneliğin bildirdiği izinlerle, tenant geneli kayıt kapsamıyla. Aboneliğin modülü firmada kapalıysa teslim yapılmaz. Hassas alanlar (Y8b) aboneliğin izniyle görülemiyorsa farktan çıkarılır, adları `HiddenFields`'ta verilir; outbox tam farkı saklar.
- **Teslim:** işleyici her 5 saniyede dağıtılmamış olayları yazılış sırasıyla eşleşen aboneliklere `platform.EventDeliveries` satırı olarak dağıtır (dağıtım uygulama kilidiyle tek örnekte), sonra teslimleri kiralayıp aboneyi çalıştırır. Abone açık bir veritabanı işleminde çalışır: yaptığı değişiklik, kuyruğa yazdığı e-posta ve teslimin "başarılı" işareti birlikte yazılır ya da hiçbiri. Teslim en az bir kezdir; abone idempotent yazılır (olay kimliği). Kira 2 dakikadır, abone çalışırken 30 saniyede bir uzatılır; aboneye 5 dakika verilir. Birden fazla uygulama örneği çalışabilir; kirası dolan örneğin geç sonucu yazılmaz.
- **Sıra:** aynı kaydın olayları bir aboneye sıra numarasıyla teslim edilir; önceki teslim başarılı veya atlanmış olmadan sonraki alınmaz. Sırası önemsiz abone `Ordered = false` der. Bir turda tek firmadan en fazla 20 teslim alınır; bir firmanın birikmesi veya hatası diğerlerini bekletmez.
- **Hata:** abone istisna fırlatırsa yalnızca o teslim 1 dk, 5 dk, 15 dk, 1 sa, 4 sa arayla (±%20) yeniden denenir; 6. denemeden sonra veya `PermanentEventFailureException` ile `Failed` olur. Başarısız sıralı teslim aynı kaydın sonraki teslimlerini bekletir. Firma kapalıysa, aboneliğin modülü kapandıysa veya abonelik koddan kaldırıldıysa teslim atlanır (`Skipped`). Abonenin değişikliği yeni olay üretir; derinliği 5'i aşan olay yazılır ama dağıtılmaz (uyarı loglanır). Loglara ve `LastError`'a olay kimliği, tenant, kayıt türü ve kimliği yazılır; payload ve alan değeri yazılmaz.
- **Platform ekranı** (`/platform/olaylar`, yalnızca platform yöneticisi): bekleyen, bekletilen ve başarısız teslimler firma, abonelik, olay türü, durum ve tarihe göre süzülür; satırda olay türü, kayıt türü ve kimliği, abonelik, deneme sayısı, son hata ve beklettiği teslim sayısı görünür, payload gösterilmez. **Yeniden dene** (deneme sayacı sıfırlanır, hemen zamanlanır) ve **Atla**, tek tek veya süzülmüş liste için (en fazla 500); çalışmakta veya bitmiş teslim değişmez. İşlem teslimin firmasının denetim kaydına `core.event-delivery` olarak yazılır. API: `GET /api/platform/events/summary`, `GET /api/platform/events/deliveries?tenantId=&subscription=&eventType=&state=Failed&from=&to=&page=`, `POST /api/platform/events/deliveries/retry` ve `/skip` gövde `{ "ids": [...] }` veya `{ "filter": { ... } }`.
- **Gözlemleme:** `Modulix.Events` ölçümleri: `modulix.events.undispatched.age` ve `modulix.events.deliveries.pending.age` (saniye), `modulix.events.deliveries.failed`, `modulix.events.deliveries.completed` (abonelik ve sonuç etiketiyle). `/health` dağıtılmamış olay 15 dakikadan eskiyse `Degraded` döner.
- **Saklama:** başarılı ve atlanmış teslimler ile bütün teslimleri bitmiş olaylar 7 gün, başarısız teslimler ve olayları 30 gün sonra saatlik temizlikte silinir; dağıtılmamış veya bekleyen olay silinmez. Kalıcı geçmiş denetim kaydıdır.
- **Atama e-postası** (`core.assignment-email`, çekirdek): firma, fırsat veya aktivite (modüllerin `OwnedRecords` türleri) başkasına atanınca yeni sorumluya "Size bir kayıt atandı" e-postası gider: kayıt türü, kaydın adı, atayan kişi ve kayda bağlantı (`App:PublicUrl` ayarlıysa; adres `OwnedRecordType.Path`). Kendine atama, sorumluyu boşaltma ve kayıt devri e-posta göndermez. Alıcı etkin üye değilse veya kaydı kendi yetkisiyle göremiyorsa e-posta yazılmaz. E-posta teslimle aynı işlemde yazıldığı için olay tekrar teslim edilse de ikinci e-posta oluşmaz. **Kayıt devri** (Y2b) olaylara `transfer` nedeni yazar ve yeni sorumluya tek özet e-postası gönderir ("3 firma, 1 açık fırsat").
- **Ayarlar** (`Events` bölümü): `WorkerEnabled` (varsayılan `true`; testler ve tek seferlik komutlar kapatır), `PollIntervalSeconds` (5), `BatchSize` (tur başına teslim, 100). İşleyici şimdilik API süreci içinde çalışır.
- `OlayZarfi` migration'ı o ana kadar birikmiş olayları dağıtılmış işaretler; geçmiş atamalar için e-posta gitmez.

## Otomasyon kuralları (Ç6b, [ADR-0027](docs/adr/0027-kural-ve-is-akisi-altyapisi.md)) — Dilim 1: tanım, sürüm, önizleme; Dilim 2: olay yolu ile çalışma

> **Dilim 1 (tanım, sürüm, önizleme) ve Dilim 2a (olay yolu ile çalışma) uygulandı; kural çalıştırma ayrıntıları aşağıda "Dilim 2" alt bölümündedir.** Kural tanımlanır, doğrulanır, yayınlanır ve yan etkisiz önizlenir. Gerçek uygulamada henüz aksiyon beyan eden modül yoktur (CRM aksiyonları Dilim 3), bu yüzden üretimde yayınlanabilir kural yoktur.

- **Modül yetenekleri:** modül `IModule.Automation` ile kural yazılabilen kayıt türlerini (`Entities`), olaylarını (`Events`), okunabilir alanlarını (`Fields`: tip, seçenek, lookup, para birimi alanı, alan izni), sınırlı ilişkilerini (`Relations`) ve aksiyonlarını (`Actions`) bildirir. Katalog açılışta doğrular (anahtar öneki, tekillik, izin/lookup/modül varlığı, işleyici tipi); hatalı beyan uygulamayı açtırmaz. Core hiçbir modülü bilmez (`AutomationNeutralityRulesTests`). Lojistik, CRM olmadan aynı sözleşmeyle belge eksikliği, bakım tarihi ve kapasite eşiği alanlarını beyan eder (sevkiyat ve araç kayıt depoları henüz yok).
- **Aksiyon (araç) sözleşmesi** (`AutomationActionDefinition`): anahtar, ad, açıklama, parametre şeması, gereken izinler, gereken modüller (lisans), yan etki sınıfı (`Read`/`Draft`/`Write`), dry-run desteği, idempotency kaynağı. Çağıran kimlik (`AutomationCallContext`: kullanıcı, otomasyon, ileride ajan) sözleşmenin dışında bağlamdır. Yayınlayan, sahip olmadığı izni gerektiren aksiyonu yayınlayamaz.
- **Koşul modeli:** tipli, iç içe AND/OR (en çok 4 seviye, 50 satır); tipe göre izinli operatörler; lookup kalıcı kimlikle; para birimi zorunlu ve farklı para birimleri karşılaştırılmaz; null'da karşılaştırmalar yanlış, `Ne`/`NotIn` doğru; tarih tenant takvim gününe göre; eski/yeni değer ve `Changed` operatörleri yalnızca güncelleme tetikleyicilerinde; sınırlı ilişki (`Exists`/`NotExists`/`Count`, ikinci seviye yok). Serbest SQL, C# veya betik yoktur; bilinmeyen düğüm tipi reddedilir.
- **Tetikleyiciler (model ve doğrulama):** kayıt oluşturma, alan değişimi, durum geçişi, günlük tarama, tarihe kala/sonra, hareketsizlik, iş olayı, elle.
- **Sürümler:** `core.AutomationRules` (başlık, durum `Draft`/`Active`/`Inactive`) ve `core.AutomationRuleVersions` (içerik). Yayınlanmış sürüm **değişmez**; yayınlanmış kuralı düzenlemek yeni taslak sürüm açar, kural başına en çok bir taslak vardır. Yeni kural taslak başlar; yayınlarken açık/kapalı seçilir (varsayılan kapalı). Yayınlama ve açma, tanımı **güncel katalogla** yeniden doğrular: silinen/pasifleşen alan, kapanan modül veya kaybedilen izin bağımlı kuralı sessizce bozmaz; sorun kural ayrıntısında (`DraftIssues`/`PublishedIssues`) görünür ve yayını/açmayı engeller (kapatmak her zaman serbesttir).
- **Önizleme** (`POST /api/automation/preview`): örnek kayıtta (kayıt boru hattından, çağıranın izni ve kapsamıyla okunur) hangi koşulların neden geçtiğini ve hangi aksiyonların hangi parametrelerle planlandığını gösterir. Aksiyon işleyicisi çağrılmaz; kayıt yazılmaz, denetim kaydı, olay veya bildirim oluşmaz. Olayın `{alan:{old,new}}` farkı verilebilir.
- **İzinler (Core):** `core.automation.read` (kural, katalog), `core.automation.manage` (taslak, silme, önizleme), `core.automation.publish` (yayın, açma/kapama); `core.automation.run` (elle çalıştırma, yeniden deneme, iptal) ve `core.automation-logs.read` (çalışma geçmişi) Dilim 2'de kullanılır; `core.automation.approve` tanımlıdır ama onay özelliği Dilim 4'tedir. "Yönetici" rolünde hepsi vardır.
- **Uç noktalar** (`/api/automation`): `GET catalog`, `GET rules` (modül, durum, arama, sayfa), `GET rules/{id}`, `POST rules`, `PUT rules/{id}` (taslak; `expectedVersion` ile eşzamanlılık), `DELETE rules/{id}/draft`, `POST rules/{id}/publish` (sorun varsa 422 + `issues`), `PUT rules/{id}/active`, `POST preview`. Başka tenant'ın kuralı 404 döner; tablolar query filter ve Row-Level Security ile korunur.
- **Denetim:** her yönetim işlemi `core.automation-rule` kaydıdır (ad, durum, öncelik, sürüm, okunabilir kural özeti; ham JSON yazılmaz).
- **Dağıtım ve geri dönüş:** `AutomationRules` migration'ı yalnızca iki yeni tablo ekler (geriye uyumlu; eski sürüm tabloları görmez). Uygulamak için `dotnet run --project src/Modulix.Api -- migrate`. Geri dönüş: önceki uygulama sürümüne dönmek yeterlidir (tablolar zararsız kalır); verinin atılması gerekirse `Down` tabloları RLS politikasından çıkarıp siler (önce `tenant-export`).
- **Maliyet:** harici ücret yoktur; kural verisi veritabanı ve denetim kaydı depolaması, önizleme ise kayıt okuma CPU'su kullanır. Yürütme gelince değerlendirme CPU'su ve çalışma kaydı büyümesi eklenir (ADR-0027, "Maliyet"). Ölçülmemiş gecikme veya kapasite vaat edilmez.

### Dilim 2: kuralların çalışması (olay yolu), tekilleştirme, yeniden deneme, acil durdurma

> **Çalışan:** kayıt oluşturma, alan değişimi, durum geçişi tetikleyicili kurallar ve elle çalıştırılan kurallar. **Çalışmayan (Dilim 2b):** günlük tarama (`Scheduled`), tarihe kala/sonra (`DateRelative`), hareketsizlik (`Inactivity`) ve modül iş olayı (`DomainEvent`) tetikleyicileri; bunlarla kural **yayınlanamaz** (422, "henüz çalışmıyor"), taslak olarak saklanabilir. Gerçek uygulamada hâlâ aksiyon beyan eden modül yok (CRM, Dilim 3); bu yüzden üretimde yayınlanabilir kural yoktur ve çalıştırıcı boş döner.

- **Olay yolu:** `core.automation` aboneliği (`IEventSubscriber`, sırasız, izinsiz) `RecordCreated`/`RecordUpdated` olaylarını alır. Abonelik yalnızca modüllerin `IModule.Automation` ile **kural yazılabilir** bildirdiği kayıt türlerine bağlanır; hiçbir modül bildirmediyse abonelik de, olay teslimine ek yük de yoktur. Abone yalnızca ucuz iş yapar: olayın farkından tetikleyiciyi eşler ve eşleşen her etkin kural için bir `Pending` **çalışma** (`core.AutomationRuns`) yazar. Kayda bakmaz, koşul değerlendirmez, aksiyon çalıştırmaz. Hassas alanın değeri aboneye gelen olay farkından çıkarılmış olduğundan o alana bağlı tetikleyici eşleşmez.
- **Tekilleştirme:** `DedupeKey = SHA-256(tenant | olay kimliği | kural sürümü | kayıt türü | hedef kayıt)`, `UNIQUE(TenantId, DedupeKey)`. Aynı olayın ikinci kez teslimi (en az bir kez) ikinci çalışma üretmez. Her adımın idempotency anahtarı `SHA-256(DedupeKey | adım kimliği)`'dir ve aksiyona geçirilir; yeniden deneme aynı anahtarı kullanır. Kural kaynaklı olay zincirinde (derinlik > 0) aynı iz + aynı kural + aynı kayıt için ikinci çalışma açılmaz (döngü kesilir); derinlik sınırı ADR-0007'deki 5'tir.
- **Çalıştırıcı** (`AutomationRunner`, arka plan işçisi `AutomationWorker`; `Automation:WorkerEnabled`, `Automation:PollIntervalSeconds`): tenant başına oturum kilidiyle (`sp_getapplock`) tek örnekte koşar. Çalışma koşullu UPDATE ile **kiralanır** (kira belirteci, 3 dk); kirasını yitiren işleyici sonuç yazamaz. Bir tur tenant başına en çok `Automation:RunsPerTenantPerRound` (25) çalışma işler: bir tenant diğerlerini aç bırakamaz.
- **Kuralın kimliği:** koşul ve aksiyonlar tetikleyen kullanıcının değil **kuralın** kimliğiyle çalışır: izinleri yalnızca tanımın gerektirdikleridir (kayıt türünün okuma izni, koşulda/bağlamada kullanılan hassas alanların okuma izni, aksiyonların gerektirdiği izinler), kayıt kapsamı tenant geneli, tenant'ı oturumdan gelir. Kullanılmayan hassas alan izni kurala verilmez. Aksiyonun yaptığı değişiklik tetikleyen olaya bağlanır (`CausationId`, aynı iz, derinlik + 1, kaynak arka plan işi, abonelik `core.automation`). Çalışma anında modül/lisans yeniden denetlenir.
- **Değerlendirme:** kayıt kuralın kimliğiyle okunur (alan yetkisi uygulanır); eski/yeni değer koşulları olayın farkından (outbox) gelir. Koşul sağlanmazsa çalışma `NotMatched` biter ve aksiyon çağrılmaz; sağlanırsa kural **sürümündeki** aksiyonlar sıralı adımlar olur. Çalışma başladığı sürüme bağlı kalır: kural sonradan yeniden yayınlansa da yürüyen çalışma eski sürümle biter, yeni olaylar yeni sürümü kullanır. Aksiyon parametreleri çalışma anında kaydın güncel değerinden çözülür (önizleme ile aynı kod); kayıt değeri çalışma satırında saklanmaz. Zorunlu parametre kayıtta boşsa adım `Skipped` olur (hata değildir).
- **Yeniden deneme:** geçici hata (aksiyon `Retryable` dedi ya da istisna fırlattı) 1 dk, 5 dk, 15 dk, 1 sa aralıkla en çok 5 denemeye kadar tekrarlanır; kalıcı hata ya da hak bitince adım `Failed`, kalan adımlar `Cancelled`, çalışma `Failed` olur. İstisna iletisi kayıt değeri taşıyabileceği için **yazılmaz**, yalnızca hata türü yazılır. Beklenmeyen çalıştırıcı hatası çalışmayı sonsuza kadar yeniden denetmez, `Failed` işaretler.
- **Acil durdurma:** (1) platform: `Automation:Enabled=false` hiçbir tenant'ın çalışmasını işlemez (kuyruktakiler bekler, iptal edilmez); (2) firma: **Ayarlar → Otomasyon → "Otomasyon kuralları çalışsın" (`core.automation.enabled`) = Hayır** kuyruktaki çalışmaları iptal eder ve yürüyen çalışmayı bir sonraki adım sınırında durdurur; kurallar silinmez; (3) kural: kapatılan kuralın kuyruktaki çalışmaları iptal edilir.
- **Tenant limitleri:** tenant başına en çok 200 **etkin** kural (aşınca açma/yayınla-aç 409); bir olay için en çok 50 aday kural; tur başına çalışma sınırı (yukarıda).
- **Çalışma geçmişi ve müdahale** (`/api/automation`): `GET runs` (kural, durum, kayıt, sayfa), `GET runs/{id}` (adımlar, deneme sayısı, özet, etkilenen kayıt) — `core.automation-logs.read`; `POST rules/{id}/run` (yalnızca `Manual` tetikleyicili ve açık kural; çağıran kaydı **kendi yetkisiyle** görebilmelidir; aynı kural sürümü aynı kayıt için tenant gününde bir kez, ikincisi 409 + mevcut çalışma), `POST runs/{id}/retry` (başarısız çalışmayı kaldığı adımdan tekrar kuyruğa alır; başarılı adımlar tekrarlanmaz), `POST runs/{id}/cancel` — `core.automation.run`. Her müdahale `core.automation-rule` denetim kaydına "Çalışma" alanıyla yazılır.
- **Veri:** `core.AutomationRuns`, `core.AutomationRunSteps` (migration `AutomationRuns`, RLS). Koşulu sağlamayan olayların sayısı `NotMatched` çalışma olarak görünür; eşleşmeyen tetikleyiciler satır üretmez. Çalışma/adım satırlarının **saklama süresi uygulanmadı** (aşağıdaki sınırlama).
- **Dağıtım ve geri dönüş:** migration yalnızca iki yeni tablo ekler (geriye uyumlu). Uygulamak için `dotnet run --project src/Modulix.Api -- migrate`. Geri dönüş: önceki uygulama sürümüne dönmek yeterlidir (eski sürüm bu tabloları görmez); verisini de kaldırmak için migration geri alınır (`TenantIsolationSql.RemoveTable` + `DropTable`). Çalıştırıcıyı geçici durdurmak için `Automation__Enabled=false`.
- **Bilinen sınırlamalar:** tarama tabanlı tetikleyiciler, iş olayı tetikleyicisi ve `IAutomationRecordSource` (kayıt sayma) yok (Dilim 2b); çalışma/adım saklama süresi (90/180 gün) ve temizlik işi yok; işçi, kural yeteneği beyan eden modülü açık her tenant'ı turda gezer (çok tenant'ta ölçüm Dilim 6); kural önbelleği yok (olay başına bir indeksli sorgu); gerçek kayıt okuma yolu (CRM) Dilim 3'te gerçek bir modülle doğrulanacak.

## Sürekli entegrasyon (Görev 3)

`main` dalına her push'ta ve her pull request'te GitHub Actions (`.github/workflows/ci.yml`):

1. SQL Server'ı yereldekiyle aynı `compose.yaml` ve `init.sql` ile açar; şifreler her çalışmada yeniden üretilir.
2. Release modunda derler. Yüksek veya kritik güvenlik açığı olan bir paket varsa derleme durur.
3. Migration'ları uygular; mimari, birim ve entegrasyon testlerini çalıştırır.

CI tüm dallarda çalışır. Yeni migration'ı GitHub üzerinde üretmek için **Actions → EF migration olustur → Run workflow**.

Sonuç GitHub'da reponun **Actions** sekmesinde ve README'deki rozette görünür. Bir çalışma yaklaşık 5–8 dakika sürer; özel repolarda bu süre aylık ücretsiz dakika kotasından düşer.

## Sorun giderme

- **"A compatible .NET SDK was not found"**: `global.json` .NET 10 SDK istiyor. `dotnet --list-sdks` ile kurulu sürümleri kontrol edin.
- **PowerShell betik çalıştırmayı engelliyor**: Komutu yukarıdaki gibi `-ExecutionPolicy Bypass` ile çalıştırın.
- **Docker "Engine" çalışmıyor**: Docker Desktop'ı açın, "Engine running" yazısını bekleyin.
- **`.env` silindi, SQL Server artık açılmıyor**: Veritabanı eski şifreyle kalır. Yerel veriyi silip baştan kurmak için `docker compose down -v`, ardından `scripts\db-up.ps1`.
- **Port 14333 dolu**: `.env` içindeki `MSSQL_PORT` değerini değiştirip `scripts\db-up.ps1` çalıştırın.
- **"Solution zaten var"**: Betik yalnızca boş repoda çalışır. Yeniden denemek için oluşan `src`, `tests`, `Modulix.sln*`, `.gitignore`, `.editorconfig` dosyalarını silin.
